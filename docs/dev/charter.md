## 1. 项目背景与定位

### 1.1 一句话定位

**阡陌（AgentNest）是一个云端常驻智能体交流网络：让智能体挣脱单次会话的桎梏，长期驻留、持有记忆，并且彼此可寻、可唤、可协作。**

名字出自《桃花源记》"阡陌交通，鸡犬相闻"——阡陌是纵横相连的路网，鸡犬相闻是彼此可感知、可呼应。这正是我们要给智能体建的东西：路网 + 相闻。

### 1.2 核心判断

当前主流智能体产品的形态是"会话内工具"：用户开一个窗口，智能体在窗口里干活，窗口关闭即消散。这带来两个结构性缺陷：

1. **没有持续存在**。每次都要重新解释项目背景、重新交代约束、重新建立信任。智能体无法"托付"，只能"使唤"。
2. **没有彼此**。每个智能体都是孤岛，跨项目、跨机器、跨团队的能力无法组合。用户成了智能体之间唯一的消息总线。

我们判断下一个范式是**常驻交流型智能体**：

- **常驻** = 有独立生命周期、有分层记忆、可休眠可唤醒的长期存在，而不是一次性会话。
- **交流** = 智能体之间可注册、可发现、可按名寻址、可加密通信、可协商资源，而不是必须由人转述。

### 1.3 两条产品线与飞轮

| 产品线 | 内容 | 角色 |
|---|---|---|
| ① 云端常驻编程智能体 | 沙箱驻留、项目记忆、休眠唤醒、随叫随到、模型中立 | 网络中的**节点** |
| ② 智能体通信协作网络 | 注册发现、按名寻址、加密消息、权限分级、限流防循环、跨节点资源协同 | 连接节点的**网络** |

节点提供网络存在的理由，网络提升节点的价值上限。先有可用的节点，网络才不是空壳；网络成型后，单节点的能力边界被打开。M0 必须同时验证这两端最小形态，否则飞轮无法起转。

> v2.0 补注：基座路线变更**没有改变**这个飞轮的形状，改变的是两端的起点高度。基座已经提供了一个功能完整的单机编程智能体（产品线 ①的躯干），而产品线 ② 所需的跨机传输层在基座上游已于 2026-07 被整体删除。落到工程上就是：**节点这一端从"从零造"变成"改造与常驻化"，网络这一端仍然是纯自研，且成为新的关键路径长杆。**依据见 `base-adoption.md`。
>
> **v2.2 修正**：上段"跨机传输层在基座上游已于 2026-07 被整体删除"**不成立**——2026-07 删除的只是 Remote Control 的 `src/bridge/`，基座仍有数千行在用的跨机传输代码（含 WebSocket 与 SSE），且 `RemoteIO extends StructuredIO` 意味着**主循环已经能跑在网络传输上**。因此网络这一端**不是纯自研**，我方缺的是服务端半边与跨节点会话路由（见 §3.3 C-3）。**"存在长杆"的结论不变，变的是长杆位置**：新的长杆是跨节点 activator 与休眠，二者都没有扩展点可挂。行数、出处与逐条依据见 `selection-m0.md` §2、§5。

### 1.4 总体架构（五层）

```
应用层      编程智能体 / 运维值守 / 协作开发
调度层      原因级诊断 / 资源协商 / 隧道扩容
通信层      注册发现 / 加密消息 / 空闲唤醒
运行时层    会话管理 / 分层记忆 / 休眠唤醒
接入层      云端沙箱 / 本地服务器 / 多模型适配
------------------------------------------------
纵贯全层：安全与权限模型
对外兼容：MCP（工具接入）、A2A（智能体互操作）
```

### 1.5 分层记忆

| 层 | 内容 | 生命周期 |
|---|---|---|
| 工作记忆 | 当前任务的对话与中间状态 | 任务级，任务结束沉淀或丢弃 |
| 项目记忆 | 代码库理解、历史决策、约定与踩坑 | 项目级，长期保留，可人工废止 |
| 基线与周期档案 | 用量基线、赛事日历、长期趋势 | 账户级，持续累积 |

两个动作贯穿三层：**沉淀归档**（低层向高层压缩）与**检索唤醒**（高层向低层注入）。

### 1.6 安全设计哲学：爆炸半径控制

我们不用"层层人工审批"换安全——那会把常驻智能体退化成需要人盯着的会话工具。我们用**可恢复性**兜底：

- 不可逆操作隔离（删除、发布、支付走独立通道与独立确认）
- 备份对智能体不可删除（备份介质在沙箱权限之外）
- 金额与资源硬上限（协议层强制，不依赖智能体自觉）
- **消息不能替用户授权**：智能体之间的消息只能传递请求，不能构成用户授权；越权动作必须回到用户授权链路
- 全部消息留痕可溯（trace_id 贯穿，审计日志只增不改）
- 数据境内存储

## 2. 目标与非目标

### 2.1 M0 目标（2026H2，原型验证期）

M0 只回答一个问题：**"常驻 + 交流"这条路在工程上走得通吗？** 具体拆成三件事：

### 3.3 通信层

- **C-1 消息协议与信封**：地址格式 `qianmo://<node>/<agent>`、消息生命周期状态机、错误码表、hop/trace 字段。协议资产的处置见 §5.5（**已决**：`@qianmo/protocol` 已从历史提交 `67f6081` 原样复活）。**基座起点：自研**。**v2.2 决议**：协议**自研 + 概念对齐 A2A，不采用 A2A 子集**——A2A v1.0 规范中完全不存在 hop / TTL / 环路检测 / 去重键字段（已逐词检索确认），阡陌 AC-3 依赖的核心字段在其中只能塞进扩展位；免费对齐的只有三处：任务状态机名、`taskId` / `contextId` 分离、Agent Card 形状。`trace_id` 采用 **W3C `traceparent` 格式**（MCP 规范 SEP-414 已采纳，免费获得生态互通），C-6 的贯穿字段同此。**N-4 与 P-4（A2A 对齐评估报告）不变。**依据见 `selection-m0.md` §4。（喻永昌 / 陈曦宇）

- **C-3 节点间传输通道**：长连接 + TLS + 预共享密钥握手，断线重连，at-least-once 投递 + 去重。**基座起点：部分**（**v2.2 修正**：原判定"自研——基座上游已于 2026-07 删除全部远程传输层"**不成立**。删除的只是 Remote Control 的 `src/bridge/`；基座仍有数千行在用的传输代码，且 `RemoteIO extends StructuredIO` 意味着主循环已能跑在网络传输上。我方缺的是**服务端半边与跨节点会话路由**。**但请保留态度**：由此得出的工作量下调**仅凭"代码存在与形状"判断，可改造性未验证**，要 S0 实际动手才知道，不作为排期承诺。依据见 `selection-m0.md` §2）。（陈曦宇）
- **C-4 防循环与限流**：**处理者粒度查重**（首次回访同一处理者地址 + 同一任务标识即切断）+ `LIMITS.maxHops` 兜底、消息指纹去重、运行时层令牌桶限流、`loop_detected` 审计事件。**所有协议级数值上限以 `@qianmo/protocol` 的 `LIMITS` 为唯一出处**（`maxHops=8`、`maxMessageBytes=256KiB`、`defaultTtlMs=30s`、`defaultTaskTtlMs=5min`、`ratePerMinute=600`），文档与其他包不得各写一份。**基座起点：自研**（基座信箱有配额但无跳数与循环概念）。**v2.2 修正**（随 D-2）：查重粒度由原文的"hops 查重（回环即时切断）"——即**节点**粒度——改为**同一处理者地址（node/agent）+ 同一任务标识**，`LIMITS.maxHops` 相应降为纯兜底；理由是节点粒度会误杀合法 spiral，RFC 3261 附录 A 已将其定性为规范级 bug。**另需注意**：`ttlMs` 当前同时承担**投递时限**与**任务时限**，与 AC-2 的 ack 预算相矛盾；拆分为两个字段（投递时限 / 任务时限）**已由 P1.1 落实**（`docs/dev/protocol.md` §5）：`defaultTtlMs` 收窄为**仅投递时限**（`created → acked`），新增 **`defaultTaskTtlMs = 5 min`** 承担**任务时限**（`created → completed / failed`），取值精确对齐 §4 AC-2 的 result 线——超过它的任务本就已经验收失败，协议不该还算它活着；冻结期由时间跳跃闸门排除，不烧任务预算。**数值仍以 `LIMITS` 为唯一出处。**依据见 `selection-m0.md` §2。（陈曦宇）
- **C-5 权限分级**：智能体身份、能力清单、三级权限（只读 / 受限写 / 需用户确认），强制"消息不能替用户授权"。**基座起点：部分**——基座有工具权限模式与审批链路可复用，跨节点身份与授权不可跨越是自研。**v2.2 决议**：capability 用**每节点 Ed25519 密钥签发**，预共享密钥**仅作接入门禁**。理由：PSK 是对称的，任何持钥节点都能伪造**任意节点**签发的令牌（含"用户已确认"凭证），本条会从**结构性保证退化为约定**。M0 自研约 200 行，`node:crypto` / WebCrypto 已实测可用、零依赖。**与 N-3 的界线**：N-3"不做 PKI、不做证书签发与轮换"**不变**——它禁止的是证书体系（CA、签发链、证书轮换与托管），而**节点级密钥对自签 capability 不属于该禁止范围**，两者不冲突。依据见 `selection-m0.md` §4。（陈曦宇）
- **C-6 审计与全链路追踪**：trace_id 贯穿、消息全量留痕、日志查询 CLI。**基座起点：部分**。（陈曦宇 / 陈子轩）

### 5.2 法律状态：许可链清晰，但溯源仍需谨慎

**这是本次变更中最容易被误读的一节。**基座换成自有 MIT 项目解决了"能不能用"的问题，**没有**解决"这份代码的血统是什么"的问题。两件事分开说：

**① 许可链（已解决）**

- 基座以 MIT 授权。MIT 明确允许使用、复制、修改、合并、发布、再分发，唯一条件是保留版权声明与许可声明。
- 因此阡陌可以：把基座代码入库、修改它、把它编译进产物、随演示材料分发、开源发布。**旧版 §5.2 的两条硬约束（不可再分发、不可作为交付物）随之作废。**
- 阡陌仓库 `LICENSE` **沿用基座 MIT**。自研 `@qianmo/*` 作为 workspace 包随仓库以 MIT 发布（旧版的 Apache-2.0 决定作废，见 §5.5）。

**② 溯源（未消失，需如实陈述）**

### 5.5 自研边界与成果归属

- **阡陌自有代码有两种形态**：① `packages/` 下的 `@qianmo/*` workspace 包（沿用既有命名，`@qianmo/<domain>` 单段）；② 对基座运行时的常驻化改造（直接改基座代码，不另建平行实现）。
- **许可**：随仓库以 MIT 发布。旧版的 Apache-2.0 决定及配套的版权头模板**作废**，S0 内清理。
  - **版权头（v2.5：已决 —— 加）**：给 `@qianmo/*` 全部自有源文件加统一版权头，格式为文件最前两行行注释 `// Copyright 2026 Qianmo AgentNest Team` + `// SPDX-License-Identifier: MIT`，与原有模块级 JSDoc 之间空一行。理由：风险 L-1（成果认定争议）评级为高/中，逐文件版权头是软著材料的标准实践且**零运行时成本**，"与基座现状一致"抵不过 L-1。**已于 P0.5 落地，覆盖 `protocol` / `registry` 两包 `src/` 与 `test/` 共 15 个 `.ts` 文件**；此后新增的 `@qianmo/*` 源文件一律带头，**不为此新增 CI 断言**（漏加由 PR 评审兜）。原「提请评审」条就此关闭。
- **成果边界的技术基线**（**v2.4 修正**，见下方「举证命令勘误」）：基座以零改动快照**导入于本仓库提交 `3380c88`**（一次性引入 3,911 个文件），对应上游 open-claude-code 的 `848ad8c2` = v2.38.3。此后**所有**提交都是阡陌工作，因此：
  - `git diff 3380c88..HEAD` 即为本项目的工作面，`git log 3380c88..HEAD` 即为工作记录；
  - 另加导入**之前**的两个立项提交 `67f6081`（立项初始化）与 `74f7a22`（撤下洁净室脚手架），它们同样是阡陌工作；
  - 基座的贡献边界可用 `git show --stat 3380c88` 单独举出，与我方工作互不混排。
  - **举证命令勘误**：`848ad8c2` 是**上游仓库**的提交 SHA。本仓库经快照导入、**不含上游 git 历史**，故该 SHA 在本仓库**不是有效 git 对象**——旧文写的 `git diff 848ad8c2..HEAD` / `git log 848ad8c2..HEAD` **无法执行**（实跑报 `unknown revision`）。上游溯源以 `BASE.md` 的记录 + 与上游仓库比对为准，不经本仓库 git 对象。

### 7.1 分工表

### 7.2 工作方式

1. **文档先行**：任何核心模块开工前，先在 `docs/dev/` 提交设计文档并通过评审。无设计文档的功能 PR 不予合入。
2. **集体评审**：协议变更、安全模型变更、跨模块接口变更必须全员评审。评审时**该方向辅助人**必须在场并能复述设计意图。
3. **双人懂原理**（**v2.3 措辞对齐 §7.1**）：**主开发 + 方向辅助人**的双人知情制——每个核心模块除主开发外，该方向的辅助人须能复述其设计原理；M0 结项时双人签字确认（P9.3）保留不变。
4. **迭代节奏**：双周迭代（周一开始、周日结束），每周一次同步会（30 min，只对齐阻塞项），每迭代末做复盘 + 下期任务包确认。
5. **代码规范**：全部走 PR + 至少一人评审；**沿用基座门禁**——`bun run precheck`（typecheck + lint + test）零错误，CI 全绿方可合入；不允许直推主干。提交用 Conventional Commits + 中文描述（基座既有约定）。
6. **边界日**：每双周固定半天，全员主动注入故障、找边界问题，产出即 CI 用例（对策 T-2）。
7. **v2.0 新增 · 改造优先走扩展点**：能用基座既有扩展点实现的，不改基座核心。必须改核心时，PR 描述里注明"为什么扩展点不够用"（对策 T-5）。
