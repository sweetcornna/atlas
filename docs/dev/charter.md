## 1. 项目背景与定位

### 1.1 一句话定位

**阡陌（AgentNest）是一个云端常驻智能体交流网络：让智能体挣脱单次会话的桎梏，长期驻留、持有记忆，并且彼此可寻、可唤、可协作。**

名字出自《桃花源记》"阡陌交通，鸡犬相闻"——阡陌是纵横相连的路网，鸡犬相闻是彼此可感知、可呼应。这正是我们要给智能体建的东西：路网 + 相闻。

### 1.2 核心判断

当前主流智能体产品的形态是"会话内工具"：用户开一个窗口，智能体在窗口里干活，窗口关闭即消散。这带来两个结构性缺陷：

1. **没有持续存在**。每次都要重新解释项目背景、重新交代约束、重新建立信任。智能体无法"托付"，只能"使唤"。
2. **没有彼此**。每个智能体都是孤岛，跨项目、跨机器、跨团队的能力无法组合。用户成了智能体之间唯一的消息总线。

我们判断下一个范式是**常驻交流型智能体**：

- **常驻** = 有独立生命周期、有分层记忆、可休眠可唤醒的长期存在，而不是一次性会话。
- **交流** = 智能体之间可注册、可发现、可按名寻址、可加密通信、可协商资源，而不是必须由人转述。

### 1.3 两条产品线与飞轮

| 产品线 | 内容 | 角色 |
|---|---|---|
| ① 云端常驻编程智能体 | 沙箱驻留、项目记忆、休眠唤醒、随叫随到、模型中立 | 网络中的**节点** |
| ② 智能体通信协作网络 | 注册发现、按名寻址、加密消息、权限分级、限流防循环、跨节点资源协同 | 连接节点的**网络** |

节点提供网络存在的理由，网络提升节点的价值上限。先有可用的节点，网络才不是空壳；网络成型后，单节点的能力边界被打开。M0 必须同时验证这两端最小形态，否则飞轮无法起转。

> v2.0 补注：基座路线变更**没有改变**这个飞轮的形状，改变的是两端的起点高度。基座已经提供了一个功能完整的单机编程智能体（产品线 ①的躯干），而产品线 ② 所需的跨机传输层在基座上游已于 2026-07 被整体删除。落到工程上就是：**节点这一端从"从零造"变成"改造与常驻化"，网络这一端仍然是纯自研，且成为新的关键路径长杆。**依据见 `base-adoption.md`。

### 1.4 总体架构（五层）

```
应用层      编程智能体 / 运维值守 / 协作开发
调度层      原因级诊断 / 资源协商 / 隧道扩容
通信层      注册发现 / 加密消息 / 空闲唤醒
运行时层    会话管理 / 分层记忆 / 休眠唤醒
接入层      云端沙箱 / 本地服务器 / 多模型适配
------------------------------------------------
纵贯全层：安全与权限模型
对外兼容：MCP（工具接入）、A2A（智能体互操作）
```

### 1.5 分层记忆

| 层 | 内容 | 生命周期 |
|---|---|---|
| 工作记忆 | 当前任务的对话与中间状态 | 任务级，任务结束沉淀或丢弃 |
| 项目记忆 | 代码库理解、历史决策、约定与踩坑 | 项目级，长期保留，可人工废止 |
| 基线与周期档案 | 用量基线、赛事日历、长期趋势 | 账户级，持续累积 |

两个动作贯穿三层：**沉淀归档**（低层向高层压缩）与**检索唤醒**（高层向低层注入）。

### 1.6 安全设计哲学：爆炸半径控制

我们不用"层层人工审批"换安全——那会把常驻智能体退化成需要人盯着的会话工具。我们用**可恢复性**兜底：

- 不可逆操作隔离（删除、发布、支付走独立通道与独立确认）
- 备份对智能体不可删除（备份介质在沙箱权限之外）
- 金额与资源硬上限（协议层强制，不依赖智能体自觉）
- **消息不能替用户授权**：智能体之间的消息只能传递请求，不能构成用户授权；越权动作必须回到用户授权链路
- 全部消息留痕可溯（trace_id 贯穿，审计日志只增不改）
- 数据境内存储

## 2. 目标与非目标

### 2.1 M0 目标（2026H2，原型验证期）

M0 只回答一个问题：**"常驻 + 交流"这条路在工程上走得通吗？** 具体拆成三件事：

1. **编程智能体最小可用版**：能在沙箱内驻留、持有项目记忆、进程重启后续答、能真实完成团队自有仓库的小型编码任务。
2. **双节点通信原型**：两台节点上的智能体经注册中心按名互寻，加密投递消息，唤醒对端休眠智能体，全链路可审计、防循环、可限流。
3. **数模竞赛场景演示**：以数学建模竞赛周期为首个压力场景，端到端演示原因级诊断 → 竞赛算力互援 → 预测性扩容。

M0 的产出是**可演示、可复现、可测量的原型**，不是可交付用户的产品。验收标准见 §4。

### 2.2 非目标（M0 明确不做）

写下来是为了在答辩压力和演示诱惑面前守住范围。以下每一条都是主动放弃，不是遗漏：

| # | 不做 | 理由 / M0 替代方案 |
|---|---|---|
| N-1 | **计费与结算** | 不做用量计价、账单、支付。协议层保留 `cost_limit` 字段但恒为 0，只验证"硬上限能拦住"这个机制。 |
| N-2 | **多租户与租户隔离** | M0 全部节点属于同一团队、同一信任域。不做账号体系、不做租户级数据隔离。内测（M1）再做。 |
| N-3 | **生产级加密** | M0 用 TLS + 预共享密钥握手，够演示不够上线。不做 PKI、不做证书签发与轮换、不做端到端加密、不做密钥托管。M1 替换为 mTLS。 |

| N-12 | **性能优化** | M0 只测基线、不调优。除非某项指标卡住验收标准（如唤醒延迟），否则不投入优化工时。 |

### 3.3 通信层

- **C-1 消息协议与信封**：地址格式 `qianmo://<node>/<agent>`、消息生命周期状态机、错误码表、hop/trace 字段。协议资产是否从历史提交 `67f6081` 复活见 §5.5。**基座起点：自研**。（喻永昌 / 陈曦宇）
- **C-2 注册中心与按名寻址**：注册 / 心跳 / 注销 / 查询，跨节点地址解析。**基座起点：部分**——基座的 Agent Teams 有单机 roster 与按名信箱寻址，但明确不支持跨会话/跨主机寻址。（陈曦宇）
- **C-3 节点间传输通道**：长连接 + TLS + 预共享密钥握手，断线重连，at-least-once 投递 + 去重。**基座起点：自研**——基座上游已于 2026-07 删除全部远程传输层。（陈曦宇）
- **C-4 防循环与限流**：hops 查重（回环即时切断）+ `LIMITS.maxHops` 兜底、消息指纹去重、运行时层令牌桶限流、`loop_detected` 审计事件。**所有协议级数值上限以 `@qianmo/protocol` 的 `LIMITS` 为唯一出处**（`maxHops=8`、`maxMessageBytes=256KiB`、`defaultTtlMs=30s`、`ratePerMinute=600`），文档与其他包不得各写一份。**基座起点：自研**（基座信箱有配额但无跳数与循环概念）。（陈曦宇）
- **C-5 权限分级**：智能体身份、能力清单、三级权限（只读 / 受限写 / 需用户确认），强制"消息不能替用户授权"。**基座起点：部分**——基座有工具权限模式与审批链路可复用，跨节点身份与授权不可跨越是自研。（陈曦宇）
- **C-6 审计与全链路追踪**：trace_id 贯穿、消息全量留痕、日志查询 CLI。**基座起点：部分**。（陈曦宇 / 陈子轩）

### 3.4 调度层

## 4. M0 验收标准

### 5.2 法律状态：许可链清晰，但溯源仍需谨慎

**这是本次变更中最容易被误读的一节。**基座换成自有 MIT 项目解决了"能不能用"的问题，**没有**解决"这份代码的血统是什么"的问题。两件事分开说：

**① 许可链（已解决）**

- 基座以 MIT 授权。MIT 明确允许使用、复制、修改、合并、发布、再分发，唯一条件是保留版权声明与许可声明。
- 因此阡陌可以：把基座代码入库、修改它、把它编译进产物、随演示材料分发、开源发布。**旧版 §5.2 的两条硬约束（不可再分发、不可作为交付物）随之作废。**
- 阡陌仓库 `LICENSE` **沿用基座 MIT**。自研 `@qianmo/*` 作为 workspace 包随仓库以 MIT 发布（旧版的 Apache-2.0 决定作废，见 §5.5）。

**② 溯源（未消失，需如实陈述）**

基座本身是**对 Anthropic Claude Code 的逆向恢复实现**。基座 `README.zh.md` 自述其定位为"以逆向复原（reverse-engineered restoration）的代码为基座，由社区维护和优化的衍生版本"，并在致谢中记录它 fork 自另一个还原工程。由此得出三条**不因换基座而放松**的纪律：

1. **MIT 是基座作者对其自身还原与原创工作的授权**，不构成、也无法构成 Anthropic 对其上游表达的授权。对外表述必须准确到这一层，见 §5.8。
2. **商标不随代码走。**"Claude"、"Claude Code"、"Anthropic" 是 Anthropic PBC 的商标。阡陌与 Anthropic **无关联、未获背书**。
3. **对官方 Claude Code 的行为参考，继续执行"结论性描述、不复现表达"的既有纪律**（原 §5.6，现 §5.6 第 2 条）。这条纪律的对象从"旧基座"换成了"Anthropic 官方 Claude Code"，强度不变。

**③「明确不改」清单（新增约束）**

基座 `src/constants/brand.ts` 顶部注释列出了一批**看起来像品牌、实际承载协议**的字符串，改了会以难以诊断的方式坏掉。阡陌做身份隔离改名时**同样不动**：

- 系统提示词的 `You are Claude Code, Anthropic's official CLI for Claude` 前缀（Anthropic 侧的提示缓存与行为调优按这段文本命中）
- `claude-code/<version>` User-Agent（Anthropic 侧限流与资格判定读它）
- OTel `service.name: 'claude-code'`
- `CLAUDE.md` / `CLAUDE.local.md` / `AGENTS.md` 文件名（跨工具生态约定）
- 子进程环境变量 `CLAUDECODE=1`（跨工具提示协议）

> 这里有一个必须让全员理解的张力：上面这几条要求我们**保留** Anthropic 相关标识，而 §5.2② 要求我们对外**不暗示关联**。两者不冲突——前者是让协议继续工作的技术约束，后者是对外表述约束。**技术上保留 ≠ 对外宣称。**判断口径以 §5.8 为准，有疑问找安全 owner（陈曦宇），不要自行决定。

### 7.2 工作方式

1. **文档先行**：任何核心模块开工前，先在 `docs/dev/` 提交设计文档并通过评审。无设计文档的功能 PR 不予合入。
2. **集体评审**：协议变更、安全模型变更、跨模块接口变更必须全员评审。评审时 backup 必须在场并能复述设计意图。
3. **双人懂原理**：每个核心模块 owner + backup 双人制，M0 结项时双人签字确认（P9.3）。
4. **迭代节奏**：双周迭代（周一开始、周日结束），每周一次同步会（30 min，只对齐阻塞项），每迭代末做复盘 + 下期任务包确认。
5. **代码规范**：全部走 PR + 至少一人评审；**沿用基座门禁**——`bun run precheck`（typecheck + lint + test）零错误，CI 全绿方可合入；不允许直推主干。提交用 Conventional Commits + 中文描述（基座既有约定）。
6. **边界日**：每双周固定半天，全员主动注入故障、找边界问题，产出即 CI 用例（对策 T-2）。
7. **v2.0 新增 · 改造优先走扩展点**：能用基座既有扩展点实现的，不改基座核心。必须改核心时，PR 描述里注明"为什么扩展点不够用"（对策 T-5）。
