## 1. 项目背景与定位

### 1.1 一句话定位

**阡陌（AgentNest）是一个云端常驻智能体交流网络：让智能体挣脱单次会话的桎梏，长期驻留、持有记忆，并且彼此可寻、可唤、可协作。**

名字出自《桃花源记》"阡陌交通，鸡犬相闻"——阡陌是纵横相连的路网，鸡犬相闻是彼此可感知、可呼应。这正是我们要给智能体建的东西：路网 + 相闻。

### 1.2 核心判断

当前主流智能体产品的形态是"会话内工具"：用户开一个窗口，智能体在窗口里干活，窗口关闭即消散。这带来两个结构性缺陷：

1. **没有持续存在**。每次都要重新解释项目背景、重新交代约束、重新建立信任。智能体无法"托付"，只能"使唤"。
2. **没有彼此**。每个智能体都是孤岛，跨项目、跨机器、跨团队的能力无法组合。用户成了智能体之间唯一的消息总线。

我们判断下一个范式是**常驻交流型智能体**：

- **常驻** = 有独立生命周期、有分层记忆、可休眠可唤醒的长期存在，而不是一次性会话。
- **交流** = 智能体之间可注册、可发现、可按名寻址、可加密通信、可协商资源，而不是必须由人转述。

### 1.3 两条产品线与飞轮

| 产品线 | 内容 | 角色 |
|---|---|---|
| ① 云端常驻编程智能体 | 沙箱驻留、项目记忆、休眠唤醒、随叫随到、模型中立 | 网络中的**节点** |
| ② 智能体通信协作网络 | 注册发现、按名寻址、加密消息、权限分级、限流防循环、跨节点资源协同 | 连接节点的**网络** |

节点提供网络存在的理由，网络提升节点的价值上限。先有可用的节点，网络才不是空壳；网络成型后，单节点的能力边界被打开。M0 必须同时验证这两端最小形态，否则飞轮无法起转。

### 1.4 总体架构（五层）

```
应用层      编程智能体 / 运维值守 / 协作开发
调度层      原因级诊断 / 资源协商 / 隧道扩容
通信层      注册发现 / 加密消息 / 空闲唤醒
运行时层    会话管理 / 分层记忆 / 休眠唤醒
接入层      云端沙箱 / 本地服务器 / 多模型适配
------------------------------------------------
纵贯全层：安全与权限模型
对外兼容：MCP（工具接入）、A2A（智能体互操作）
```

### 1.5 分层记忆

| 层 | 内容 | 生命周期 |
|---|---|---|
| 工作记忆 | 当前任务的对话与中间状态 | 任务级，任务结束沉淀或丢弃 |
| 项目记忆 | 代码库理解、历史决策、约定与踩坑 | 项目级，长期保留，可人工废止 |
| 基线与周期档案 | 用量基线、赛事日历、长期趋势 | 账户级，持续累积 |

两个动作贯穿三层：**沉淀归档**（低层向高层压缩）与**检索唤醒**（高层向低层注入）。

### 1.6 安全设计哲学：爆炸半径控制

我们不用"层层人工审批"换安全——那会把常驻智能体退化成需要人盯着的会话工具。我们用**可恢复性**兜底：

- 不可逆操作隔离（删除、发布、支付走独立通道与独立确认）
- 备份对智能体不可删除（备份介质在沙箱权限之外）
- 金额与资源硬上限（协议层强制，不依赖智能体自觉）
- **消息不能替用户授权**：智能体之间的消息只能传递请求，不能构成用户授权；越权动作必须回到用户授权链路
- 全部消息留痕可溯（trace_id 贯穿，审计日志只增不改）
- 数据境内存储

## 2. 目标与非目标

### 2.1 M0 目标（2026H2，原型验证期）

M0 只回答一个问题：**"常驻 + 交流"这条路在工程上走得通吗？** 具体拆成三件事：

1. **编程智能体最小可用版**：能在沙箱内驻留、持有项目记忆、进程重启后续答、能真实完成团队自有仓库的小型编码任务。
2. **双节点通信原型**：两台节点上的智能体经注册中心按名互寻，加密投递消息，唤醒对端休眠智能体，全链路可审计、防循环、可限流。
3. **数模竞赛场景演示**：以数学建模竞赛周期为首个压力场景，端到端演示原因级诊断 → 竞赛算力互援 → 预测性扩容。

M0 的产出是**可演示、可复现、可测量的原型**，不是可交付用户的产品。验收标准见 §4。

### 2.2 非目标（M0 明确不做）

写下来是为了在答辩压力和演示诱惑面前守住范围。以下每一条都是主动放弃，不是遗漏：

| # | 不做 | 理由 / M0 替代方案 |
|---|---|---|
| N-1 | **计费与结算** | 不做用量计价、账单、支付。协议层保留 `cost_limit` 字段但恒为 0，只验证"硬上限能拦住"这个机制。 |
| N-2 | **多租户与租户隔离** | M0 全部节点属于同一团队、同一信任域。不做账号体系、不做租户级数据隔离。内测（M1）再做。 |
| N-3 | **生产级加密** | M0 用 TLS + 预共享密钥握手，够演示不够上线。不做 PKI、不做证书签发与轮换、不做端到端加密、不做密钥托管。M1 替换为 mTLS。 |
| N-4 | **跨厂商 A2A 完整实现** | 只做协议对齐评估报告与字段映射分析（见 §3 P6.4），不实现完整 A2A 协议栈，不追求与任何第三方智能体真实互通。 |
| N-5 | **图形界面 / Web 控制台** | M0 全部交互走 CLI + 结构化日志。演示靠终端与日志回放，不投入前端。 |
| N-6 | **高可用与水平扩展** | 注册中心单点部署，允许单点故障。不做主从、不做集群、不做故障自动转移。 |
| N-7 | **真实云厂商弹性扩容对接** | "隧道扩容"在 M0 用两台自有/学生机模拟，不接入任何公有云弹性 API，不做实例申领与计费联动。 |
| N-8 | **语义/向量记忆检索** | M0 只做确定性检索（结构化条目 + 标签 + 关键词 + 时间衰减）。向量检索的召回质量不可控，放到 M1 与治理机制一起做。 |
| N-9 | **智能体市场 / 插件生态 / 移动端** | 与验证核心判断无关，一律不碰。 |
| N-10 | **商业化动作** | 不做定价方案、不做用户增长、不做对外招募。2028 商业化的前提是先跑通 M0/M1。 |
| N-11 | **形式化验证与合规认证** | 不做协议形式化证明，不申请任何安全认证。安全靠边界用例库（§4 AC-8）保障。 |
| N-12 | **性能优化** | M0 只测基线、不调优。除非某项指标卡住验收标准（如唤醒延迟），否则不投入优化工时。 |

## 3. 范围：M0 功能清单

按五层架构组织。每项标注负责方向，详细排期见 `roadmap.md`。

### 3.1 接入层

- **A-1 云端沙箱执行环境**：容器化工作区、路径白名单、宿主路径只读挂载、命令超时与资源上限。（董宗岳）
- **A-2 多模型适配层**：统一 `chat / tool_call / stream` 接口，至少 2 家供应商实现，能力探测与降级。切换供应商只改配置不改代码。（董宗岳 / 陈子轩）
- **A-3 本地节点部署脚本**：两台节点一键部署、种子数据、一键重置。（董宗岳）

### 3.2 运行时层

- **R-1 会话持久化**：append-only 事件日志 + SQLite 快照，进程崩溃后凭持久化会话恢复上下文。（董宗岳）
- **R-2 分层记忆**：工作/项目/基线三层 schema，条目带来源与时间戳，沉淀归档任务，确定性检索唤醒并注入提示词。（董宗岳 / 李怡康）
- **R-3 休眠与唤醒**：温休眠（进程退出、状态落盘）；唤醒触发源为消息到达 / 定时 / 手动；冷启动耗时埋点。（董宗岳）
- **R-4 备份与不可删除保护**：工作区快照托管在沙箱权限之外，智能体只写不删。（董宗岳）

### 3.3 通信层

- **C-1 消息协议与信封**：地址格式 `qianmo://<node>/<agent>`（以 `@qianmo/protocol` 的 `ADDRESS_SCHEME` 为准）、消息生命周期状态机、错误码表、hop/trace 字段。（喻永昌 / 陈曦宇）
- **C-2 注册中心与按名寻址**：注册 / 心跳 / 注销 / 查询，跨节点地址解析。（陈曦宇）
- **C-3 节点间传输通道**：长连接 + TLS + 预共享密钥握手，断线重连，at-least-once 投递 + 去重。（陈曦宇）
- **C-4 防循环与限流**：hops 查重（回环即时切断）+ `LIMITS.maxHops` 兜底、消息指纹去重、运行时层令牌桶限流、`loop_detected` 审计事件。**所有协议级数值上限以 `@qianmo/protocol` 的 `LIMITS` 为唯一出处**（`maxHops=8`、`maxMessageBytes=256KiB`、`defaultTtlMs=30s`、`ratePerMinute=600`），文档与其他包不得各写一份。（陈曦宇）
- **C-5 权限分级**：智能体身份、能力清单、三级权限（只读 / 受限写 / 需用户确认），强制"消息不能替用户授权"。（陈曦宇）
- **C-6 审计与全链路追踪**：trace_id 贯穿、消息全量留痕、日志查询 CLI。（陈曦宇 / 陈子轩）

### 3.4 调度层

- **S-1 原因级诊断**：故障分类为 OOM / 超时 / 依赖缺失 / 磁盘满 / 额度耗尽等结构化 `diagnosis` 事件，而非笼统"失败"。（李怡康）
- **S-2 资源协商协议**：请求 → 报价 → 授权 → 释放 四段式，时长/CPU/金额硬上限。（喻永昌）
- **S-3 按需加密隧道**：授权后建立，任务结束 / 超时 / 异常退出三种情况均自动拆除并留痕。（陈曦宇）
- **S-4 预测性扩容 v0**：基于用量基线 + 赛事日历提前触发扩容。（李怡康）

### 3.5 应用层

- **P-1 编程智能体 CLI**：接任务 → 读代码 → 改文件 → 跑测试 → 报结果 的最小闭环。（陈子轩）
- **P-2 数模竞赛场景演示**：完整分镜脚本、数据集、一键复现。（李怡康）
- **P-3 MCP 兼容子集**：作为 MCP client 接入 ≥2 个现成 MCP server。（董宗岳）
- **P-4 A2A 对齐评估报告**：字段映射与差距分析，不实现。（喻永昌）

### 3.6 工程与质量

- **E-1 monorepo 工程地基**：Bun workspaces、`packages/` 下 `@qianmo/*` 包、TypeScript、lint、CI。（董宗岳 / 陈子轩）
- **E-2 基座拉取与隔离机制**：`scripts/fetch-base.sh`、`vendor/` gitignore、pre-commit 拦截、CI vendor-guard。（陈子轩）
- **E-3 边界用例库**：五类通信边界问题的自动化测试，进 CI 门禁。（陈子轩）
- **E-4 基线报告**：唤醒延迟、消息吞吐、内存占用，作为 M1 对比基准。（李怡康）

## 4. M0 验收标准

以下 8 条是 M0 的出口条件。每条都必须**可脚本化复现、可录屏演示、有明确判据**。全部 PASS 或对未通过项有书面豁免决议，M0 方可结项。逐条走查安排见 roadmap 的 P8.2。

| 编号 | 验收标准 | 判据 | 依赖功能 |
|---|---|---|---|
| **AC-1** | **进程重启后凭持久化会话恢复上下文并续答** | 智能体 A 在多轮任务途中被 `kill -9`；重启进程后不重放对话历史，直接追问"继续刚才那步"，输出与重启前上下文一致（引用到重启前才知道的项目细节）；`session_id` 保持一致；从进程启动到可接收新消息 ≤ 10 s。脚本 `demo/ac1-restart.sh` 一键复现。 | R-1 |
| **AC-2** | **跨节点按名寻址唤醒休眠智能体并回执** | 节点 A 上的智能体经注册中心解析 `qianmo://node-b/reviewer`，向节点 B 上处于休眠态（进程不在内存、状态仅落盘）的智能体投递任务消息；对端被唤醒并在 **60 s 内返回 ack 回执**，在 **5 min 内返回任务结果**。连续 10 次测量，ack P95 ≤ 60 s、成功率 10/10。 | C-1/C-2/C-3, R-3 |
| **AC-3** | **消息循环被即时切断，两层限流各自生效** | 人为构造 A→B→A 回环，防循环机制在**首次回访节点时即被切断（≤ 2 跳）**——协议层 hops 查重先于 `LIMITS.maxHops = 8` 兜底上限生效——并产生 1 条 `loop_detected` 审计事件，含完整消息链 trace_id。限流分两层独立验证：① **运行时层**单发送方对单目标 60 s / 20 条，第 21 条被拒并返回明确错误码；② **协议层**接收节点对单发送方的入站预算 `LIMITS.ratePerMinute = 600`。两层机制不得混写。 | C-4/C-6 |
| **AC-4** | **项目记忆可跨会话检索唤醒** | 向项目记忆写入一条历史决策（如"本项目统一用 Bun 作为运行时与测试器，不引入 npm/pnpm"）；新开一个**无任何对话历史**的工作记忆会话，提问相关问题；智能体的回答命中该决策，且在输出中标注记忆条目来源 ID 与写入时间。对 5 条不同决策测试，命中 5/5，且对未写入的伪造决策不产生幻觉引用。 | R-2 |
| **AC-5** | **模型中立：同一任务在两家供应商下均跑通** | 同一条编程任务用例脚本，在 ≥ 2 个不同模型供应商适配器下均完成并通过任务自带的测试断言；两次运行**仅修改配置文件，不改任何代码**；适配器一致性测试套件（多轮 / 工具调用 / 流式 三项）对两家全绿。 | A-2 |
| **AC-6** | **爆炸半径受控：越权被拒、删库可恢复** | 三个子项全部通过：(a) 沙箱内向宿主白名单外路径写入被拒，产生审计事件；(b) 智能体执行 `rm -rf` 删除自身工作区后，由其**无删除权限**的备份在 10 min 内完整恢复，恢复后 `git status` 与删除前一致；(c) 智能体尝试删除备份本身时被拒。 | A-1, R-4, C-5 |
| **AC-7** | **数模竞赛场景端到端连续演示** | 一次 ≥ 10 min、**全程无人工修改代码或数据**的连续演示，覆盖：提交建模任务 → 节点 A 智能体失败并给出**原因级**诊断（明确报出"内存不足 OOM"而非"执行失败"）→ 向节点 B 发起资源协商 → 用户授权后建立加密隧道 → 任务在借用资源上跑完 → 隧道自动拆除并留痕。连续 3 次执行成功 3/3。 | S-1/S-2/S-3, P-1/P-2 |
| **AC-8** | **通信边界问题沉淀为自动化回归用例** | 五类边界（触发时机、超时、消息风暴、欠费/额度耗尽、异常退出）**每类至少 2 条**自动化测试用例，M0 结束时用例总数 ≥ 12 条，全部进 CI 且连续 5 次构建全绿；流程约束：M0 期间每修复一类边界问题，同一 PR 内必须附带对应用例，无用例的边界修复 PR 不予合入。 | E-3, C-1~C-4 |

**豁免规则**：任一条无法达成时，需在结项评审上说明根因、给出 M1 补做计划，并由负责人 + 该方向 owner 双签。豁免不得超过 2 条，否则 M0 判定为未通过。

### 5.2 法律状态：为什么必须小心

**该还原源码没有有效开源许可。** 没有 LICENSE 即默认"保留全部权利"，且其来源是对他人已发布产品的反向还原。由此推出两条硬约束：

1. **不可再分发**——我们不能以任何形式传播它（入库、打包、随演示材料分发、上传到任何我们控制的公开位置）。
2. **不可作为交付物**——它不能出现在我们的产品、开源仓库、软著申请材料或竞赛成果中的任何位置。

后果是实打实的：若我方仓库被认定包含或衍生自该代码，开源受阻、软著申请被驳回、竞赛成果被质疑，三者任一都足以让项目停摆。

**执行机制**：

| 机制 | 状态 | 说明 |
|---|---|---|
| `scripts/fetch-base.sh` | ✅ 已落地 | 按 pinned commit 拉取，拉完校验 `HEAD`，不符即非零退出；幂等；执行后打印中英双语禁止事项横幅。不做静默降级。 |

界线一句话说清：**可以学它怎么想，不能抄它怎么写。**

### 5.5 自研边界

- `packages/` 下全部代码为团队原创，拥有完整自主版权。
- 许可证已定为 **Apache-2.0**（根 `LICENSE`），授权范围由根 `NOTICE` 界定：仅覆盖 `packages/`、`scripts/`、根配置与团队撰写的 `docs/`，**明确不覆盖 `vendor/`**。源文件带版权头。
- 允许在**接口和协议层面**兼容外部规范（MCP、A2A）——那是公开规范，与基座无关。
- 实现必须自研。命名、结构、注释均不得沿袭基座。

### 5.6 记录义务

任何从基座得来的设计启发，必须在 `docs/dev/base-analysis.md`（NOTICE 中已指向该文件）中留一份记录，格式固定为三段：

1. **来源**：基座中的哪个模块 / 哪类行为（描述性，**不贴代码**）
2. **结论**：我们从中得到的设计判断
3. **我方实现差异**：我们打算怎么做，与它有何不同、为何不同

这份记录既是设计资产，也是将来证明"独立实现"的时间戳证据。

**硬性约束**：`docs/` 是**入库目录**，研究文档会随仓库分发。因此"不贴代码"不是文风建议而是法律要求——文档中不得出现基座源码原文、类型定义原文、`文件:行号` 级定位，也不得使用"抄 / 照搬"这类在知识产权审查中不利的措辞。第 1 段"来源"只允许**描述行为与设计意图**，不允许复现表达。研究文档的合规核查由安全 owner（陈曦宇）逐节签字，与代码 PR 评审同等对待。

### 5.7 后续替换路径

基座是脚手架，不是地基。M0 结束后必须拆掉。

| 路径 | 内容 | 优先级 |
|---|---|---|
| **A. 迁移到官方 Claude Agent SDK** | 使用有明确公开许可的官方 SDK 替代参考依赖。工作量低、法律风险最低。 | 首选 |
| **B. 净室实现（clean room）** | 阅读者只输出中文规格说明书，实现者**不接触基座**，仅依据规格实现。人员分离与文档时间戳全程留痕。 | 路径 A 覆盖不到的部分 |

**触发条件（取最早者）**：首次开源前 / 软著申请前 / 首次有外部用户前。

**里程碑硬约束**：

- **M0（P7.4）**：CI 中固化 `no-vendor` 作业——`rm -rf vendor/ && bun install && bun test && bun run typecheck` 自研包全绿，证明运行期与构建期均无基座依赖。
- **M1 结束前**：完成路径 A 或 B，`scripts/fetch-base.sh` 从仓库中删除，基座彻底退场。

### 5.8 对外表述口径

在竞赛材料、答辩、宣传中提及技术来源时，统一表述为："参考业界公开的智能体工程实践进行独立设计与实现"。**不得**出现基座仓库名、不得暗示与 Anthropic 存在授权或合作关系（根 `NOTICE` 已载明商标归属与无隶属关系声明，对外表述须与之一致）。对外材料由负责人（喻永昌）与安全方向 owner（陈曦宇）双签后方可发出。

### 7.2 工作方式

1. **文档先行**：任何核心模块开工前，先在 `docs/dev/` 提交设计文档并通过评审。无设计文档的功能 PR 不予合入。
2. **集体评审**：协议变更、安全模型变更、跨模块接口变更必须全员评审。评审时 backup 必须在场并能复述设计意图。
3. **双人懂原理**：每个核心模块 owner + backup 双人制，M0 结项时双人签字确认（P9.3）。
4. **迭代节奏**：双周迭代（周一开始、周日结束），每周一次同步会（30 min，只对齐阻塞项），每迭代末做复盘 + 下期任务包确认。
5. **代码规范**：全部走 PR + 至少一人评审；CI 门禁（lint / 类型 / 测试 / vendor-guard）全绿方可合入；不允许直推主干。
6. **边界日**：每双周固定半天，全员主动注入故障、找边界问题，产出即 CI 用例（对策 T-2）。
