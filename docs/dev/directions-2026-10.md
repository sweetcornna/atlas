## §0 范围与口径

| 方向 | 编号 | 一句话 | 能力来源 |
|---|---|---|---|
| 接力插件化 | P19 | Claude Code、Codex 等工具装上阡陌插件，本机与控制台配对一次后即可转交、查看、接回 | 阡陌自研；插件格式用各工具公开的插件接口 |
| 节点间文件互通 | P20 | 节点按地址申请另一节点的文件，所有者授权后经中枢传输、核对摘要、记审计，可汇集到一个节点 | 阡陌自研 |
| 云端电脑 | P21 | 用户为节点的主智能体开一台专属电脑和浏览器，按节点隔离、可回收，敏感操作要用户确认 | 操作电脑和浏览器的能力来自基座；阡陌负责分配、隔离、回收、授权与审计 |
| 按任务匹配模型 | P22 | 在模型服务页给代码、对话、规划、看图、生图、视频等方向各指定模型 | 阡陌自研的路由与下发；生图、视频调用各厂商公开接口 |
| 长期记忆 | P23 | 智能体记住偏好、计划、项目和日常信息；用户在控制台查看、修改、遗忘 | 在 P16 记忆之上扩展 |
| 主动执行 | P24 | 定时让节点生成简报、跟进任务、整理邮件，结果推送给用户 | 在 P13 值守作业之上扩展 |
| 应用连接 | P25 | 日历、邮件等外部服务接到中枢，智能体经中枢调用，发信和建日程要用户确认 | 阡陌自研 |

**口径**（与章程 N-9、§5.8 一致）：

- 基座自带的浏览器、电脑操作、生图工具不算阡陌成果；对外写「能力来自基座，阡陌负责分配、隔离、回收和审计」。
- 没有用真实服务验证过的接口（生图、视频、邮件、日历的具体厂商）一律标「未评估」；夹具测试通过不等于接上了真实服务。
- 部署仍按观察窗口：本轮只开发与本机验证，不部署舰队。

## §1 公共底座：控制链路与上行调用

七个方向里有四个要求中枢对节点做事（开关云端电脑、读写记忆、读写文件、问状态），有两个要求节点向中枢要东西（申请别的节点的文件、调用中枢保管凭据的应用）。现有通道各管一件事（审批订阅、对话、值守作业、接力派发），本轮新增一条通用的，两个方向共用。

**不变的约束**：节点从不主动拨号（H-2，`resident/test/no-dial.test.ts`）；信封只有 JSON、单条不超过 256 KiB（`protocol/src/limits.ts`）；节点以 Ed25519 握手认出对端（`transport/src/frames.ts`）。

### 1.1 控制链路（中枢 → 节点）

| 项 | 定案 |
|---|---|
| 谁拨号 | 中枢的 `qm console` 进程按 `--control <节点>=<ws 地址>` 对每个节点拨一条链路，签名身份与值守作业、审批相同（`--print-wake-identity` 那一把）；10 秒重连一次 |
| 节点认谁 | 节点以 `--controller <节点名>=<公钥>` 列出可以下控制命令的中枢；不在集合里的对端一律 `E_CAP_INSUFFICIENT`。与 `--trust`（谁能派任务）、`--approver`（谁能批准）三个集合分开 |
| 消息 | 新类型 `node.control`（请求）与 `node.control.result`（应答，reply 类型，沿用请求的 taskId）。请求载荷 `{op, args, actor}`：`op` 形如 `desktop.enable`、`memory.forget`、`files.read`；`actor` 是发起这次操作的控制台主体（账号或 `admin`），只进审计 |
| 节点处理 | `resident.ts` 的 `#receive` 在 authz 之后、邮箱之前截住 `node.control`，按 `op` 的前缀交给注册的处理器；处理器返回 JSON 或错误码。未注册的前缀回 `E_UNSUPPORTED` |
| 审计 | 节点每处理一条写一行 `control.<op>`（来源 `control`），中枢在动作账本记一行；两边都带同一个 taskId |
| 超时 | 中枢等应答 30 秒；文件分块等单块 30 秒 |
| 节流 | 控制链路出站单列每分钟 300 条（节点入站预算 600 的一半），不套用智能体互答的 20 条/分钟运行时节流（AC-3 ①）；页面轮询记忆、文件、云端电脑状态时不会被它卡住 |

### 1.2 上行调用（节点 → 中枢）

| 项 | 定案 |
|---|---|
| 怎么走 | 中枢在控制链路建立后发 `hub.subscribe`；节点把这条链路记为上行通道（同审批订阅的做法）。节点的宿主工具要调用中枢时发 `hub.call {callId, op, args}`，中枢回 `hub.call.result {callId, ok, value|error}` |
| 能调什么 | 本轮只有两类：`files.request`（P20）与 `connector.*`（P25）。中枢按 `op` 分发，未知的回 `unsupported` |
| 没有上行通道时 | 宿主工具直接返回「中枢未连接」，不排队、不重试；模型据此告诉用户 |
| 节点身份 | 中枢以链路握手认出的节点名为准，载荷里的节点名一律忽略 |

### 1.3 落点

- 协议：`atlas/packages/protocol` 增四个类型与载荷校验；`docs/dev/protocol.md` 增 §15。
- 节点：`atlas/packages/node/src/host/control.ts`（处理器注册表、上行调用客户端）。
- 中枢：`atlas/packages/node/src/commands/consoleControl.ts`（链路池、请求/应答关联、上行分发表）。
- 控制台端口：`deps.ts` 的各方向端口都由这一层实现，控制台包不直接碰传输。

### 1.4 安全契约（v1.1，复核 D01–D04）

- **身份**：控制链路只接受完成双向签名认证、公钥按本地配置钉住的对端；PSK 身份、信封 `from` 与载荷里的节点名都不作授权依据（D02）。回包按认证对端、连接代次与调用号关联，连接换代时旧代次的等待一律以「结果未知」结束。
- **幂等与急停**：每个控制调用带 `operationId`；有副作用的操作在节点持久化「操作号 → 参数摘要 + 结果」，同号同摘要回放原结果、同号异摘要拒绝。断线与超时分「未发出」和「结果未知」，后者不盲目重发。急停时只放行注册方逐个列出的查询、停止、撤销、清理操作，其余在处理器之前拒绝（D03）。
- **租户**：新增端口须按当前请求的租户范围包装，`actor` 只用于归因、不授予权限。包装做完之前，租户范围内的调用方拿不到这些端口（控制台对它们答 501，D01）。
- **大小**：全部报文按最终序列化后的 UTF-8 字节数检查 256 KiB；文件内容用有界 base64 分块，清单、记忆列表、邮件与日历结果分页；分块服从既有速率限制（D04）。

#### D02 实现记录（FX2）

实现：认证成功的每个 socket 分配随机 UUID 代次；上行订阅、双向 pending 与入站上下文快照共同校验 channel 和代次，换代或断线撤下旧调用。控制请求使用一次发送队列；已写入后无回包返回 `ok:false, code:'unknown'`，未写入则撤下并返回 `code:'not-sent'`，均不自动重放。急停在注册处理器与幂等账本前检查，注册项 `estopAllowed` 只匹配完整操作名，默认拒绝，`node.ping` 放行并复用现有 `E_BUSY` 拒绝码。（FX2）

#### D03 实现记录（FX2）

实现：调用者可在 `request`/`call` 的 options 传 UUID `operationId`，省略时为新调用生成；重试必须保留原操作号。注册项 `sideEffects(op)` 声明副作用；节点在 `qianmoConfigPath('resident', node, 'control-operations.sqlite')` 持久化操作号、规范化参数及身份摘要和结果，执行前预留 `unknown` 防崩溃重做，同号异参拒绝。保留 24 小时、最多 1024 条、结果总量 16 MiB、数据库上限 32 MiB，满额拒绝新操作，过期后可回收。数据库 0600，目录 0700，查询不入账；两参数注册仍可编译，默认不声明副作用且急停拒绝。协议版本不变；握手 `supportedTypes` 附加 `control.operation-id` 能力标记，只有声明此能力的对端收到可选 `operationId` 字段，旧 S0 严格载荷校验器继续收到旧结构。旧节点不提供业务幂等保证；新节点的副作用操作缺操作号时拒绝。（FX2）

迁移：现有 `ok` 分支保持不变，失败分支须区分 `unknown`（可能已执行，核对或用原操作号取结果）与 `not-sent`（明确未发送，可重试），不能把失联/超时的未知结果视为未执行或用新操作号盲重试。副作用注册者需补第三参数；未声明的操作沿用普通查询派发，不提供幂等保证。操作号保留窗口之后的重复调用视为新操作。

## §2 P19 接力插件化

### 2.1 目标与完成标准

至少两种工具（Claude Code、Codex）装上阡陌插件后，本机与控制台配对一次，就能在工具里发起转交、查看进度、接回结果；omp 也能装同一个插件（它读 Claude Code 插件格式），但 omp 会话不作为转交来源。

不再为单个工具维护分支：节点续跑改用官方 Codex 的 app-server（`codex app-server`，状态目录用 `CODEX_HOME` 隔离），qmcode 保留为可选项，不再更新。

### 2.2 配对：认证一次

| 步骤 | 做法 |
|---|---|
| ① 控制台出配对码 | 「接力」页「添加设备」：成员及以上（或旧式管理令牌）点一下，得到一个 12 位配对码（形如 `K7QM-2XPA-9FDE`），10 分钟有效、只能用一次；中枢只存哈希，记下签发人 |
| ② 本机换设备令牌 | `qm handoff login <控制台地址> --code <配对码> [--name <设备名>]`。中枢核对配对码后建设备记录，回 `{deviceId, name, token}`；令牌 `qmd_` 开头，32 字节随机，只显示这一次，中枢只存 SHA-256 |
| ③ 本机落盘 | `~/.qianmo/qianmo/handoff/device.json`（控制台地址、设备号、设备名）与 `device.token`（0600、属当前用户、不是软链，读取时照 `readTokenFile` 的规矩检查） |
| 之后 | 所有 `/v0/handoff/*` 请求与 git 传输都用这枚设备令牌；不再要求每个仓库 `qm handoff init`，也不要 SSH 钥匙 |

设备令牌的权限：只能访问接力接口与本设备的 git 引用；以签发人的身份行事，签发人的账号被吊销或降为只读时，设备令牌随即失效。控制台「连接」页的「本机工具」一半列出设备（名称、签发人、最近一次使用、平台），可以逐台吊销。配对接口按来源地址限流（每分钟 10 次），配对码错 5 次作废。

**v1.1（D05、D06）**：设备令牌是独立的凭据类型，不能换取控制台会话，也不继承签发人的全部接口；服务端按方法和路径列出设备可用的接口，配对签发与设备管理不在其中。每次请求与业务执行前复核设备状态、签发账号状态和凭据代次；任务归属和设备号由认证结果生成。配对用公开的 `pairingId` 加一次性秘密码，原子消费。本机令牌文件以不跟随软链的方式打开，核对属主与父目录。

### 2.3 代码经 GitHub（v1.2）

中枢不再托管裸仓。项目的仓库就是用户在 GitHub 上的仓库（本机检出的 `origin`）：

| 步骤 | 做法 |
|---|---|
| 转交 | 本机把工作区快照与会话记录推到该仓库的 `qianmo/wip/<设备号>/<任务号>` 与 `qianmo/sessions/<设备号>/<任务号>` 两个分支，再向控制台登记任务（仓库、分支、提交号）。用的是用户本机已有的 git 凭据 |
| 续跑 | 中枢派发任务时，把运维登记的 GitHub 连接（§8.3）的令牌经签名控制链路随任务交给节点；节点只放在子进程环境里（`GIT_CONFIG_COUNT/KEY/VALUE` 传 `http.extraHeader`），不进命令行、不落盘。节点按提交号浅取，续跑完把结果推到 `qianmo/result/<任务号>` |
| 接回 | 本机按台账里的结果提交号从 GitHub 拉回 |
| 清理 | 任务接回或作废后，节点或本机删除这三个分支；台账保留提交号 |

- **会话记录只进私有仓库**：本机推送前查仓库可见性，公开仓库只推代码快照、不推会话记录，并在工具里说明。
- **中枢存什么**：只有任务台账（谁、哪个仓库、哪几个分支和提交号、状态），不存代码。
- **令牌范围**：建议用细粒度令牌，只授权这一个仓库的 contents 读写；连接页测试时核对可见性与权限。
- 旧的 `--handoff-root`（中枢 HTTPS git 与裸仓）和 `--hub user@host:root` + SSH 方式保留给已有部署，新部署默认不开。

### 2.4 任务归属

台账每个任务记 `ownerDevice` 与 `ownerSubject`。设备令牌只看得到、只能 send / attach / return 自己账号的任务；控制台页面上的人按原有角色看全部。`GET /v0/handoff` 的过滤从客户端挪到中枢。

### 2.5 来源工具

| 工具 | 会话位置 | 回合结束同步 | 状态 |
|---|---|---|---|
| Claude Code | `~/.claude/projects/…/<会话>.jsonl`（由 hook 输入给出） | 插件的 `hooks/hooks.json`：`Stop`（async）与 `SessionEnd` | 已有，改由插件安装 |
| Codex（官方） | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*-<线程>.jsonl`，未设时 `~/.codex` | 插件 hooks（Codex `hooks` 特性，稳定版默认开） | 新增；格式与 qmcode 相同，按 `codex` 记 |
| qmcode | `$QMCODE_HOME` | 内置 notify | 保留，不再更新 |
| omp | — | — | 能装插件、能调用转交工具查看与接回；omp 自身会话暂不作为转交来源 |

`qm handoff sync --hook auto` 按 hook 输入里的 `transcript_path` 判断是哪种工具，插件只写这一条命令。

### 2.6 插件包

放在 `atlas/plugins/qianmo/`，仓库根放 `.claude-plugin/marketplace.json`（Claude Code 与 Codex 都读这个格式）。`qm handoff plugin install --tool claude-code|codex|omp` 把同一份插件写进 `~/.qianmo/qianmo/plugin/`，再调用各工具自己的命令登记本地 marketplace 并安装；不改各工具的其他配置。

| 文件 | 内容 |
|---|---|
| `.claude-plugin/plugin.json`、`.codex-plugin/plugin.json`、`plugin.json` | 名称 `qianmo`、版本跟随阡陌发行号、说明、`mcpServers: ./.mcp.json` |
| `.mcp.json` | `qianmo → qm handoff mcp` |
| `hooks/hooks.json` | `Stop`、`SessionEnd` → `qm handoff sync --hook auto` |
| `commands/handoff.md`、`pull.md`、`status.md`、`login.md` | `/qianmo:handoff` 等；正文只指示模型调用对应 MCP 工具或运行 `qm handoff login` |
| `skills/qianmo-handoff/SKILL.md` | 用户说「交给云端」「我要关机了」时调用 `qianmo_handoff`，并把目标、已完成、剩下的写清楚 |

MCP 工具沿用 P17 的五个（`qianmo_status`、`qianmo_handoff`、`qianmo_task`、`qianmo_send`、`qianmo_pull`），另加 `qianmo_login_status`（只读：是否已配对、控制台地址、设备名）。

### 2.7 节点续跑换成官方 Codex

`qm handoff node` 增 `--app-server-bin`（默认 `codex`）与 `--app-server-home-env`（默认 `CODEX_HOME`）；节点的 app-server 用 `-c mcp_servers={} -c notify=[]` 起，避免反向调用。`qm handoff attach` 调本机 `codex resume --remote …`（`--client-bin` 可改回 `qmcode`）。官方 Codex 0.162 的 `resume --remote`、`--remote-auth-token-env`、app-server 都已核实存在；Claude Code 会话导入沿用 `externalAgentConfig/import`。

**v1.1（D09）**：实时 attach 仍要读节点 app-server 令牌并建隧道，本轮继续需要独立的 SSH 条件。「配对一次即可互通」的承诺限定在转交、查看、追加与接回。

## §3 P20 节点间文件互通

### 3.1 流程（v1.2：经 GitHub 交换仓库）

文件不经中枢中转。运维在「连接」页登记一个**私有**的 GitHub 交换仓库（§8.3），节点之间经它交换：

| 步 | 谁 | 做什么 | 审计 |
|---|---|---|---|
| ① 申请 | 节点 A 的主智能体调 `qianmo_file_request {from: "qianmo://B/<agent>", path, reason}`；或控制台用户在「文件互通」页直接发起 | 经上行调用 `files.request` 到中枢，中枢记一条待批申请 | `files.requested` |
| ② 授权 | B 的所有者（B 所在租户的成员及以上；未开账号时为管理令牌） | 在「文件互通」页批准或拒绝；批准时写明范围（一个文件或一个目录前缀）与有效期（默认 1 小时，最长 24 小时） | `files.granted` / `files.denied` |
| ③ 发布 | 中枢 → B | `files.publish`：B 生成不可变快照、扫描秘密、写 `MANIFEST.json`（每个文件的相对路径、大小、SHA-256），提交到交换仓库的 `qianmo/files/<传输号>` 分支并推送，回报提交号 | B：`files.published` |
| ④ 取回 | 中枢 → A | `files.fetch {commit}`：A 按提交号浅取，逐文件核对清单摘要，一致才以不覆盖方式原子移进工作区 `inbox/<B 节点>/…` | A：`files.delivered` / `files.rejected` |
| ⑤ 清理 | 中枢 → B | 送达后删除该分支（保留期可配，默认立即删）；台账保留提交号与清单摘要 | `files.cleaned` |

由用户在页面上直接发起的传输，发起人同时是 A、B 的所有者时，②省掉，记一条 `files.granted`（`by: 发起人`）。中枢只转控制命令和提交号，不经手文件字节。

### 3.2 汇集

「汇集」是一组传输：选一个目标节点和若干来源（节点 + 路径），每个来源各推一个分支、各走一遍 ③–⑤，落在目标节点 `inbox/<来源节点>/…` 下。页面上整组显示进度，任何一项失败不影响其余各项，失败项可单独重试。

### 3.3 界限

| 项 | 规矩 |
|---|---|
| 能读什么 | 只读 B 的智能体工作区内（`--agent <名>=<目录>` 给的目录），不跟随指向工作区外的软链；`.git`、`.qianmo`、`.omp`、`.ssh` 与 `inbox/` 不出；命中接力秘密扫描规则（`@qianmo/handoff` 的 `secrets.ts`）的文件拒绝传出并在审计里写明 |
| 多大 | 单个文件 64 MiB（低于 GitHub 单文件 100 MB 的上限），一次传输 256 MiB、1000 个文件；超出拒绝 |
| 写到哪 | 只写 A 工作区下的 `inbox/`，同名文件不覆盖，另存为 `<名>.<传输号前 8 位>` |
| 授权再用 | 授权在有效期内可以重复取（例如数据更新后再取一次），过期或被撤销后拒绝 |
| 暂存 | 中枢不暂存（v1.2）；节点的快照与取回暂存在 `<节点配置根>/qianmo/files/<传输号>/`，智能体读不到，完成或失败后删除 |
| 仓库 | 交换仓库必须私有，连接页测试时核对；令牌经签名控制链路随命令下发，节点不落盘 |
| 打开方式（v1.1，D10） | 来源先在智能体不可写的位置生成不可变快照，后续只传这份快照；路径用目录句柄约束，拒绝链接、硬链、特殊文件、路径穿越与目标文件系统上的名称冲突（大小写、Unicode 等价）；目标在隔离暂存区写完、核对后以不覆盖方式原子提交 |
| 秘密（v1.1，D11） | 文件导出有单独的秘密策略：秘密文件名规则加阡陌凭据格式，扫描完整快照；二进制与归档不宣称做过内容秘密检测；审计只记规则编号与路径 |
| 授权绑定（v1.1，D12） | 授权绑定来源、目标、规范化范围（目录前缀按路径段比较）与两端工作区代次；有效期内再取是新建一次传输、重走全部检查；每次读取与提交前复核过期、撤销与租户归属；汇集的每个来源各自要有有效授权 |

### 3.4 落点

协议没有新消息类型，全部走 §1 的 `node.control`（`files.publish|fetch|clean|abort`）与 `hub.call`（`files.request`）。节点侧 `atlas/packages/node/src/host/files.ts`；中枢侧 `consoleFiles.ts`（申请、授权、传输三张账本，`files.ndjson`）；宿主工具 `qianmo_file_request` 只给主智能体。


**实现（P26b）**：③ 来源节点在暂存里用 git 底层命令建一个无历史的提交（树固定为 `MANIFEST.json` 加 `files/<相对路径>`），推到 `refs/heads/qianmo/files/<传输号>`；④ 目标节点 `git fetch --depth=1` 后核对 `FETCH_HEAD` 等于台账提交号，不 checkout，先 `ls-tree -r -z` 查遍全树（只收 `100644`/`100755` 普通 blob 和固定布局），再逐个 `cat-file` 核对大小与 SHA-256、清单摘要与台账一致，才原子落进 `inbox/`。与上表不同的一处：⑤ 由中枢直接删分支（一个临时空仓库里 `push --delete`，不取对象），不经 B；失败遗留的孤儿分支从首次发现起算保留期，由清扫器删除。节点只接受 `https://github.com/<owner>/<name>.git` 这一种远端地址（测试用的本机远端要显式开关）。原 P20 的 `files.read|write|commit` 分块搬运与中枢暂存已删除。

## §4 P21 云端电脑（专属电脑与浏览器）

### 4.1 分配与隔离

用户在控制台「云端电脑」页为某个节点的主智能体打开「专属浏览器」或「专属电脑」，经控制链路下发 `desktop.enable`。节点的宿主据此起一套环境：

| 项 | Linux 节点 | macOS 节点 |
|---|---|---|
| 显示 | 独立的 Xvfb（`:<编号>`，1440×900），只监听本机 Unix 套接字 | 不提供专属电脑（会操作真实桌面）；只开专属浏览器 |
| 浏览器 | 节点自己起 Chromium：`--user-data-dir=<节点配置根>/qianmo/desktop/<agent>/browser`、`--remote-debugging-port=<随机>`、只绑 127.0.0.1；在该 Xvfb 上有头运行 | 无头 Chromium，同样的独立资料目录 |
| 给 omp 的配置 | 会话覆盖层写 `browser.enabled: true`、`browser.cdpUrl: http://127.0.0.1:<端口>`；开电脑时 `computer.enabled: true`，子进程环境 `DISPLAY=:<编号>`、删掉 `WAYLAND_DISPLAY` | 只有浏览器那一半 |
| 归属 | 资料目录、下载目录、登录状态都在这个节点、这个智能体名下；别的节点、别的智能体看不到 | 同左 |
| 回收 | `desktop.recycle`：停浏览器与 Xvfb，删资料目录；`desktop.disable` 只停不删 | 同左 |

### 4.2 授权与审计（v1.1 重写，复核 D13–D16）

v1.0 的做法是给主智能体放出 `eval`、给基座两个前导函数补批准提示。复核核实了三件事，这条路不成立：`eval` 的执行环境能直接用文件、进程、模块导入与网络，工作区检查管不到；一次前导调用可以包含多次界面操作，`run`、`call` 的函数参数还能执行代码；常驻宿主只接 `confirm`，前导函数发的是 `select`。

改为（复核方案 D）：

1. **`eval` 继续禁用。** 阡陌扩展注册类型化工具 `qianmo_browser_*`、`qianmo_computer_*`（打开网址、截图、读页面、点击、输入、按键等），每个工具的参数有精确 schema，由宿主代码构造基座参数、调用基座的浏览器与电脑实现。模型不能提交程序代码、函数标记、原始 CDP 地址、程序路径或任意本地文件路径。
2. **确认方式**：「只看自动 · 其余逐次确认」（默认）——截图、读页面这类只观察当前页面和屏幕的操作自动放行，其余每次经结构化宿主确认转成 P14 审批；「每一步都确认」——全部转审批。只读与否由执行器按工具决定，不信调用方自报。确认不放宽文件、网络和资源隔离；批准后执行前复核目标与资源代次，需确认的操作只接受一次性授权。
3. **隔离与回收**：资源句柄由宿主固定，拒绝调用方选择 CDP、程序路径与启动参数。独立资料目录和显示号不算隔离证明；Linux 上的 UID、挂载、进程、网络与显示隔离要经过验收，Chromium 自身沙箱保持开启。回收先关闭全部使用者、确认整个进程树退出，再清资料；任一步失败不报告已回收。
4. **审计**：每次操作写 `desktop.action`（操作类别、目标主机名、是否经过确认、结果），不记输入正文；保存能追溯到具体批准与执行结果的标识。

操作电脑和浏览器的能力来自基座，阡陌的成果是类型化外壳、授权、隔离、回收与审计；不改基座的前导函数。

**实现（P21）**：P21 采用复核后的方案 D。本节取代 §4.1 中关于 eval、显示与隔离强度的旧口径：macOS 只称「独立浏览器资料环境」，不宣称进程或节点间隔离。浏览器与电脑执行能力复用 oh-my-pi，阡陌实现受限工具、身份绑定、审批与资源生命周期。

1. `eval`、原始 browser/computer 工具保持禁用。阡陌扩展只注册 `qianmo_browser_*`（截图、读页面、查元素、列 tab、导航、点击、输入、按键、滚动）和 `qianmo_computer_*`（截图、点击、输入、按键、滚动）。每项精确 schema，并保留原始工具调用校验，避免基座参数修复把未知字段删掉后执行；拒绝代码、函数标记、通用调用链、CDP 地址、程序/启动参数、Cookie/Storage 导出和文件路径参数。可信适配层构造公开 `createBrowserPrelude` / `createComputerPrelude` 的调用。
2. 宿主从真实 RPC 子进程与活动 turn 确定 node、agent、contextId、taskId。资源单位为 `(node, agent, resourceEpoch)`；tab 句柄由宿主签发，旧代次及其他资源的句柄拒绝。宿主持有资源操作租约，审批期间不接受并行操作；绑定观察到的目标摘要，执行前再观察并复核。
3. `sensitive` 默认仅截图、读页面、查元素、列 tab 免审批；导航、点击、输入、按键、滚动逐次确认（滚动事件也可能改变外部状态）。`always` 连观察也逐次确认。审批走现有 `QIANMO_AUTHZ_V1`、P14 与宿主授权账本，拒绝窗口 grant，只认绑定 `node/agent/contextId/taskId/invocationId/resourceId/resourceEpoch/op/canonicalArgsDigest/observedTargetDigest` 的单次批准。参数正文仅存在受保护的审批材料中。
4. 执行前持久化一次性意图、原子消费批准，再检查活动 turn、资源代次、目标摘要与批准时效；提交只能一次。完成、失败、结果未知分别记录，未知不自动重试。每次操作记 `desktop.action`，关联 actionId、taskId、invocationId、resourceEpoch 与 digest；公共审计仅记操作类别、目标主机名、确认与结果，不记输入正文。
5. Chrome 独立资料目录 0700，下载目录独立；保留 Chromium 沙箱，无头启动，`--remote-debugging-port=0` 后读取 `DevToolsActivePort`，CDP 绑定 127.0.0.1。Linux 电脑须有 Xvfb 与 xauth，使用动态显示号、`1440x900x24`、`-nolisten tcp`、独立 Xauthority，不用 `-ac`；控制子进程设置 DISPLAY/XAUTHORITY 并清除 WAYLAND_DISPLAY。Linux 路径只有假启动器测试，本机未实测。
6. 停用/回收先停接动作、递增代次、撤销待批与在途，再终止整个进程树并确认退出；停用保留资料，回收删除资料、下载、截图和锁文件，失败显示失败。重启清查持久化 PID 并验证进程标记，不能确认的孤儿阻止开启。tab 上限 4、下载上限 100 MiB、空闲 15 分钟停用，由宿主每 2 秒看护。每资源 1–2 GiB 内存仅为待验证规划值，尚未实现 cgroup/内存限制或独立 UID/容器。

### 4.3 落点

节点：`atlas/packages/node/src/host/desktop.ts`（分配、进程看护、回收、状态）、`residentOmp.ts` 的覆盖层与环境、扩展里的 `qianmo_browser_*` / `qianmo_computer_*` 工具；中枢：`consoleDesktop.ts`；控制台「云端电脑」页。

## §5 P22 按任务匹配模型

### 5.1 任务方向

| 方向 | 说明 | omp 角色 | 工具 |
|---|---|---|---|
| 编程（默认） | 写代码、改 bug、跑测试 | `default`、`task` | 原有 |
| 对话与简报 | 日常问答、整理、写简报 | 自定义角色 `chat` | 原有 |
| 规划与推理 | 方案、拆解、复杂分析 | `plan`、`slow` | 原有 |
| 快速小任务 | 标题、摘要、压缩 | `smol`、`commit`、`tiny` | — |
| 看图 | 读截图、图表 | `vision` | — |
| 生图 | 按描述生成图片 | `image` | 基座 `generate_image` |
| 语音 | 文字转语音 | `speech` | 基座 `tts` |
| 视频 | 按描述生成短视频 | 自定义角色 `video` | 阡陌宿主工具 `qianmo_generate_video` |

### 5.2 怎么选

- **页面**：模型服务页增「任务分工」卡片，每个方向选一个模型服务和其中一个模型；不选的方向跟随主模型，生图、语音、视频不选就不开对应工具。可以按节点覆盖。
- **自动匹配**：任务进来时，中枢派发的请求可以带 `direction`（定时任务、对话页都能指定）；显式方向优先且只作用于本轮，其次是会话人工选择（`/model`、`/thinking`/`/effort` 或显式 RPC 切换，`/model auto` 清除），再其次才是开启 `qianmoRouting.auto` 时按任务文字做一次确定性的归类（关键词表在 `atlas/packages/providers/src/directions.ts`，例如「画、海报、插图」→生图，「视频、短片」→视频，「计划、方案、分析」→规划，代码与报错特征→编程，其余→对话），用该方向的模型开这一轮。归类结果写进审计 `model.route`，页面上能看到每个节点最近 20 次的归类。
- **下发**：沿用第六类动作，`apply` 由一个档案扩为「主档案 + 被引用的档案 + 路由表」；节点编译成多个 `qm-*` provider 与完整的 `modelRoles`，生图、语音模型带上 `kind` 与 `api`。
- **v1.1（D17）**：路由分成对话轮主模型与媒体工具模型。编程、对话、规划、快速任务、看图选适合对话的模型（看图另要求图像输入能力）；生图、语音、视频只给对应工具用，不作聊天主模型，没配时工具关闭、不回退主模型。优先级从高到低：本轮显式方向、会话里的人工选择（`/model`、`/thinking`）、自动归类；都没有时不切换。节点在一轮开始前串行切换并读回实际生效的模型，审计记路由原因、配置修订与实际模型。中枢不代调用模型（N-5）。

### D17 媒体模型与对话模型分离

媒体方向（image/speech/video）只指定工具模型，不切换接收主提示的对话模型。无显式方向、无人工选择且未开启自动路由时保持会话当前模型；查询类本地命令不触发路由切换。

实现：会话人工选择持久化、本轮显式方向结束后恢复、路由簿 PID/nonce/时间锁与回收、节点受保护暂存和 MP4 校验/限额提交；vision 路由档案无输入模态数据，未收紧（FX3）。

视频保存上限在节点配置 `qianmoVideoLimits` 中指定正整数字节数：`maxFileBytes` 和 `maxCallBytes` 默认各 512 MiB，`maxStagingBytes` 默认 2 GiB。短视频通常远小于单文件上限；暂存总量为四份默认短片留余量且包含崩溃残留。暂存在 `qianmoConfigPath('resident', 'video-staging')`，保存前核对不在节点任何已配置的智能体工作区内；拒绝暂存或下载时取消内容流。并发下载共用节点锁，按实际收到字节计数，超限取消流并清理当前部分文件。Linux 经 `O_DIRECTORY|O_NOFOLLOW` 目录句柄和 `/proc/self/fd` 提交；macOS 逐级打开并在复制前后核对 inode 和 realpath。Linux 仍有已打开目录被重命名的窗口，macOS 另有父路径在检查与打开/复制之间被替换的窗口；复核和尽力删除降低风险，不能宣称完全消除竞态。

### 5.3 预设与口径

新增生图（OpenAI Images、Gemini 图片、OpenRouter 图片）、语音（OpenAI Speech）、视频（OpenRouter 视频）预设，全部标「未评估」。现有网关（api2）只提供 `gpt-6-luna`，所以本轮能实测的只有对话类方向的路由与切换；生图、语音、视频只做到夹具验证。

## §6 P23 长期记忆

### 6.1 问题

P16 的记忆按「智能体 + 会话」分区，每个对话、每个值守作业各是一个分区。于是在一次对话里记下的偏好，下一次对话就看不到。

### 6.2 做法

| 项 | 定案 |
|---|---|
| 长期分区（v1.1，D18） | 每个「智能体 × 已验证账号」一个长期分区（工作层，账号主体 `u:…` / `legacy:admin`；`taskId` 用独立的 `l-` 命名空间），跨会话共享；不按智能体整体共享，免得 A 的偏好在 B 的会话里被召回。共享给整个节点要用单独的显式范围，并在批准时列出读者。无已验证身份（匿名、无账号映射、其他节点触发）的任务不读写长期分区。每一轮的冻结召回同时取「本会话分区 + 请求者的长期分区」，合并后统一去重、计预算（50 条 / 2 万字），长期分区优先 |
| 类别 | 用标签 `kind:preference`（偏好）、`kind:plan`（计划）、`kind:project`（项目）、`kind:daily`（日常）；不改记录格式 |
| 谁来写 | 智能体的 `qianmo_memory_write` 增可选参数 `kind` 与 `scope: "long"`；仍然每条都要用户批准（P14，单次批准）。用户在控制台写的直接生效，来源 `user:console:<账号>`，信任高于智能体写的 |
| 改与忘 | 沿用「不原地改」：修改 = 新写一条并 `supersedes` 旧的；忘记 = `revoke` 并写原因；事实过期 = `invalidate` |
| 控制台 | 「记忆」页：选节点与智能体，按类别筛、按文字搜；新增、修改、忘记、标为过期；看每条的来源与历史 |
| 通道 | 控制链路 `memory.list|add|edit|forget|invalidate`；节点用 `FileMemoryStore` 以运维写者身份执行 |
| 分区 API（v1.1，D19） | 统一的类型化分区解析与校验，长期分区用不会和会话分区相撞的命名空间；端口保留 `supersedes` 数组与来源信任语义，不压成单值 |

语义检索仍默认关闭，长期记忆走确定性召回；不把「记得住」说成「答得准」，回答质量仍以 P16 的评测为准。

## §7 P24 主动执行

### 7.1 定时任务

在控制台里建、改、停，不用改文件、不用重启进程。调度放在中枢 `qm console` 进程里，经对话面（`consoleChat.ts` 的 `send`）把提示词送进该智能体的一个专属会话，回复正文与对话记录一起保存。原有 `qm watch` 值守作业保留、页面上照旧只读。

| 字段 | 说明 |
|---|---|
| 目标 | `qianmo://<节点>/<智能体>` |
| 时间 | 每天 HH:MM；每周几 HH:MM；每隔 N 分钟或 N 小时（最短 15 分钟）；时区默认 Asia/Shanghai |
| 内容 | 模板：晨间简报、跟进待办、整理邮件（需要 P25 邮件连接）、自定义；模板只是预填的提示词，用户可改 |
| 方向 | 可选 P22 的方向，默认「对话与简报」 |
| 通知 | 结果推送到一个或多个通知渠道；可选「只在智能体主动通知时推送」 |
| 状态 | 启用 / 停用；超时（默认 10 分钟） |

每次运行记一行：计划时间、实际时间、任务号、结果（完成 / 失败 / 超时 / 跳过）、回复前 2000 字；页面上能看历史并跳到对应会话。同一任务上一轮没结束时，这一轮记「跳过」。紧急停止文件对定时任务同样生效。

**v1.1（D20）**：定时任务以创建者的身份运行，与 HTTP 对话共用一个授权派发服务（`chatDispatch.ts`）：每次运行前重新检查账号、角色、租户范围与对话白名单，开会话时登记属主，发送前预留配额；创建者已无权限时这一次记「跳过」。每个计划时间只建立一条持久运行记录；投递结果未知时不自动重发，远端终态或明确确认之前不仅凭本地超时解除占用。计划按创建者隔离：成员只看得到、改得了自己的，运维可以代管。定时任务不是对未来敏感操作的预批准，仍按 P14 走审批。

### 7.2 通知渠道

控制台「主动执行」页管理渠道：通用 Webhook、Bark、企业微信群机器人、飞书群机器人、ntfy。地址里含密钥的只显示主机名。发送失败记进运行记录，不重试超过 3 次。各渠道只按公开文档写了请求格式，没有对真实服务发过，标「未评估」。

**v1.1（D21）**：出站默认只走 `https:`；连接前解析目的地址，落在回环、私网、链路本地、CGNAT、组播、ULA 等受保护地址段（含 IPv4 映射的 IPv6）一律拒绝，内部服务只能由运维逐个放行；不跟随重定向，响应只读前 4 KiB，错误不回显带密钥的地址。

## §8 P25 应用连接

### 8.1 做法

凭据只留在中枢：节点上的智能体调宿主工具，宿主经上行调用把请求交给中枢，中枢用保管的凭据访问外部服务，把结果交回。

| 连接 | 协议 | 宿主工具 |
|---|---|---|
| 邮件 | IMAP（读）+ SMTP（发），TLS | `qianmo_mail_search {query?, folder?, since?, limit?}`、`qianmo_mail_read {id}`、`qianmo_mail_send {to, subject, body}` |
| 日历 | CalDAV（读写），或 ICS 订阅地址（只读） | `qianmo_calendar_events {from, to}`、`qianmo_calendar_create {title, start, end, location?, notes?}` |

### 8.2 界限

- 发信、建日程每次都要用户批准：节点先走 P14 审批（批准绑定这次调用的全部参数），批准后才发上行调用；中枢再按连接的授权表核对这个智能体能不能用它。
- 读邮件只取纯文本正文前 64 KiB，附件只列名称和大小；不下载附件。
- 凭据用模型密钥同一套信封加密（`consoleProvidersSecrets.ts` 的做法）存在中枢，页面只显示「已设置」和设置时间。
- 每次调用写审计 `connector.<操作>`（连接名、结果、条数），不记邮件正文与收件人地址的完整值（只记域名）。
- 预设：QQ 邮箱、163 邮箱、Gmail（应用专用密码）、Outlook、自定义；iCloud 与自定义 CalDAV、ICS 订阅。全部标「未评估」，本轮用夹具服务器验证协议实现。
- **v1.1（D21–D23）**：
  - 中枢执行点另行核验并原子消费一次性动作记录，记录绑定认证节点、智能体、会话、连接修订、操作与完整参数摘要；布尔 `approved` 字段和连接使用权都不能代替这次批准。节点上这些工具不用窗口授权和旧授权快速命中。外部调用结果未知时不自动重发。
  - 工具必须指明 `connectorId`；邮件句柄绑定账号、文件夹、UIDVALIDITY 与 UID。拒绝邮件头里的 CR/LF；读取前按流量限额，MIME 正文规范处理。
  - ICS 订阅地址里的令牌整体算秘密，进秘密库，不按普通设置落盘。
  - 出站策略与 §7.2 相同：限定协议、端口与目的地，重定向逐跳复核、跨源不带凭据。

### 8.3 GitHub 仓库连接（v1.2）

应用连接新增一类 `repo`：登记一个 GitHub 仓库（`owner/name`）与令牌，授权给哪些节点使用。用途有两个：接力续跑时节点取代码、推结果（§2.3）；节点间文件互通的交换仓库（§3.1）。令牌与邮箱口令一样只在中枢加密保管，页面只显示「已设置」；「测试」核对令牌能否读写该仓库、仓库是否私有。出站只放行 `github.com` 与 `api.github.com`。真实 GitHub 上的验证另记，测试用本机 git 远端代替。
