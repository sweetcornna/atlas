# 阡陌 v3.1.0 GitHub Release

v3.1.0 收录 v3.0.1 之后合入 main 的全部改动（#217–#274）：多底层与默认 DeepSeek Harness、magpie 模型网关与公开版、聊天渠道、后台任务与并行子会话、专属电脑补全、扩展自配置、智能体改设置、Windows 与 Linux 客户端 `qmo`、桌面版。产品代码与 10 月 23 日部署到内测环境的产物相同（main `c47564c5`），标签所在提交只多了这次的文档改动（本文、路线图、README、`qmo-app.md`），可以用 `git diff --stat c47564c5 v3.1.0` 核对。发行形式与 v3.0.1 相同：`sweetcornna/atlas`，源码归档加 `SHA256SUMS`，不附可执行文件和安装包。识别 `qm` 产物以编译进去的源码提交为准（CONTRIBUTING §11）；`qmo` 与桌面壳自报 0.1.0。

下文写的是代码已经实现的能力。只在测试替身、假网络或本机上验证过的部分逐条注明，逐包状态见[路线图](./roadmap.md)。

## 变化

### 底层与模型

- **多底层并存**（#229，P27）：每个智能体选自己的底层与模型，同一节点可以混用。外部底层用官方 CLI 的原生协议接入（`claude -p` 流式 JSON、`codex app-server`），宿主工具经 `qm runtime-mcp` 回环桥提供，状态目录与凭据隔离在阡陌配置根下。
- **底层目录与默认 DeepSeek Harness**（#237，复核修复 #242、#243、#248，P36）：
  - 目录含 dsh（缺省）、qianmopi（内置退路）、Claude Code、Codex、Gemini CLI、Qwen Code、opencode；dsh 与其他 ACP harness 共用一条 ACP 通道。
  - `runtime.versions / install / remove / update / status / configure`，`--default-runtime`（缺省 dsh）、`--runtime-bin`、`--no-runtime-autoinstall`。底层用不了时退回 qianmopi 并写明原因，换底层时对话带着前情继续。
  - 所有底层拿到同一套宿主工具；新增 `qianmo_agents` 与同步问答 `qianmo_ask`，同节点互问不死锁。
  - 插件、MCP、技能按各 harness 原生方式装在智能体自己的状态目录；`qm runtime open <智能体>` 用同一份环境启动官方前端。
  - 顺带修了 Codex 的一处信任泄漏：第一轮可写回合会把工作区标成受信，之后工作区 `.codex/config.toml` 里的 MCP 服务不经询问就运行。会话现在一律钉为不受信。
- **magpie 统一模型调度**（#230、#231、#239，P33）：magpie（开源模型网关，MIT）作为平台网关单独运行，节点带各自的网关密钥直连它，中枢只调它的管理接口发放密钥、写白名单、设额度、读用量，不转发模型流量。一把网关密钥经 `laneAddresses` 同时服务 qianmopi、Claude Code 与 Codex。阡陌签发的密钥只放行 API key 类上游，不用个人订阅登录。#231 修了节点能力未知时下发会悄悄丢掉另两条通道的问题。控制台的「网关」页管理连接、上游、路由组、网关密钥与用量（P34）。
- **公开版**（#230，复核修复 #238，P35）：同一份代码的另一种部署，仅可购买订阅使用。按节点订阅，不卖模型额度，订阅者把自己的模型 key 加到平台 magpie；新包 `@qianmo/billing`（哈希链账本、预付周期订阅、兑换码），微信支付 APIv3 Native 与支付宝当面付按官方接口实现；成员没有有效订阅时写请求一律 402。独立构建 `bun run atlas:build:public`，公开页面页脚给出对应源代码链接（AGPL §13）。
- **任务模型三档与原生模型字段**（#261，P38）：任务按复杂 / 一般 / 简单三档分，生图、语音、视频单独配，每档可设模型与推理强度；没标难度的任务按内容自动分档。模型按各底层的原生字段下发：Claude Code 的 `ANTHROPIC_DEFAULT_<档>_MODEL` 与 `--effort`、Codex 的 `model_reasoning_effort`、dsh 的 `reasoningEffort`、opencode 的 `small_model`、qianmopi 的 `--model` / `--thinking`。路由账本 v1 在读取时迁到 v2。
- **模型服务**：任务分工保存后明示「尚未下发」，下发带修订号，分工在途中被改就整次 409（#221）；中枢后台刷新跳过 5 分钟内刚查过的节点、节点按输入指纹缓存 `effective`，消除了同机两个节点时的内存尖峰（#226）。

### 后台任务与会话

- **前台常驻、后台子任务**（#229、#232、#234，P29）：主会话保持空闲，一两步能完成的当场做，长过程交给同一智能体的子会话，简单但耗时的活交给名册里的其他智能体。`qianmo_task_start` 支持 `after` / `at` 延时和 `everyMinutes` + `times` 重复；`qianmo_task_agents` 列出可派的智能体。子任务做完回到原对话，取消、超时、重启续跑、账本清理都有专门处理。
- **并行子会话**（#261，P38）：节点闸门改为会话内串行、名额内并行，`qm resident --max-turns`（缺省 4）与 `--max-background-turns`（缺省 3），始终给前台留一个名额；中枢每节点的子任务名额由 `qm console --task-workers` 设（缺省 3）。`turn.steer` 把追加指示送进在跑的子会话；子会话完成后，主会话忙时送进它在跑的那一轮，空闲时合成一个回报回合。
- **复用对话与缓存命中**（#229，P30）：一个聊天对应一条会话，外部底层保持热进程，系统提示按会话冻结，工具面保持稳定。
- 下发模型服务后紧接着的第一条消息不再被退回（#221）；`qianmo_task_start` 的可选参数填 0 当没给（#236）。

### 专属电脑与浏览器

- **外部底层可用、工具面补全**（#232，P21+）：Claude Code 与 Codex 经 MCP 使用专属浏览器与电脑；电脑工具补到 16 个（含批量动作、`observe`、`element`、`menu`、`zoom`）。Linux 节点上每个智能体有自己的私有桌面，应用在 bubblewrap 里打开，只开运维白名单里的应用；macOS 节点只操作运维列出的应用。新增确认方式 `autonomous`：观察与日常操作直接执行，高风险操作转一次性批准。
- **调试入口按智能体隔开**（#233）：Chromium 改用 `--remote-debugging-pipe`，不监听端口，宿主为每个浏览器起一座需要认领的桥；同一节点上的智能体互相连不到对方的浏览器，撤掉「一台节点只给一个智能体开终端」的限制。
- **租约**（#224）：接受 Responses 协议模型的工具调用编号（带 `|`），每种拒绝写明原因；同一子进程里并行发出的浏览器调用排队，不再互相顶掉。

### 聊天渠道

- **五个渠道**（#229，P28）：QQ（开放平台官方机器人）、微信（iLink）、Telegram、Discord、Slack 接入控制台「渠道」页，连接都由中枢拨出。
- **对齐 hermes-agent 与个人 QQ**（#245，P28.1）：六个平台的发送重试、长回复、分块上限、发送间隔、长粘贴续段、群聊上下文、防机器人互回、去重、线程参与、配对码按 hermes-agent 的做法重写。新增「个人 QQ」渠道，经用户自备的 SnowLuma（OneBot 11）接入，公开版不提供（章程 v3.8 §7.2 第 8 条例外）。
- **群聊响应**（#261，P28.2）：个人 QQ 的群准入、冷却、发言上限、续问迁自格兰；其他平台的响应逻辑按 hermes-agent 重写为纯函数，NOTICE 五.5 保留 MIT 声明；渠道新增免 @ 群、唤醒词、群冷却、发言上限四类配置。

### 扩展与更新

- **扩展自配置**（#229、#232，P32）：控制台「扩展」页给智能体配 MCP 连接器、技能与插件，秘密封存在中枢，GitHub 来源钉到提交号与目录摘要，按节点下发、每 10 分钟对账；三种底层各用原生方式加载。节点按「条目 × 智能体」记结果，中枢只重发可重试的失败。
- **定时检查更新与在线升级**（#229、#232，P31）：「更新」页按设定时间检查 qianmopi 上游、Claude Code、Codex 与阡陌发行，可选只通知或自动处理；上游同步只出草稿 PR。阡陌自身的在线升级校验摘要、排空在途、原地重启，节点先升、中枢后升；外部底层的新版本先装进临时前缀跑一遍兼容检查，通过才换上。

### 授权与设置

- **智能体改设置**（#264、#267、#268，P40）：`qianmo_settings_list` 读全部设置（密钥只显示是否已设与末四位），`qianmo_settings_change` 一次改一项。设置目录登记控制台全部 99 个写接口，智能体能申请其中 74 项；替人批准、账号与凭据、给智能体加权限、计费等 25 项只能本人操作。云端电脑与渠道两项只许收紧。
- **批准不再要求再次输入凭据**（#270）：登录着的人直接批准、拒绝或「批准并继续」，角色规则不变。被拒时状态行写明原因（#271）。
- **主人自己的一轮即授权**（#272）：主人在自己的对话里提出的请求就是批准，这一轮里智能体的调用（改设置、发信、建日程、写记忆、电脑与高权限请求等）直接执行，不出卡片；决定照常以主人身份签名，账本行带 `basis: chat-turn`。定时任务、后台子任务、不是主人私聊的渠道对话仍出卡片；hardline、急停与只能本人操作的设置照旧拒绝。
- **高权限模式**（#261，P39）：人工确认 / 自动接受编辑 / 自动审批 / 跳过权限确认四档。命令只在 bubblewrap 沙箱里执行，读网址只放行公网地址；收回和急停立即停掉在途工作。中枢要开 `--elevation` 才生效。

### 控制台

- 后台 `/admin`、登录与邀请页改用前台同一套样式（#218）；侧栏分簇，一行超过两个操作时收进 ⋯ 菜单（#262）。
- 「网关」页并入「模型」页，`/admin/magpie` 308 到这一页；新增初始化配置页 `/admin/setup`；对话输入框里加模型菜单与权限模式菜单（#261）。
- **添加服务器**（#220、#225）：把新服务器的一次性 SSH 登录信息交给主智能体或填进「服务器」页，中枢把自己的部署树复制过去并起一个节点。凭据只用于这一次的 SSH 主连接，不进回包、日志与账本；模型档案以发起部署的运维账号下发。
- 定时任务与通知渠道按租户包装，跨租户访问答 404（#219）；操作记录按写操作 / 只读事件分类，缺省只列写操作（#221）。

### 客户端与桌面版

- **`qmo`**（#266，P37.1、P37.2）：Windows 与 Linux 客户端，`qmo sign-in / open / status / sign-out`。登录即设备配对，Windows 用 DPAPI、Linux 用 0600 文件保管设备令牌；每开一次窗口向中枢要一张 60 秒、单次使用的票据，Linux 上票据不出现在任何命令行。中枢新增 `/v0/client/*` 与 `/client/enter`，只有客户端设备能换票据。
- **桌面版**（#274，P37.8、P37.10、P37.11）：Tauri v2 原生壳 `atlas/apps/qmo`，加中枢渲染的对话界面 `/app` 与快速输入 `/app/quick`，与智能体界面 `/` 共用一套视觉。壳经随包的 `qmo session --json` 进门，页面只能调六个命令。`bun run atlas:build:app` 在 macOS 本机构建；没有签名与安装包。

## 升级注意

- **没写 `--agent-runtime` 的节点**：升级后会在后台安装 dsh，装好后改用 dsh（约 850 MB，需要 Node `^22.19.0 || >=24`）。要保持原来的 qianmopi，启动参数加 `--default-runtime qianmopi`；不想自动安装加 `--no-runtime-autoinstall`。
- **聊天渠道的配对档位**：升级前已有的渠道读作 `off`，行为不变；新建渠道缺省 `auto`。
- **审批**：浏览器里批准不再要求再次输入个人凭据；旧页面验过的审批 cookie 在有效期内仍然认，`POST /v0/approvals/auth` 保留。主人自己的对话里，智能体这一轮的调用不再逐次确认（#272），包括它在这一轮里读到的邮件、网页把它引偏的情形；智能体之间的消息开不出这样的一轮，仍然不能替人授权。每次调用照旧有签名的决定和账本行。
- **任务路由账本**：v1 在读取时迁到 v2，下次保存才写回；旧节点仍按 plan / code / fast 收提示。
- **网关页**：`/admin/magpie` 永久重定向到「模型」页。
- **设备**：配对时记下设备类别，没写类别的旧行算接力设备。接力设备（`qm handoff login` 配对的）要客户端票据得 403 `device_kind`，`qmo` 要自己用 `qmo sign-in` 配对。
- **添加服务器**：开了 `--replicate` 的中枢复制时会往 `ops/console.env` 追加 `--chat-url`，之后重跑中枢腿要带上现有尾参。
- **v2.47.x 的旧节点**：它的运行时发出的一个工具缺 `input_schema.type`，走 Anthropic Messages 协议的模型服务会 400；内测环境把 beta-1 钉在 Responses 协议线上绕开。
- **构建与开发**：工具链是 Bun 1.4.3（`.tool-versions`）；1.4.2 在 Linux 上有 `spawnSync` 空转的问题。
