# M2 节点粒度租户隔离与开放注册

本文件承接 `tenancy-m1.md` §9。它规定本轮开发的接口与验收，不代表现场部署或两周影子观察已经完成。注册中心 HA 由独立工作包负责，注册中心 v0、节点证书、capability claims 和消息协议不增加租户字段。

## 1. 归属与信任边界

租户是一组共享节点与数据的个人账号。一个节点只能属于一个租户，agent 从地址的节点段继承归属。账号以服务器验证的 `u:<id>` 为键；请求体、查询参数、信封 `from` 都不能选择请求者的租户。没有归属的账号能登录，但节点、会话、审计、作业和通知均为空，不能执行节点操作。

个人 `ops` 角色只提供其所属租户内的运维权限。平台管理身份必须另外列入本地 `platformSubjects`；平台管理能看全部租户并维护归属，不能由网页注册获得。M2 下旧 token 默认不能读取租户数据；应急访问只在已明确开启 break-glass 时作为平台操作，沿用已有审计。未开启 M2 的部署保持 M1 行为。

租户配置版本 1 包含 `hubServer`、`tenants[{id,label?}]`、`subjects[{subject,tenant}]`、`nodes[{nodeId,tenant,server,memoryRoot}]`、`jobs[{jobId,tenant,nodeId}]` 与 `platformSubjects[]`。未知字段、重复键、缺失引用和非法标识符均拒绝。配置存储必须原子写入、0600，并在读坏时停止租户数据请求；不得回退到无租户模式。启动时没有配置文件与已启用但文件丢失是两个状态。

## 2. 部署硬条件

中枢所在 `hubServer` 不可包含用户节点。同一 `server` 的全部节点属于同一租户；不同租户的记忆根经宿主解析符号链接、规范化后不得相同或互为祖先。配置中的每个作业必须显式声明租户且与目标节点相同。节点数量限制可部署的租户数量；不把一台节点中的多个 agent 当作强隔离。

路径规范化由宿主完成，包内校验仅消费规范化后的绝对路径。中枢的 `FileTenantStore` 检查中枢可访问的本地或镜像根；远端 Windows 路径必须在该节点上规范化并由节点闸门校验，不能将中枢的字符串检查解释为对远端文件系统的验证。新增节点路径需解析最深存在祖先，防止尚未创建的后缀绕过符号链接检查。Windows 路径比较不区分大小写，按路径段判断祖先，不能用裸字符串前缀。

## 3. 控制台请求边界

控制台在认证后创建请求专属 scope，再把宿主端口包装成该 scope 可见的端口。共享 RegistryPort 本身不持有身份。名册、生命周期、会话列表/详情/流、唤醒、审计来源、服务器备注、通知、作业、接力、用量与审批都沿用同一个 scope。跨租户与不存在资源的详情均 404；写请求在账本写入、拨号和任何业务副作用之前拒绝。

无法按节点归属安全拆分的全局管理功能（共享模型档案、全局默认、账号邀请与重置、平台设置）仅平台管理身份可用，不能因租户内角色为 ops 自动授权。模型节点读取与操作未来可以细分，但不得以共享 secret/profile 意外把其它租户带入范围。

所有异步 HTTP 响应在装饰与压缩结束后、返回前重新验证原凭据和初始租户配置修订号；修订变化或账号撤销时丢弃响应并关闭流。审计来源的读取与 trace 查询另在 await 前后复核节点归属，平台身份也不豁免最终复核。SSE 先订阅再复核凭据，阻止认证与订阅之间撤权的竞态。SSE 只转发当前 scope 内事件；归属变化使既有会话流关闭，下一请求重新认证与取 scope。配置版本是 scope 的修订号，不把在旧版本下成功授权视为后续版本永久授权。

## 4. 节点、通知与调度

延时唤醒的权限检查贯穿真实发送：HTTP 注入原凭据的非续期复查，租户包装器绑定请求开始时的配置修订，生命周期包装器复查暂停/退役状态；这些宿主回调不能由请求 JSON 覆盖。等待延时后、双向握手后且发送前再次同步执行全部检查。平台身份同样绑定原配置修订，不能沿用等待前的授权。发送前拒绝释放已预留用量；已经尝试投递但结果未知的情况仍保留预留。真实传输负控覆盖延时撤权、握手中撤权和目标暂停，接收端均未收到唤醒信封；合法对照正常受理。

节点闸门由 resident 实现，紧接认证 router 的 inbound 判定，早于 owed 重发、notify drain、ESTOP 和其它副作用。身份来自已认证对端，不能从信封标签推导租户。中枢被显式列为可信入口；其它对端需与本节点同租户，未知归属拒绝。会话键包含认证发送方，避免不同发送方复用自选 contextId。

启用 `--tenancy` 的控制台若配置聊天或唤醒出口，必须使用具名 `--chat-url node=url` / `--wake-url node=url`，分别开启 `--chat-sign` / `--wake-sign`，并用本地 `--trust node=publicKey` 固定每个目标公钥。命令签名与双向传输握手共用控制台自己的命令密钥；两条链路都要求对端签名，不能回退为只有 PSK，也不从注册中心临时接受公钥。没有配置出口的只读控制台不需要创建命令密钥。未开启 M2 的既有裸 URL 模式保留原有兼容行为。

notify 按中枢连接目标节点归属；作业 tenant 与 target node 的一致性在加载配置时检查，实际派发仍需检查当前版本。节点更换租户要停机清理/迁移租户数据并重启，采用滚动、单节点短停；禁止宣称零停机迁移。

## 5. 用量与配额

复用 M1 `UsagePort`：`UsageScope={subject,kind:'person'|'job',tenant?}`。入口 reserve 原子检查主体、tenant 和 global 三层，任何一层超额不增加其它层计数。reservation 维持至真实任务终态；HTTP 已返回 pending 不代表释放。重复终态幂等释放。账号与租户变更不把正在运行的 reservation 改记给别人。

自然日固定 UTC+8；用量显示 input、output、cacheWrite、cacheRead 四列，charged=input+output+cacheWrite。cacheRead 不计入配额。无法观察后台/压缩等调用时标下界。至少两周 shadow 后才有现场 enforce 依据；开发测试可明确注入 enforce。429 响应包含 used/limit/resetsAt，速率限制与日配额分开。

## 6. 开放注册

默认关闭，宿主 operator 显式配置 enabled、maxAccounts 和每来源限速后开放 `/signup`。GET 不创建账号；POST 仅同源表单，来源只取 socket peer、不信任 X-Forwarded-For，并采用专门注册速率桶（成功也计数）。账号上限在同步创建事务内再次检查，含已吊销账号，避免重复创建/撤销绕过容量。

注册只生成新的随机 subject 和 member 凭据，不接受 subject、role、tenant、inviteId 或已有账号标识。备注不作身份。新账号默认未映射，数据可见性为零。凭据只在创建响应显示一次，落盘只存哈希；刷新 GET 不重发，失败不会返回旧账号凭据。注册无权生成重置邀请、接管账号或授予平台权限。运营者随后通过租户配置分配节点归属。

## 7. 实现分工与验收

Models：tenant store/policy、控制台 scope/HTTP、开放注册、usage/approvals 页面与控制台审批签名运输。Resident：M1 持久计量与节点审批运输、节点 M2 闸门/配置、实际任务终态 reservation、调度派发归属。Root：注册中心 HA、P18.17 P2 界面、总体计划与验收材料。

自动化需包含两租户双向越权负控，以及相同入口的同租户正控；未映射与旧凭据负控；列表/详情/写入/SSE/通知/作业/审计/服务器映射；被拒请求的下游调用数为零；损坏配置重启仍关闭；注册并发容量、限速、同源、角色伪造与已有账号接管负控；租户与主体/global 配额原子性；审计导出不能越过 scope。现场 N1/N2 拨不通的拓扑只计构造测试，不计真机腿。证据写入 `atlas-evidence/m1-work/m1-completion/Models/`，不把本地通过当作现场完成。

## 8. 个人审批接线与恢复边界

`--approvals` 复用固定 `--chat-url node=url` 和本地 `--trust node=publicKey`，通过已签名握手主动订阅节点；注册中心的公钥或端点不参与信任决定。控制台命令密钥与独立 `console-keys/<console>.approver.json` 必须不同。节点由 `--approver` 独立接受审批公钥。

普通会话仅能查看本人待办；提交前须重新验证同账号个人凭据，得到 30 分钟绝对期的独立 HttpOnly、Secure、SameSite=Strict cookie。每次决定由宿主再次检查 live 账号、角色、属主、当前 tenant、凭据时效与 digest。窗口最多 60 分钟，界面默认提供 5 分钟。旧 token 不能审批。

控制台在发送前将决定写入私有哈希链，只有节点成功回执并完成本地记账才显示已批准；超时或拒收显示投递未确认，不自动再签一个决定。账号 reset/revoke 会把该人的已发授权列入持久撤销队列；离线重试。重启会保守撤销所有历史未撤销窗口，包括投递未确认项；需要重新申请，不承诺跨重启保留窗口。节点最终授权账本仍为真源。

「批准并继续」只接受本控制台、本人会话的原任务关联，并要求已收到节点有效 `task.result`、会话没有在途任务；本地超时或重启兜底不构成节点终态。它先原子检查个人/目标租户/全局消息及在途配额，再持久写入一次性继续意图，批准后经已有 ChatPort 发一个新的签名入站任务。端点查询 await 后再次检查权限与终态。并发双击、丢失 HTTP 响应、重启以及未确认发送均不自动重发；在途 reservation 留给实际新任务的终态释放。`--approvals` 的普通聊天链路与独立审批链路都使用命令密钥进行已钉住公钥的签名握手。

`/v0/approvals/report` 是每节点最近 500 条审计记录的有界投影，附来源完整性与截断状态；坏链或见证篡改不计入。viewer 只有请求、使用、拒绝、待批数；member 只看本人会话记录；ops 只看当前请求 scope 内的节点。报告不包含原始工具参数。
