## 0. 本文档的定位

本文回答四个问题：**基座是什么、为什么换、它给了阡陌什么又缺什么、代价与风险是什么。**

它**取代**旧文档 `docs/dev/base-analysis.md` 在文档集中的位置，但**定位不同**：旧文档是"一棵不能碰的树的研究笔记"，服务于隔离；本文是"一块地基的采用决策与能力盘点"，服务于施工。旧文档研究的是**另一棵树**（来源不明、无有效许可的第三方反编译树），与本次基座**没有关系**，已随路线变更废止，保留在历史提交 `67f6081` 中。

**证据纪律**：本文所有关于基座能力的陈述都注明出处文件。没有出处的判断标为"推断"。**没有实测的性能数字一律不写**——本文出现的每一个数字要么来自基座自己的文档，要么来自可复现的命令（如 `git log`），且都标了来源。第 7 节列出本报告的局限，请连它一起读。

## 2. 为什么改路线

### 2.1 旧路线（洁净室）在做什么

旧路线的全部工程约束都源自一个事实：**旧基座没有有效的开源许可授权。**没有 LICENSE 即默认"保留全部权利"，且其来源是对他人已发布产品的反向还原。由此派生出一整套隔离机制——`vendor/` 不入库、`scripts/fetch-base.sh` 按 pin 拉取、pre-commit 拦截、CI `vendor-guard`、CI `no-vendor` 作业、`docs/` 零代码片段、M1 前基座必须彻底退场。自研代码则从零写起，落在 `@qianmo/*` 三个包里。

这套机制**本身没有做错**。在那个前提下它是唯一正确的选择。变的是前提。

### 2.2 新前提

| 维度 | 旧基座 | 新基座（occ） |
|---|---|---|
| 许可 | 未识别到有效授权 | **MIT**（可用、可改、可再分发，条件是保留版权与许可声明） |
| 归属 | 第三方，来源不明 | **项目负责人自有** |
| 分发状态 | 单个匿名提交的 GitHub 仓库 | **已在 npm 公开发布**，有版本历史与 tag |
| 可运行性 | 旧调研结论为静态解析下不可运行（多处空实现与整目录缺失） | **完整可运行**（`bun install` / `bun run dev` / `bun run precheck`） |
| 升级路径 | 无（上游闭源，本地只有一个压缩提交） | **有**（git 历史完整，可按 tag 合并） |
| 能否入库/分发/进产物 | 三项全禁 | **三项全可** |

三条硬约束（不可再分发、不可作为交付物、必须隔离）同时消失。**隔离机制失去了隔离对象。**

### 2.3 收益（诚实分栏：哪条产品线受益）

|---|---|---|---|
| G-1 | 法律状态从"无有效许可"变为 MIT，可入库、可分发、可开源、可进产物 | 全局 | **决定性** |

| G-4 | 省掉旧路线的全部隔离机制建设：fetch-base 脚本维护、pre-commit vendor hook、CI vendor-guard、CI no-vendor 作业、文档零代码片段的逐节合规核查 | 工程与合规工时 | 中 |

### 2.4 代价：放弃洁净室损失了什么

**这一节是本文最重要的部分。**路线变更不是纯收益，下面每一条都是真实损失，必须让团队在评审时看到。

| # | 损失 | 影响 | 缓解 |
|---|---|---|---|
| **C-1** | **失去了"100% 自研"这个简单叙事。** 旧路线里 `packages/` 全部原创、Apache-2.0、与基座物理隔离，成果归属一句话说清。现在的叙事变成"基于自有 MIT 基座 + 我方改造"，**需要额外举证才能说清哪部分是本项目做的** | 高 —— 直接落在申报与答辩上 | 章程 §5.5 的 git 基线（`git diff 3380c88..HEAD`；**v2.4 勘误**：旧文的 `848ad8c2..HEAD` 在本仓库不可执行，`848ad8c2` 是上游 SHA、本仓库不含上游历史）+ P8.3 的材料分栏 + 答辩预案。这是**举证成本，不是不可解**，但它确实是新增的成本 |
| **C-2** | **失去了 `no-vendor` 这类"一句话自证清白"的机制。** 旧路线可以跑一个 CI 作业、拿一份构建日志，直接证明"运行期与构建期均无基座依赖"。新路线**没有等价物**——基座就是依赖，证据从"机器可验证的断言"退化为"需要解释的许可链" | 中到高 | 证据包（基座 LICENSE + npm 发布记录 + 归属关系 + pin/tag）+ 科技处口径。见 §5 风险 R-2 |
| **C-3** | **逆向工程这件事从"在我方之外"变成"在我方之内"。** 旧路线里那棵树是别人的、我们只读、M1 前拆掉——逆向溯源与我方资产可切割。现在基座在我们仓库里、由我方负责人维护、是长期地基——**溯源成了我方资产的一部分，不可切割** | 中 —— 这是**性质变化**，不是程度变化 | 如实陈述（章程 §5.8 第 3 条）。**没有技术手段能缓解它**，只能靠口径准确与事前咨询。见 §5 风险 R-1 |
| **C-4** | **短期内自有代码归零。** 旧洁净室三包（`@qianmo/protocol` / `registry` / `runtime-adapter`）连同其测试已从工作区撤下，保留在历史提交 `67f6081`。撤下当日，账面上的"已完成自研工作量"归零 | 中，且**心理影响大于实际** → **已大部分回补** | **已决（负责人 2026-08-11 决议，章程 v2.1 §5.5）**：`@qianmo/protocol` 与 `@qianmo/registry` **原样复活**并接入基座 workspace，测试随 `bun run precheck` 全绿；`@qianmo/runtime-adapter` **仅取设计不取代码**（其抽象的旧绿地运行时已被基座本体取代）。设计资产（信封、寻址、限额）本就与基座无关、仍然有效。**该决议非全员评审结论，S0 的 P0.5 改为复核（维持或推翻），排期仍不得预设复核必然维持。** |
| **C-5** | **失去了"随时可换基座"的选项性。** 旧路线把基座定义为脚手架，M1 必须拆掉，因此任何时候都可以换。现在是绑定关系：常驻化改造直接改基座代码，改得越深越绑得越紧 | 中 | 章程 T-5 的对策——改造优先走扩展点、M0 冻结 pin、S7 做同步演练测冲突成本 |
| **C-6** | **认知负担与故障面显著上升。** 从"读一棵不能碰的树"变成"维护一个生产级 CLI"。基座的工程约定里有大量非直觉规则（路径必须经 `paths.ts` 派生、若干看似品牌的字符串实为承载协议、feature flag 只能用在条件位置、mock 是进程全局的），踩中任何一条都会产生难以诊断的故障 | **中 / 高概率** | 章程 T-6：P0.2 强制全员通读基座 `CLAUDE.md`、阡陌自己的 `CLAUDE.md` 复述硬规则、沿用基座门禁把标准交给 CI |
| **C-7** | **依赖面与许可核查面变大。** 旧路线 `packages/` 是零第三方依赖的纯 TypeScript；现在整个基座的依赖树都进了我方 SBOM | 低到中 | P8.4 的 SBOM 与许可证清单，范围已按新事实扩大 |

### 2.5 净判断

**收益集中在产品线 ① 与工程质量；产品线 ② 一分未得；法律面是换了一种问题，不是消灭了问题。**

- 产品线 ①（云端常驻编程智能体）：起点从零抬高到"一个功能完整的单机编程智能体"，剩下的是**常驻化**（休眠唤醒、节点形态、沙箱）。
- 产品线 ②（智能体通信协作网络）：**基座给的是零**，理由见 §3.2——跨机传输层在基座上游已被整体删除。路线图 v2.0 因此把传输通道（P2.2）推上关键路径长杆。
- 法律面：从"没有许可，必须隔离"变成"许可清晰，但溯源需要如实陈述并事前咨询"。**后者更好处理，但不是自动消失。**

即便计入 §2.4 的七项代价，路线变更仍然成立——因为 C-1/C-2/C-3 是**举证与陈述成本**，而旧路线的约束是**能力上限**（不能分发、不能进产物、M1 前必须拆掉重写）。用可解释的成本换掉不可逾越的上限，这笔交易划算。**但它不是免费的，评审时请按这个口径理解。**

## 3. 基座给了什么、缺了什么

判定三态：**已有**（可直接使用，我方工作是核验与配置）/ **部分**（有骨架或相邻能力，需改造补齐）/ **无**（基座不提供，从零自研）。

### 3.1 产品线 ①：云端常驻编程智能体

| 阡陌能力 | 判定 | 基座提供了什么（附出处） | 缺口 |
|---|---|---|---|
| **会话持久化与恢复** | **已有** | append-only JSONL 会话记录，路径 `<配置根>/projects/<project-key>/<sessionId>.jsonl`；子 agent 以 sidechain 形式落在 `subagents/agent-<agentId>.jsonl`；重建不是线性重放，而是按 `parentUuid` 回溯活跃链并投影 compact 边界。恢复入口：`--continue`、`--resume <uuid>`、`--fork-session`、`--resume-session-at`（出处：`docs/zh/internals/session-transcript-persistence.md`） | AC-1 的三条判据需实测；`kill -9` 半写事件一致性需核验；`session_id` 在阡陌节点语义下是否等价需确认 |
| **分层记忆** | **部分** | 纯文件式项目记忆，"没有数据库、没有向量存储"；`MEMORY.md` 索引每次对话全量加载（有行数与体积上限）；记忆文件按封闭的四类分类法组织，带 frontmatter；另有按日归档的日志目录。含召回管线与注入系统提示词的链路（出处：`docs/zh/context/project-memory.mdx`） | **阡陌的三层 schema（工作/项目/基线）与基座的四类分类法不是同一套**；基线层（用量基线、赛事日历）基座完全没有；条目级的来源 ID + 废止标记需补 |
| **上下文压缩** | **已有** | 三级机制：MicroCompact（超大工具输出，无 API 调用）、Session Memory Compact（自动触发，无 API 调用）、传统 API 摘要。含压缩边界标记、保留段、工具对完整性、prompt-too-long 应急降级（出处：`docs/zh/context/compaction.mdx`） | 无（M0 直接用） |

| **编程闭环（接任务→读码→改文件→跑测试→报结果）** | **已有** | 基座的核心能力 | 失败路径的结构化输出可能需补，供原因级诊断消费 |
| **工具权限与审批** | **部分** | 工具权限模式（含自动/默认/接受编辑/计划/不询问/绕过等模式）与审批链路，经 ACP 可对外桥接（出处：`docs/zh/features/acp-zed.md`） | **无容器化沙箱**、无路径白名单、无宿主只读挂载、无 CPU/内存上限。AC-6(a) 仍需自研 |
| **后台/并发智能体** | **已有** | 后台 agent 有独立面板与生命周期，transcript 落盘为 `agent-<id>.jsonl` 并可按需重新水化（出处：`docs/zh/features/background-agent-selector.md`）；确定性工作流脚本编排多子 agent，带 journal 重放恢复、并发上限、无进展看门狗与重试分类（出处：`docs/zh/features/workflow-scripts.md`） | 这些都是**单进程内**的并发，不是常驻节点 |

### 3.2 产品线 ②：智能体通信协作网络

**这一节的结论是本次采用决策中最需要被听见的一条。**

| 阡陌能力 | 判定 | 基座提供了什么（附出处） | 缺口 |
|---|---|---|---|
| **注册与发现** | **部分（仅单机）** | Agent Teams 有团队 roster：`config.json` 记录成员（agentId、name、类型、模型、状态等），团队文件是跨进程事实源（出处：`docs/zh/agent/coordinator-and-swarm.mdx`） | **跨节点注册中心、心跳租约、状态持久化全无** |
| **按名寻址** | **部分（仅单机）** | 信箱按 name 寻址，路径 `<配置根>/teams/<team-name>/inboxes/<agent-name>.json`；支持点对点与广播（同上） | **明确不支持跨会话寻址**——目标名里带 `@` 会被输入校验直接拒绝，文档原话是"一个 session 只有一个 team，没有跨 session 寻址"。阡陌的 `qianmo://<node>/<agent>` 是新建的一层 |
| **消息协议** | **部分** | 有结构化协议消息类型（任务指派、权限请求/响应、计划审批、关闭请求、模式设置等），并明确要求协议消息不得被当作普通上下文吞掉（同上） | **无信封、无 hop/trace/fingerprint 字段、无生命周期状态机、无错误码表**。阡陌协议是新建 |
| **跨节点传输通道** | **无** | — | **基座起点为零。**远程控制传输层已于 2026-07 整体删除（约 45k 行，含 bridge、远程控制服务端、ACP 代理包）；`DIRECT_CONNECT` 与自建服务端一并删除；两个直接相关的实验开关 `LAN_PIPES`、`UDS_INBOX` 连代码一并移除（出处：基座 `CLAUDE.md`、`docs/zh/features/acp-zed.md`）。**现存的对外通道只有 stdio（ACP、MCP）与 SSH**，且 SSH 那条按其自身文档不在默认构建里 |
| **加密消息** | **无** | 单机信箱靠文件系统权限；远程控制的端到端加密由第三方客户端负责，不在基座内（出处：`docs/zh/features/acp-zed.md`、`remote-control-self-hosting.md`） | **全部自研。**与旧调研对旧基座的结论一致：这一项没有可参考的现成实现 |
| **防循环** | **部分（形态不同）** | 团队 roster 扁平，"teammate 内禁止再 spawn teammate，避免团队嵌套"；worker 的工具池里不含发消息与建团队的工具（出处：`docs/zh/agent/coordinator-and-swarm.mdx`） | 这是**结构性禁止嵌套**，不是 hop 计数与回环检测。阡陌的 `maxHops` + 首次回访即切断是新建 |
| **限流 / 配额** | **部分（形态不同）** | 信箱有保留上限（普通消息最多 1000 条、未读协议消息最多 2000 条等），带文件锁与原子重命名；MCP 采样有每会话调用次数上限；对供应商的重试有分类与预算（出处：`docs/zh/agent/coordinator-and-swarm.mdx`、`mcp-2026.md`、`providers.md`） | 这些是**存储配额与客户端重试**，不是"单发送方对单目标的令牌桶"。AC-3 的两层限流是新建 |
| **权限分级 / 消息不能替用户授权** | **部分** | 工具权限模式与审批链路可复用作本地执行侧；协议消息里已有权限请求/响应与计划审批的往返（出处：同上） | 跨节点身份认证、能力清单、"跨节点消息无法提升本地权限等级"的协议级强制是新建 |
| **审计与全链路追踪** | **部分** | 会话 JSONL 本身是 append-only 的完整留痕，含元数据条目（出处：`session-transcript-persistence.md`） | trace_id 贯穿跨节点链路、被丢弃/被限流/被去重消息的留痕、查询 CLI 是新建 |
| **资源协商 / 加密隧道 / 预测性扩容** | **无** | — | 全部自研 |

**小结**：基座在**单机多 agent 协作**上相当完整——有 roster、有按名信箱、有结构化协议消息、有配额与文件锁。这些是很好的**形状参考**（阡陌协议定稿前应当看一遍，见路线图 P1.1 的前置）。但它**在跨主机这一维上是零**，而且不是"没做"，是"做过又删了"。阡陌要的正是跨主机那一维。

### 3.3 一条容易被误读的提醒

基座功能表很长（插件市场、Artifacts、语音、Computer Use、Channels、工作流编排……），容易产生"什么都有了"的印象。**请按 §3.1 与 §3.2 的逐项判定理解，不要按功能表理解。**具体地：

- 功能多**不等于**阡陌需要的功能多。章程 N-9 已明确基座既有的市场/插件类能力不纳入 M0 验收与演示。
- 功能多**会**放大需求漂移风险（章程 P-3）——"顺手接进演示"的诱惑显著高于旧路线。
- 功能多**会**放大认知负担与故障面（章程 T-6）。

## 5. 风险

### R-1 ⚠️ 基座是逆向工程产物这一事实，对参赛与开源发布的影响

**这是本报告必须如实写清、且不做任何粉饰的一条。**

**事实（全部有出处）**：

1. 基座自述其定位为"以逆向复原（reverse-engineered restoration）的代码为基座，由社区维护和优化的衍生版本"，并在致谢中记录它 fork 自另一个 Claude Code 还原工程（出处：基座 `README.zh.md`）。
2. 基座以 MIT 许可发布（出处：基座 `LICENSE`、`package.json`），已在 npm 公开发布（`@sweetcornna/open-claude-code`）。
3. 基座**故意保留**了一批 Anthropic 相关标识，理由是它们承载协议而非品牌：系统提示词中 `You are Claude Code, Anthropic's official CLI for Claude` 前缀、`claude-code/<version>` User-Agent、OTel `service.name: 'claude-code'`、`CLAUDECODE=1` 子进程环境变量（出处：基座 `src/constants/brand.ts` 顶部注释的"明确不改"清单）。
4. 基座 `README.zh.md` 的许可章节**曾**写有"本仓库的还原与原创工作以 MIT License 发布，**仅供学习研究用途**"，同时声明"'Claude'、'Claude Code' 与 'Anthropic' 是 Anthropic 的商标；本项目与 Anthropic 无关联、未获其背书"。**已解决（2026-08-11）**：基座侧同日修正三语 README 许可段——中文版删去"仅供学习研究用途"限定，英文版与日文版补上 MIT 授权表述并统一商标声明；本仓库内的基座 `README.zh.md` / `README.ja.md` 已同款修正。**许可正文与自述自此一致**，商标与"无关联、未获背书"声明**逐字保留不变**。

**由此产生的四个问题，本报告不替团队回答，只如实列出**：

| # | 问题 | 现状 |
|---|---|---|
| Q-1 | MIT 是基座作者对**其自身还原与原创工作**的授权。它能否覆盖上游被还原的表达？ | **本报告不作法律判断。**这是章程风险 L-2 的核心，须经学校科技处/知识产权办公室（路线图 P8.4） |
| Q-2 | 基座 README 自述"仅供学习研究用途"，与竞赛参赛、软著申报、乃至 M3 商业化是什么关系？MIT 正文本身不含用途限制，二者不一致 | **已解决（2026-08-11）。**处理方式正是本行原先建议的那一条：由基座作者（即项目负责人）在**基座侧调整措辞**——三语 README 许可段同日修正，用途限定移除，许可正文与自述一致；本仓库内的基座 `README.zh.md` / `README.ja.md` 已同步（见上方事实第 4 条）。章程风险 L-5 相应标记为已解除。**Q-1 不随之解决**——MIT 能否覆盖上游被还原的表达是另一个问题，仍在 L-2 轨道上开放 |
| Q-3 | 代码里合法保留着 Anthropic 标识（上述第 3 点），会不会在演示或截屏中被理解为"与官方有关联"？ | 章程 §5.2③ 已明确"技术上保留 ≠ 对外宣称"，但这是**口径纪律，不是技术隔离**——演示时屏幕上可能真的出现这些字符串。P8.3 需要专门准备说法 |
| Q-4 | 评审专家若追问"这是不是把别人的产品改个名参赛"，怎么答？ | **必须事前准备，不能现场发挥。**建议口径见 §6 |

**不粉饰的判断**：换基座**降低了**许可维度的风险（从"无授权"到"MIT"），但**没有消除**溯源维度的质疑空间，并且把这个质疑从"第三方的问题"变成了"我方资产的问题"（§2.4 的 C-3）。**任何认为"换成自有 MIT 项目之后法律问题就没了"的理解都是错的**，评审时请纠正这种理解。

**对策**（与章程 §6.2 一致）：如实陈述不回避；备齐许可链证据；申报前主动咨询科技处；材料双签；**若科技处口径要求更强隔离，触发范围评审——这条退路必须预留，不要假定一定过**。

### R-2 成果边界不清

见章程 L-1。技术基线是 `git diff 3380c88..HEAD`（**v2.4 勘误**：`848ad8c2` 是上游仓库 SHA，在本仓库不是有效 git 对象，旧写法跑不通——基线以本仓库的基座导入提交 `3380c88` 为准，详见章程 §5.5「举证命令勘误」）；**破坏该基线的 git 操作（rebase 掉导入提交、squash 跨越它、强推改写其后历史）一律禁止**。

### R-3 关键路径风险从"常驻"转移到"通信"

§3.2 的结论直接改变了排期的风险重心。路线图 v2.0 已重新推导关键路径，把传输通道（P2.2）识别为新的长杆。**风险不是变小了，是换了地方**——如果团队沿用"S1 做完持久化就稳了"的旧直觉，会在 S4 集中爆雷。

### R-4 上游漂移与硬分叉

见章程 T-5。M0 冻结 pin + 改造优先走扩展点 + S7 演练测成本。

### R-5 认知负担与故障面

见章程 T-6。基座工程约定里的非直觉规则（路径必须经 `paths.ts` 派生、若干字符串承载协议不可改、feature flag 只能用在条件位置、mock 是进程全局的 last-write-wins）都记录在基座 `CLAUDE.md` 与 `CONTRIBUTING.md` 里，**且每条背后都有真实事故**。P0.2 的全员通读不是形式主义。

## 7. 本报告的局限（置信度声明）

**请连同本节一起读，不要把上面的表当成已验证的全部事实。**

1. **本报告的能力判定基于基座文档，不是基于源码通读。** §3 的每一条都注了出处文件，但我**没有**逐条到源码里验证。路线图 P0.2 的全员通读就是补这个缺口的，判定可能在那时被修正。
