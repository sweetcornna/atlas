## §0 要补的是哪一句

`packages/audit/src/trail.ts` 的模块注释把「审计日志不可改」拆成三句，只认前两句：

1. **写入方改不了** —— 已成立（`O_APPEND | O_NOFOLLOW` 的 fd，类里没有任何 seek / truncate / delete 方法，`claim 1` 用例逐个方法名反向断言）。
2. **外部改动可检测** —— 已成立（哈希链，改一行 / 删一行 / 换顺序都从那里开始断链）。
3. **外部改动无法阻止** —— **不成立，且被一条专门用例钉着**：`claim 3 — a full rewrite that recomputes the chain is NOT detected`。

第 3 句就是本包的对象。注意它的准确含义不是「阻止」——阻止在无 sudo 的机器上做不到（§2.1），也不是本包承诺的东西。**本包要把第 3 句从「无法阻止且无法发现」改成「无法阻止但一定被发现」。**

### 0.1 攻击模型（先钉死，否则所有方案都在回答不同的问题）

| 项 | 内容 |
| --- | --- |
| 攻击者是谁 | **拿到某个常驻节点本机写权限的人**。可能是被攻陷的智能体越权、也可能是有登录凭据的运维本人 |
| 他有什么 | 该节点配置根的完整读写权（含 `<配置根>/qianmo/audit/trail.ndjson`）、节点进程能碰到的一切凭据（含节点私钥、传输 PSK、发往第二位置的写凭据），以及 `packages/audit` 的源码 |
| 他要什么 | 让审计链上某条**不利于他**的记录消失或变样，且**读链的人看不出来** |
| 他为什么现在能得逞 | 因为链内验证的全部输入都在他手里：他重写整篇、逐条重算 `prev`，`readTrail().intact` 就是 `true` |
| **不在攻击模型内** | 攻击者同时攻陷**见证侧宿主**。那已经不是「一个节点被攻陷」而是「运维平面被攻陷」，见证机制对它无解（§7 第 2 条） |

### 0.2 缺口的下游影响面

控制台（`docs/dev/console.md`，v0.1 / 2026-08-17）把 `intact` 与 `issueCount` 直接摆在审计页的表头（`packages/console/src/view/audit.ts` 的 `intact ? '完整' : '断裂 N'`）。也就是说，**面向内测用户的那个「完整」标签，此刻只代表「没有人不小心改坏它」**——`console.md` §7.3 已经原样写了这句话。本包落地后，这个标签要从两态变三态，接缝见 §6。

## §1 部署现实（三个选项的成本必须对着它算）

| 机器 | 数量 | sudo | 能做什么 |

## §2 三个选项

### 2.1 选项 ① append-only 挂载 / 文件属性

**机制。**在文件系统层面让审计文件只能追加：Linux 上是 `chattr +a`（ext4/xfs 的 append-only 属性，`open(O_APPEND)` 之外的写、`truncate`、`unlink`、`rename` 全部 `EPERM`），更强的形态是 WORM 挂载或对象存储的 object-lock。属性一旦设上，**连 root 自己也要先 `chattr -a` 才能改**（需要 `CAP_LINUX_IMMUTABLE`）。

**部署成本。**

- `chattr +a` 需要 `CAP_LINUX_IMMUTABLE`，普通用户没有 → **9 台无 sudo VPS 上直接不可用**。
- 那台有 sudo 的机器可用，但要在每个节点的审计文件创建**之后**、写入**之前**由 root 设一次属性；节点换配置根、换身份目录、重装，都要重设。这条运维动作**没有自动化入口**——节点自己没有权限设它。
- WORM 挂载 / object-lock 是另一套基础设施（NFS/S3 兼容存储 + 保留策略），M1 内没有。

**失效模式。**

- **9/10 机器上机制不存在**，这是最大的一条。
- 有 sudo 的机器上：拿到 root 的攻击者 `chattr -a` → 改 → `chattr +a`，属性本身不留痕迹。属性挡的是「误操作」和「非 root 攻击者」，不挡 root。
- 属性设在**文件**上，攻击者可以在同目录建新文件、改配置根指向别处，让节点从此往新文件里写——旧文件完好，新链从头开始。检测不到，因为「新节点第一次写」和这个长得一样。
- 属性不跨备份/迁移：`cp` 出去的副本没有属性。

**运维负担。**每台机器一次性 root 动作 + 每次配置根变更后的补设 + 一份「哪些文件应该有 `+a`」的清单，且这份清单没有任何东西替你检查。**这是三个选项里唯一需要持续 root 参与的。**

### 2.2 选项 ② 机外见证服务（常驻）

**机制。**新建一个常驻组件：节点把**每一条**审计记录（或每条记录的哈希）实时推给它，它自己存一份独立副本 / 独立哈希链。校验时比对两份链是否逐条一致。这是「双写 + 对账」，形态上接近 syslog 远端收集或透明日志（Certificate Transparency 式的 Merkle 日志服务）。

**部署成本。**M1 内**成本最高的一个**。要新建的东西：

- 一个新的 workspace 包（收集端 + 存储 + 对账查询）；
- 节点侧的推送客户端，且要处理**推送失败**——网络断了是否阻塞审计写入？阻塞则把审计变成了在线依赖（一条 `fsync` 已经是热路径，`baseline-m0.md` §7 B-3 记着「被拒消息也逐条 fsync，容量按被拒流量算 IOPS」），不阻塞则要本地排队 + 重放 + 去重，而排队缓冲又落在攻击者手里；
- 见证服务自己的存储、备份、鉴权、限流、运维（它现在是新的单点）；
- 一套对账协议与「两份链不一致时以谁为准」的裁定规则。

**失效模式。**

- **它自己变成攻击面**：接收端要接受来自 9 台节点的写入，鉴权做不好就是任何人都能往里灌。
- **本地缓冲窗口**仍在攻击者手里：还没推出去的那一段，删掉它和「网络抖动」长得一样。
- 若采用「推送失败不阻塞」，攻击者只要**制造推送失败**（防火墙掉一条规则）再改文件，就得到一个可辩解的缺口。
- 见证服务被攻陷 = 全网见证同时失效（选项 ③ 也有这条，但 ③ 的见证方是个只增不删的存储，攻击面小得多）。

**运维负担。**一个新的常驻服务：起停、监控、扩容、存储增长、版本升级。**注意它与本项目的一条纪律相冲突**——M1 头两个迭代按 roadmap 明写「预留为内测环境搭建 + 身份隔离收尾，**不排新功能**」（`retro-m0.md` §7 开篇）。新建常驻组件是新功能。

### 2.3 选项 ③ 定期锚定摘要

**机制。**不搬运日志内容，**只搬运一个哈希**。节点定期（周期 `T`）取自己审计链**当前最后一条记录的摘要** `digestOf(head)`，连同 `seq`、`count`、时间戳打包成一条**锚点**，用节点自己的 Ed25519 私钥签名，发送到一个**攻击者删不掉旧记录**的第二位置。

核心性质来自哈希链本身：`digestOf(record[N])` 的输入包含 `record[N].prev`，而 `prev` 是 `record[N-1]` 的摘要，递归下去**覆盖第 1..N 条的全部字节**。所以：

> **一个锚点对上，等于证明整个前缀逐字未变；一个锚点对不上，等于证明前缀里至少有一处被改过——无论攻击者把链内哈希重算得多自洽。**

这正好是 `claim 3` 那条用例缺的那一块：攻击者能让**链内**自洽，但他改不动**已经离开这台机器**的那个数字。

**部署成本。**三个里**最低**：

- 零特权：读自己的文件、算一次 sha-256、签一次名、发一个 HTTP POST（或写一个文件、推一次 git）。**无 sudo 的 VPS 上完全成立。**
- 无新常驻组件：锚定动作可以挂在节点已有的定时器上；见证侧最小形态是一个只增不删的存储端点（§4.1）。
- 密钥零新增：节点 Ed25519 密钥对**已经存在**（`packages/capability/src/keys.ts`，公钥就是注册中心里那个 `AgentRecord.publicKey`），不引入第二套密钥，也不触碰章程 N-3 的 PKI 禁令（界线见 charter §3.3 C-5：禁的是证书体系，不是节点自签）。
- 数据量：一条锚点 **229 字节**（§5 的实测产物，非估算）。9 台 × 每分钟一条 ≈ 1.3 万条/天 ≈ **3 MB/天**。

**失效模式。**（逐条在 §5 的脚本里跑过）

- **锚定周期就是残余风险窗口**：最后一个锚点之后写入的记录没有任何机外证据，攻击者可以随便改（§5 变体 C 如实跑出了这一条）。窗口大小 = `T`，取值与代价见 §4.2。
- **攻击者可以停止锚定**：他在节点上，杀掉锚定动作即可。对策是见证侧的**陈旧检查**——「没有新证据」必须本身是一条告警（§5 变体 E）。
- **攻击者持有节点私钥**，可以为改写后的链补签新锚点。**这不管用**，只要旧锚点删不掉（§5 变体 D1 证明了这一点，也证明了**真正干活的是第二位置的只增不删，不是签名**）。
- **第二位置若允许覆盖或删除，整个方案归零。**这是唯一一条会让它彻底失效的失效模式，所以 §4.1 把它当作硬约束写。

**运维负担。**一条定时任务 + 一个只增不删的存储端点 + 一条陈旧检查告警。**存储会单调增长**，需要一条保留策略（与 P11.3 的备份保留策略同一类问题，可以合并考虑）。

## §3 定案

> **选 ③ 定期锚定摘要。**

**为什么不是 ①。**它在 9/10 的目标机器上**根本不存在**。一个只能在唯一那台 sudo 机器上成立的机制，无法作为「阡陌节点的审计是可信的」这句话的依据；而且它需要持续的 root 参与，节点自己没有权限维护自己的保护。这两条里任何一条单独都足以出局。**它可以作为那台 sudo 机器上的加法**（成本极低、与 ③ 不冲突），但不能作为方案本身。

**为什么不是 ②。**它解决的问题比我们有的问题大一号：它保的是「日志内容在机外有独立副本」，而 P11.4 要的只是「机外有一个攻击者动不了的判据」。为了后者去建前者，代价是一个新常驻组件、一条会把审计写入变成在线依赖的推送路径、以及一个新的单点——而 M1 头两个迭代按 roadmap 明写不排新功能。**它不是错的方案，是贵了一个数量级的方案。**若将来需要「审计内容本身也要异地留存」（例如竞赛答辩要求出示不在被审计机上的原件），它是正确的升级方向，届时 ③ 的锚点正好可以当作它的对账基准。

**为什么是 ③。**它把「要保护的东西」缩到最小——一个 32 字节的哈希——于是搬运它的成本低到无特权即可完成，而哈希链的前缀覆盖性让这 32 字节的证明力覆盖整条链。它与本仓库既有的三样东西严丝合缝：审计链本来就是哈希链（无需改 `@qianmo/audit` 的记录形状）、节点本来就有 Ed25519 密钥对（无需新密钥）、`@qianmo/backup` 本来就解决过「一个只能加不能删的存储面」这个完全相同的问题（§4.1 直接照抄它的做法）。

## §4 锚定方案的四个硬问题

### 4.1 锚点存哪：第二位置的写权限凭什么攻击者拿不到

**先纠正问题本身。**攻击者**拿得到**——节点必须持有第二位置的写凭据才能锚定，而攻击者在节点上。所以命题不是「他拿不到写权限」，而是：

> **他拿到的那份写权限里，没有「改写历史」这个动词。**

这不是新问题。`packages/backup/` 解决的正是同一个：智能体能建快照、够不到删除。它的做法有三层，锚点端点**照抄**：

| 层 | backup 的做法（出处） | 锚点端点的对应 |
| --- | --- | --- |
| 面 | `BACKUP_SURFACE` 只列三条路由，`ALLOWED_METHODS = GET/POST` | 锚点面只有 `POST /v0/anchor` 与 `GET /v0/anchor?node=` 两条 |
| 形状 | `assertBackupSurfaceIsSafe()` 在 import 期扫 `DESTRUCTIVE_WORDS`（11 个词），有破坏性动词就抛 | 同一个断言，同一张词表 |
| 存储 | `FileSnapshotStore` 一律 `wx` 创建，什么都不覆盖 | 锚点一律追加；同一 `(node, seq)` 已存在则**拒绝**而不是覆盖 |

**主位置。**M1 内测环境（P11.1）会有一台**内测宿主**跑注册中心与控制台。锚点端点挂在它上面最省——那台机器已经在跑、已经有运维、已经是节点的对端。

**信任边界必须写死的一条**：见证方与被见证的节点必须处在**不同的失陷域**——不同机器、不同凭据、不同登录路径。

> ⚠️ **九台 VPS 若共用同一把 SSH 私钥，它们就是同一个失陷域，互为见证等于没有见证。**这一条要在 P11.1 的环境设计里落成硬约束，不是建议。

**次位置（零成本的第二重）。**每天最后一个锚点另发一份到一个真正独立的地方，二选一或都做：

- **git remote**（私有仓库，一行一条锚点）。要求：**远端禁 force-push**（分支保护），否则「删不掉旧记录」不成立。
- **负责人邮箱 / IM**。这是三者里唯一**真正的第三失陷域**，也是唯一人眼可读的；代价是频率只能到「天」，且不适合自动比对。

**为什么不做区块链 / RFC 3161 时间戳权威 / 公开透明日志。**它们解决的是「**第三方**能公开验证这条链在某时刻存在」；我们要的是「**本方**能发现链被改过」。前者是后者的超集，代价是外部依赖、费用、以及一条对外的数据出境路径。M1 不需要，也与章程 N-3 的克制取向一致。**答辩场景需要的是可复现的验证过程，不是公链上的一笔交易。**

### 4.2 锚定频率与「窗口内改写检测不到」的残余风险

**窗口 = 锚定周期 `T`。**最后一个锚点之后写入的记录，机外没有任何证据，攻击者可以任意改写而不被本方案发现。§5 的**变体 C** 就是把这一条如实跑出来的。

**建议取值 `T = 60 s`。**理由与代价：

| 取值 | 每天锚点数（9 节点） | 窗口 | 评价 |
| --- | --- | --- | --- |
| 每条记录一个锚点 | = 消息量 | 0 | **不做**。审计写入已是逐条 `fsync`、且被拒流量也算 IOPS（`baseline-m0.md` §7 B-3），再叠一次网络同步等于把审计变成在线依赖——这正是选项 ② 被否的理由之一 |
| **60 s** | ≈ 1.3 万 / 3 MB | **≤ 60 s** | **建议值。**开销可忽略，窗口足够小 |
| 5 min | ≈ 2600 | ≤ 5 min | 也可接受，若见证侧存储紧张 |
| 1 天 | 9 | ≤ 1 天 | 只适合 §4.1 的「次位置」 |

**为什么 60 s 的窗口是可接受的**，而不是「还有窗口所以没解决」：

1. **窗口的方向与审计的用途相反。**这个窗口只让攻击者掩盖**刚刚发生的、还没被锚定的**事；而 P7.2 的审计要回答的是「三天后的那个问题」（`packages/audit/src/index.ts` 模块注释原话）。**攻击者在事发后一分钟内就完成入侵、判断、改写的场景，不是这套审计的主要防护对象。**
2. **窗口是被报出来的，不是静默的。**验证结论里带「seq X..Y 共 N 条尚未被任何锚点覆盖」（§5 变体 C 的第二条断言）。读的人知道自己在信什么，这与本项目「说清机制买到了什么」的一贯做法一致。
3. **想再压小可以加触发式锚定**：除定时外，在写入一条 `outcome !== 'ok'` 的记录后立即补一个锚点。被拒/被丢的记录正是最值得抹掉的那些。**这条列为落地时的可选项，不进 v1**（它把锚定与写入路径耦合起来，需要单独评估热路径影响）。

### 4.3 锚点自身的完整性

三层，且**必须说清哪一层是主力**：

| 层 | 做法 | 挡住什么 | 挡不住什么 |
| --- | --- | --- | --- |
| **主力：第二位置只增不删** | §4.1 的三层面/形状/存储约束 | 攻击者删除或覆盖**已发布**的锚点 | 见证侧宿主被攻陷 |
| 辅助：Ed25519 签名 | 节点私钥签 `[v, node, seq, head, count, at]` 的定序 JSON（字段顺序定死一处，理由同 `record.ts` 的 `canonicalize`）；见证侧用带外拿到的公钥验 | **见证侧被攻陷后伪造某节点的锚点**；传输途中被改 | **节点被攻陷后补签新锚点**——他有私钥 |
| 辅助：陈旧检查 | 见证侧发现某节点超过 `2T` 没有新锚点 → 告警 | 攻击者停掉锚定 | — |

**这里最容易搞反的一点**，§5 的变体 D1 专门跑了一遍：**签名不是主力。**攻击者拿到节点私钥后可以为重写后的链签一个货真价实的新锚点——但只要旧锚点删不掉，旧锚点照样对不上，判定照样成立。**签名保的是「这条锚点确实是那个节点发的」，只增不删保的是「历史证据还在」，后者才是本方案的承重墙。**

**明确不做「锚点的锚点」**（把见证侧的锚点文件也串成哈希链再往上锚）：那是把同一个问题往上推一层，没有终点。替代做法是 §4.1 的「次位置」——**同一个锚点发到两个独立的地方，两处不一致本身就是告警**，这比无限套娃便宜也可信。

---

### 4.4 验证动作由谁在什么时机跑

**原则：验证必须发生在「有人读这条链」的时刻，而不是只在定时任务里。**一条审计链的价值在被查阅时兑现，那也正是必须知道它可不可信的时刻。定时任务只能补上「没人查的日子」。

| 谁 | 什么时机 | 需要什么输入 | 输出到哪 |
| --- | --- | --- | --- |
| **见证侧**（陈旧检查） | 定时，周期 > `2T` | 只要自己存的锚点，**不需要节点的链文件** | 运维告警 |
| **`occ audit --verify`** | 运维手动查链时 | 本机链文件 + 锚点（`--witness <路径\|URL>`） | 现有的 `--verify` 输出加一段；`process.exitCode` 的既有语义扩展为「链内断裂**或**锚点不符 → 1」 |
| **控制台审计页** | 每次渲染 | 同上，由 host 侧端口注入 | 表头的第三态（§6） |
| **答辩 / 验收** | 需要出示时 | 同上 | 一条可复跑命令 + 输出留档，与 M0 各次真机验收同一口径 |

控制台那一条的开销值得单独说一句：审计页本来就把整条链读进内存（`console.md` §7.4 已登记这条边界），锚点验证多出来的只有 **N 个锚点的摘要比对**，N 是锚点数不是记录数，且比对的是**已经算好的** `digestOf`。**这不构成新的性能问题。**

| （灰态）**未见证** | 没有配锚点，或锚点陈旧 | 未部署 / 锚定被停 |

## §7 补完之后仍然做不到什么

沿用 P7.2 的行文纪律：说清机制买到了什么，不说它听起来像什么。

1. **仍然不是「阻止」。**攻击者照样能改文件；改变的是「他改完之后一定被发现」。三句承诺的第 3 句应改写为「**外部改动无法阻止，但一定被检测到（锚定窗口内除外）**」，而不是划掉。
2. **见证侧宿主被攻陷则整体失效。**这在攻击模型之外（§0.1）。缓解是 §4.1 的次位置（git remote / 负责人邮箱），它把「同时攻陷两处」的门槛抬高，但不消除这条。
3. **锚定窗口内的改写检测不到**（§4.2、§5 变体 C）。窗口上界 = 锚定周期。
4. **不提供不可否认性的对外证明。**锚点只对本方可信，因为签名密钥与见证存储都在本方手里。要「第三方可公开验证」得上时间戳权威或公开透明日志——§4.1 已说明为什么 M1 不做。
5. **不解决「节点根本不写审计」。**攻击者可以让节点少写一条而不是改一条。那是另一个问题（覆盖率而非完整性），归 P7.2 的接线现状那一栏，不在本包。
6. **不改 `@qianmo/audit` 的记录形状。**锚点是链**之外**的东西，链本身一个字节不动——这也是它能在不触碰热路径的前提下落地的原因。
