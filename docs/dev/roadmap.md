## 0. 排期基础假设

在读任何日期之前，先认下面这几条，否则排期看起来会过于乐观。**本节 v2.0 未作任何改动**——基座换了不改变团队产能。

1. **有效产能按 60% 估**。5 名在校生，课程、实验、竞赛都在同一时间轴上。任务包工时按"这周只有 3 个有效工作日"来估。
2. **低产能窗口显式减载**，不假装它不存在：

   | 窗口 | 迭代 | 原因 | 处理 |
   |---|---|---|---|
   | 2026-09-10 ~ 09-13 | S1 尾 | CUMCM 数模国赛（团队自己参赛） | 李怡康本期不排开发任务，改为**赛中采集真实场景素材** |
   | 2026-10-01 ~ 10-07 | S3 | 国庆假期 | S3 按 50% 产能排 |
   | 2026-12-21 ~ 2027-01-03 | S9 | 期末考试周 | S9 按 50% 产能排，只做收尾，不排新功能 |

3. **关键路径任务不排进低产能窗口**。关键路径见下方"§0.1 关键路径（v2.0 重新推导）"。这条链上任一环节延期，M0 整体延期。
4. **欠账阈值**：任一迭代欠账 > 30% 时，下一迭代不加载新任务包；连续两期欠账 > 30% 触发范围裁剪评审（削减章程 §3 范围，而非削减验收标准）。
5. **迭代节奏**：双周迭代，周一开始、周日结束。每周一次 30 min 同步会（只对齐阻塞项），每迭代末复盘 + 下期任务包确认。
6. **任务包状态**：`未开始 / 进行中 / 阻塞 / 已完成`，在每期复盘时更新本文。

### 0.1 关键路径（v2.0 重新推导）

**旧链（v1.1）**：`P0.1 → P1.1 → P3.1 → P4.1 → P6.1`（工程地基 → 会话持久化 → 休眠唤醒 → 跨节点投递 → 场景端到端）

**新链（v2.0）**：

```
P0.1 基座导入与环境跑通
  → P0.2 基座通读与能力盘点
    → P1.1 消息协议草案 v0.1
      → P2.2 节点间传输通道      ← 新的长杆
        → P3.1 休眠与唤醒
          → P4.1 跨节点任务消息端到端
            → P6.1 数模场景端到端串联
```

**两处变化，各有明确理由：**

1. **会话持久化（旧 P1.1）下了关键路径。** 基座已有 append-only JSONL 会话记录与 `--continue` / `--resume` / `--fork-session` 恢复入口（出处：基座 `docs/zh/internals/session-transcript-persistence.md`），我方工作从"实现持久化层"降级为"核验判据 + 补齐 `kill -9` 半写一致性"，不再构成后续任务的阻塞前置。
2. **传输通道（P2.2）上了关键路径，且是新的最长杆。** 基座上游已于 2026-07 删除全部远程传输层实现（约 45k 行，出处：基座 `CLAUDE.md`、`docs/zh/features/acp-zed.md`），此外两个与之直接相关的实验开关 `LAN_PIPES`、`UDS_INBOX` 也已连代码一并移除。**基座在跨机通信这一端给我们的是零。**而 P3.1、P4.1 都压在它后面。

> **这条推导是本次路线变更中最需要团队记住的一句话：基座把产品线 ① 的起点抬高了，对产品线 ② 一点没抬。**排期的风险重心因此从"能不能做出常驻智能体"转移到"能不能按时打通跨节点通信"。S4（P4.1）仍是 M0 单点风险最高的一期，且现在它的前置更长了。

### 任务包字段说明

每个任务包含：**编号 / 名称 / 负责方向（owner，backup）/ 依赖 / 交付物 / 完成判据（DoD）**。
标 ⭐ 者为关键路径，标 ⚖️ 者为法律合规关键项，标 🔍 者为**核验型任务**（基座已提供实现，我方工作是验证与补齐，v2.0 新增标记）。

## M1：校内内测（2027H1，粗粒度）

**目标**：把 M0 的原型变成 20 ~ 50 名软院同学能真实用起来的内测系统。

> **v2.0 变更**：M1 的头号硬门槛"基座退场"**已取消**（基座是长期地基，不退场，章程 §5.7）。取而代之的是身份隔离验收与上游同步节奏确定——工作量小得多，且不再是"未完成不得进入 M2"的阻断项。这是本次路线变更在 M1 上释放出的最大一块工时。

| 方向 | 内容 | 出口判据 |
|---|---|---|
| **基座关系收敛** ⚖️ | 身份隔离改名完成并验证（阡陌节点 / occ / 官方 Claude Code 三者共存）；按 P7.4 演练数据确定上游跟随节奏并写入章程；决定是否向上游回贡（**提请评审**） | 三者共存实测通过；同步节奏有书面结论 |
| **注册发现产品化** | 最小 Web 控制台（智能体列表、状态、消息链查看）、账号体系、智能体生命周期管理 | 内测用户无需接触 CLI 即可完成注册与查看 |
| **权限模型上线** | 用户授权流（授权申请 → 用户确认 → 时效凭据 → 主动撤销）；权限审计报表 | 所有需确认动作 100% 经过用户授权链路，抽查无绕过 |
| **记忆能力上线** | 语义检索（在确定性检索之上叠加，非替换）、记忆治理（冲突消解、过期废止、跨项目隔离） | 检索命中率与幻觉引用率有量化指标并优于 M0 基线 |
| **生产级加密** | mTLS 替换预共享密钥；证书签发与轮换；密钥管理 | 解除章程 N-3；渗透自查无高危项 |
| **多租户与配额雏形** | 内测必需的租户隔离与用量配额（仍不做计费，N-1 保留） | 跨租户数据访问用例全部被拒 |
| **第二产品线验证** | 运维值守场景原型（常驻智能体的第二类应用） | 至少 1 个真实值守场景连续运行 7 天 |
| **稳定性目标** | 可用性 ≥ 99%（按内测时段计）、唤醒 P95 < 30 s（M0 为 60 s） | 以 P7.3 基线报告为对比基准 |
| **知识产权** | 软著申请提交；开源方案确定并执行（**前置**：M0 P8.4 的科技处口径） | 材料齐备且经学校科技处确认 |
| **边界用例库** | 从 12 条扩到 ≥ 40 条，覆盖内测暴露的真实边界 | CI 常绿，内测期新增缺陷 80% 有对应用例 |

**M1 主要风险**：真实用户带来的边界问题数量级高于自测；长期常驻下的进程稳定性与内存驻留（P7.3 的 24 h 长跑只是下限）；上游同步的真实成本仍只有一次演练数据支撑。M1 前两个迭代预留为"内测环境搭建 + 身份隔离收尾"，不排新功能。
