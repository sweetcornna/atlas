### v2.16 决策（真机验收后的边界澄清，实施方裁定）

**① 10/10 通过的是 P2.5 DoD ①，不是 AC-2。**
DoD ① 要的是「转发且不丢」，已达成。AC-2 判据要的是**60 s 内的 `ack` 回执**，而本次 demo 的目标节点**刻意没接 `@qianmo/adapter`**（`deliverAndAck`）。那条链要成立，沙箱内得跑真 occ + adapter。**归属 P4.1**（跨节点投递端到端），不在 P2.5 内补——P2.5 的职责边界是「接住、唤醒、转发」，把 ack 塞进来会让两个包的判据互相纠缠。

> **已闭合（v2.20，2026-08-13）**：P4.1 在同一套 Dormice + gVisor 环境里跑通了这条链——沙箱内是真 occ/ACP 常驻节点，ack 与 `task.result` 都从发送方自己那条连接回来，10/10、ack P95 4.440 s。本条从此只作历史记录读。

**② 这批耗时数字不能外推成 P3.1 的休眠唤醒基准。**
被唤醒的是一个 **94 KB 单文件测试节点**，堆几乎是空的；而 P3.1 的 DoD 说的是**常驻 occ 节点**「休眠 → 唤醒 → 可响应」。E2 实测 400 MiB 工作集回暖就要 9–10 s，常驻 occ 的堆通常显著更大。**本次结果只证明「沙箱冻结/解冻这一层的开销可以忽略」（p50 37 ms），把唤醒总成本的锅甩给了工作集回暖那一层**——这恰恰是 P3.1 基准该测的东西，且**尚未测得**。谁要是拿 43 ms 去填 P3.1 的基准报告，那是把测试桩的数字冒领成常驻节点的数字。

**③ 真机环境的两处一次性障碍已记录，供后续复现参考**：`workbench` 模板镜像已不在 GCP 宿主上（另注册 `qm-ac2` 模板指向 `dormice-base`，未改动既有模板）；`@qianmo/transport` 的**服务端半边用 `Bun.serve`**，而基础镜像只有 node 24，因此沙箱镜像必须带 bun（用宿主现成的 linux 二进制 `docker cp` 进去后 commit，不联网拉取）。**后者是设计约束不是环境问题**——任何要跑传输服务端的沙箱镜像都得有 bun。

**Q1 最后一跳保信箱还是改走 ACP `session/prompt`？→ 保信箱，给 ACP 补读者。**
章程 §341 定死「复用基座既有的文件信箱」，改道要动章程（§2.1：范围变更必须回写章程并升版本号），并会**让 P2.1 与 adapter 已交付的 DoD 证据链失效**——那条证据链是软著与竞赛成果认定的一部分（§5.5、风险 L-1）。而「上层封装、不再造第二条收件通道」这个定性在换宿主后**依然成立**。补一个 ACP 侧轮询器是纯增量，不推翻任何已验收的东西。

**Q2 常驻宿主真的必须是 ACP 吗（headless streaming 单会话更省事）？→ 是，维持 ACP。**
不是因为 ACP 更好，而是因为**我们已经发出去的协议假设了一个节点上有多个 agent**：注册中心用复合键 `<node>/<agent>`（`protocol.md` §2.4），D-2 把判环粒度定在**处理者**而非节点、理由正是「同一节点因不同目标地址被再次经过是正常路由」（`protocol.md:311`，已于 P0.8 评审通过），`protocol.md:594` 更直接讨论了「同一节点的两个 agent」。**headless 是单会话**，选它等于回头推翻已通过评审的 D-2 与已交付的 P2.1。

**Q3 跨会话并发（`switchSession` 改的是进程级 STATE）要不要现在处理？→ M0 内用节点级 turn 串行规避，不改基座核心。**
ACP 只保证**同一会话内**串行，跨会话不串行，而进程级身份切换会互相覆盖（transcript 落盘、成本记账、analytics 都可能串会话）。M0 锁定「**一节点同一时刻一个活跃 turn**」，串行闸放在我们自己的常驻包里 + 一条断言，**不动基座**。代价是同节点多 agent 不能真并发——M0 的验收与演示都不需要它。**此项作为已知缺口记录在案**，M1 若要真并发，须回到基座核心。

**Q4 `LIMITS.defaultTtlMs = 30_000` 小于 34.7 s 冻结，要不要改数值？→ 不改数值，改成类型强制传 `now`。**
`protocol.md` 已经要求判据先过 T-2 闸门，但那是**口头约定**：`packages/protocol/src/validate.ts` 里是裸 `Date.now()`。把「必须传 `now`」变成编译期约束，比调一个数值更能根治，且**不必回写章程 §3.3 C-4**（改 `LIMITS` 要走文档流程，代码半天、流程一周）。

**Q5 两处 factor-2 检测盲区（阈值 60 s / 40 s，而 E4 冻结 34.7 s）→ 需真机 A/B，合并进 P3.1 的基准跑。**
降 factor 会抬高误判率，这个权衡**不能在本地拍**。并入下一节的真机基准一起测。

**另记一条与本包无关但已核实的基座缺陷**（不修，仅备案）：ACP 的 `initialize` 对外声明支持 MCP（`AcpAgent.ts` 的 `mcpCapabilities`），但 ACP 路径从不构造 MCP client，客户端传入的 `mcpServers` 只被用来算会话指纹。**若 M0 演示中有人用 Zed/Cursor 接 ACP 并配 MCP server，会当场发现工具不存在。**演示脚本须避开这条路径。

- owner：董宗岳（backup：陈曦宇）——**排期归属与 owner 为提案，负责人可调**

  - **activator（跨节点唤醒转发）**：「**接住请求 → 唤醒目标节点 → ready 后转发**」。这一层非有不可——内核的连接排队缓冲**只在同机有效**（同机的 socket 激活方案解决不了跨机场景），而沙箱 daemon **只监听本机、不提供这一层**（已实测确认）。它的角色等同于 Knative 的 activator、等同于 `systemd-socket-proxyd` 的跨节点版
  - **keepalive（常驻保活心跳）**：周期**必须严格小于沙箱的冻结空闲阈值**，且**必须去打 daemon 的 API**——实测结论是**沙箱内自主工作对空闲判据零可见**：一个 100% CPU 忙碌的进程照样会在空闲阈值到点后被冻结，之后长时间零推进且**永不自恢复**。**"把停止阈值设为 null"不是解法，它反而把故障从"掉到停止态、下次冷启重来"升级为"永久静默停摆"**——这是本次实测最反直觉的一条，务必写进实现注释
  - 两者共用同一条通道：**都在宿主侧、都代表沙箱去打 daemon 的 API**，因此**都必须只暴露 touch / acquire、绝不暴露 destroy**。理由是硬的：daemon 的凭据无权限分级（销毁与执行同一把），**一旦这个组件把 destroy 暴露出去，AC-6(c) 立刻不成立**
- **为什么给它单独立包并给足工时**：它是 **M0 里唯一没有先例可抄、同时压着 AC-2 与 AC-6(c) 两条验收标准**的组件。P3.1 直接压在它后面（见 §0.1 新链）
- 交付物：宿主侧 activator/keepalive 组件——请求接住与排队、目标节点唤醒、ready 探测与转发、心跳调度；**能力面白名单**（只有 touch / acquire，destroy 与其他破坏性接口在代码层面不可达，不是靠配置关掉）；唤醒各阶段耗时埋点（接住 → 发起唤醒 → ready → 首字节转发），输出给 P3.1 与 P4.1 的基准报告
- DoD：
  - ① **唤醒转发闭环**：目标节点处于休眠态时，向它投递一条消息，**由 activator 接住并唤醒、目标 ready 后消息被完整转发且不丢**；连续 10 次 10/10；转发链路各阶段耗时有埋点数据
  - ② **防静默冻结**：一个在沙箱内持续自主工作（不经 API 交互）的常驻进程，在**超过冻结空闲阈值数倍的时长**内**始终未被冻结**且任务持续推进；作为对照，**关掉 keepalive 后同一场景必须复现被冻结**（负向自测——没有对照组的"它没坏"不算证据）
  - ③ **destroy 不可达**：断言该组件对外可达的能力面**不含任何破坏性接口**；构造一次直接调用销毁接口的尝试，**必须失败并留审计事件**；断言进 CI（与 P0.7 的不变式断言同一套机制）
  - ④ **崩溃与重启**：组件自身进程被 `kill -9` 后能自恢复，恢复期间被接住的请求要么被转发、要么明确失败，**不得静默丢弃**
- **风险跟踪**：本包**与 P3.1 互相咬合**，任一半不到位 AC-2 都不成立。若 S2 结束时 ① 与 ② 未同时拿出最小证据，**立即向负责人报警**并评估把 P3.1 的休眠半边后挪——**不要让两个都没做完的半成品在 S3 互相等待**

## M1：校内内测（2027H1，粗粒度）

**目标**：把 M0 的原型变成 20 ~ 50 名软院同学能真实用起来的内测系统。

> **v2.0 变更**：M1 的头号硬门槛"基座退场"**已取消**（基座是长期地基，不退场，章程 §5.7）。取而代之的是身份隔离验收与上游同步节奏确定——工作量小得多，且不再是"未完成不得进入 M2"的阻断项。这是本次路线变更在 M1 上释放出的最大一块工时。

| 方向 | 内容 | 出口判据 |
|---|---|---|
| **基座关系收敛** ⚖️ | 身份隔离改名完成并验证（阡陌节点 / occ / 官方 Claude Code 三者共存）；按 P7.4 演练数据确定上游跟随节奏并写入章程；决定是否向上游回贡（**提请评审**） | 三者共存实测通过；同步节奏有书面结论 |
| **注册发现产品化** | 最小 Web 控制台（智能体列表、状态、消息链查看）、账号体系、智能体生命周期管理 | 内测用户无需接触 CLI 即可完成注册与查看 |
| **权限模型上线** | 用户授权流（授权申请 → 用户确认 → 时效凭据 → 主动撤销）；权限审计报表 | 所有需确认动作 100% 经过用户授权链路，抽查无绕过 |
| **记忆能力上线** | 语义检索（在确定性检索之上叠加，非替换）、记忆治理（冲突消解、过期废止、跨项目隔离） | 检索命中率与幻觉引用率有量化指标并优于 M0 基线 |
| **生产级加密** | mTLS 替换预共享密钥；证书签发与轮换；密钥管理 | 解除章程 N-3；渗透自查无高危项 |
| **多租户与配额雏形** | 内测必需的租户隔离与用量配额（仍不做计费，N-1 保留） | 跨租户数据访问用例全部被拒 |
| **第二产品线验证** | 运维值守场景原型（常驻智能体的第二类应用） | 至少 1 个真实值守场景连续运行 7 天 |
| **稳定性目标** | 可用性 ≥ 99%（按内测时段计）、唤醒 P95 < 30 s（M0 为 60 s） | 以 P7.3 基线报告为对比基准 |
| **知识产权** | 软著申请提交；开源方案确定并执行（**前置**：M0 P8.4 的科技处口径） | 材料齐备且经学校科技处确认 |
| **边界用例库** | 从 12 条扩到 ≥ 40 条，覆盖内测暴露的真实边界 | CI 常绿，内测期新增缺陷 80% 有对应用例 |

**M1 主要风险**：真实用户带来的边界问题数量级高于自测；长期常驻下的进程稳定性与内存驻留（P7.3 的 24 h 长跑只是下限）；上游同步的真实成本仍只有一次演练数据支撑。M1 前两个迭代预留为"内测环境搭建 + 身份隔离收尾"，不排新功能。

2027 下半年开放公测：面向校外用户开放注册，多租户与配额转为正式能力，注册中心从单点转为高可用部署，接入真实云资源的弹性扩容（解除 N-7），并按 P6.4 的收敛建议补齐跨厂商 A2A 互操作；同时把编程智能体之外的第三类场景（协作开发）推上线，用公测期的真实用量数据校验"节点 + 网络"飞轮是否真的转起来——判据是跨节点协作消息量占总消息量的比例持续上升。2028 进入商业化：解除 N-1，落地计费与结算、定价方案与四类收入模式。**商业化的法律前置由 M0 P8.4 与 M1 的科技处口径承接**（风险 L-2、L-5），不再是旧路线中的"基座退场"。
