## 0. 结论摘要

| # | 结论 | 强度 |
|---|---|---|
| 1 | 三项一致性（多轮 / 工具调用 / 流式）对两条 provider **各跑一遍、6 个用例全绿** | 实测（§2） |
| 2 | 同一条编程任务在两条 provider 下**都完成并通过任务自带断言**（`bun test` 退出码 0，5 pass / 0 fail），且两次都**没动过测试文件**（sha256 前后一致） | 实测（§3） |
| 3 | 「仅改配置不改代码」达成的是**最强形态**：两次运行的命令行**逐字相同**，唯一变化是配置文件里的两行 | 实测（§3.2） |
| 4 | **判据解读有限定**：基座 `ProviderKind` 只有 `openai-compat` 一种，我们给的是「同一 kind、不同 compat profile + 不同调优门」，**不等于**判据字面的「两个不同供应商适配器」 | 代码（§1、§5 G-1） |
| 5 | **`applyCompatRule` 在基座线上请求路径没有任何调用者**——compat 档案目前是死代码，只有单测在用 | 代码（§5 G-2） |
| 6 | **新发现的基座缺陷**：端点在正文分片之间回 `reasoning_content: ""` 时，最终助手消息被切成 **37 个内容块**（18 个是空 thinking），且 `--print` 的 `result` 字段返回**空串** | 实测 + 代码（§4 D-4） |
| 7 | 两条 provider 指向**同一个网关**，因此没有验证「不同厂商 HTTP 端点」层面的差异（鉴权头、错误码、限流头） | 事实（§5 G-4） |

**一句话**：AC-5 的三条子判据在**行为层面**都测通了，卡点不在能力而在**定性**——本仓库只有一种 provider kind，所以「两家适配器」这个说法要么按 compat profile 解释（本文给的证据），要么等基座/我方新增第二种 kind。是否够，由负责人判定。

## 1. 选型与配置

### 1.1 两条 provider

配置文件 [`tests/integration/fixtures/qianmo-providers.json`](../../tests/integration/fixtures/qianmo-providers.json)：

| id | kind | compatRule | defaultModel | 选它的理由 |
|---|---|---|---|---|
| `qianmo-deepseek` | `openai-compat` | `deepseek` | `deepseek-v4-pro` | 推理模型。命中基座的 **DeepSeek 调优门**（`src/services/api/openai/requestBody.ts:137`），线上请求体会多出 `thinking` / `enable_thinking` / `chat_template_kwargs` / `reasoning_effort`；compat 档案 `always-preserve`，回放时保留 `reasoning_content` |
| `qianmo-qwen` | `openai-compat` | `strict-openai` | `qwen3.8-max` | 非 DeepSeek 家族，一条调优都不命中；compat 档案 `strip` + 不支持 `thinking` 字段 + 不支持 `stream_options.include_usage`，是矩阵里与 `deepseek` **最对立**的一条 |

选这两条不是随手挑的：`COMPAT_PROFILES` 里 `cerebras` / `groq` / `strict-openai` 三条档案**字段完全相同**，`permissive` 与 `deepseek` 只差 `reasoningContentEcho` 一档。要在本仓库现有代码里找出「两条真的走不同分支」的组合，`deepseek` × `strict-openai` 是唯一把三个开关全部拉开的一对：

```
                       supportsStreamUsageOption  supportsThinkingField  reasoningContentEcho
deepseek                       true                     true              always-preserve
strict-openai                  false                    false             strip
```

### 1.2 那条必须写清的限定

章程 §4 AC-5 的字面要求是「**≥ 2 个不同模型供应商适配器**」。本仓库的现实是：

- `src/services/providerRegistry/types.ts:19` —— `export const ProviderKindSchema = z.literal('openai-compat')`。**只有一种 kind**，没有第二种适配器实现可选。
- 因此上面两条 provider 走的是**同一套适配器代码**（`src/services/api/openai/` + `@ant/model-provider` 的 OpenAI 转换与流适配），差异只发生在**该适配器内部的分支**：compat 档案与 DeepSeek 调优门。

**我们提供的是「同一 kind、不同 compat profile / 不同调优分支」，不是「两个不同供应商适配器」。**本文不把它粉饰成完全满足；满足了什么、没满足什么见 §5。

> 顺带说明：仓库里另有 Gemini（`@ant/model-provider` 的 `providers/gemini/`）与 Grok（`src/services/api/grok/`）两条**真正独立**的适配器代码路径，但它们不由 `providerRegistry` 管理、不进 `providers.json`，且本次核验没有这两家的凭据，**未测**。如果负责人认为必须是「两套适配器代码」，那条路要走的是给 Gemini 或 Grok 弄一份凭据，而不是本文这两条。

## 2. 一致性测试套件（多轮 / 工具调用 / 流式）

代码：[`tests/integration/provider-adapter-consistency.test.ts`](../../tests/integration/provider-adapter-consistency.test.ts)

- **同一套断言，对两条 provider 各跑一遍**（`runConsistencySuite(provider)` 被 `for` 循环调用两次，测试代码对两者逐字相同）。
- 走的是基座真代码 + 真网络：`anthropicMessagesToOpenAI` → `anthropicToolsToOpenAI` → `buildOpenAIRequestBody`（含 DeepSeek 调优门）→ `applyCompatRule` → `getOpenAIClient` 真 SDK → `adaptOpenAIStreamToAnthropic`。**没有任何 `mock.module`，没有录制回放。**

- **无凭据自动 skip**：缺 `OPENAI_API_KEY` 或 `OPENAI_BASE_URL` 时整组跳过并打印原因，CI 不会因缺凭据变红。

### 2.3 逐项结论

| 项 | 断言的实质 | `qianmo-deepseek` | `qianmo-qwen` |
|---|---|---|---|
| **流式** | 事件序列以 `message_start` 开、`message_stop` 收；正文**分多次 delta 到达**（不是一发整块）；`stop_reason=end_turn` | ✅ 33 个 `text_delta` | ✅ 7 个 `text_delta` |
| **多轮** | 第一轮的助手输出（含 thinking 块）被**原样回填**进第二轮请求，第二轮答案依赖第一轮上下文（41 → 42） | ✅ 回填带 thinking 块，答 `42` | ✅ 回填带 thinking 块，答 `42` |
| **工具调用** | 模型发起 `tool_use`（名字、`id`、参数 JSON 均可解析），`stop_reason=tool_use`；回灌 `tool_result` 后**据其作答** | ✅ 参数 `{"project":"qianmo"}`，回灌后答 `failing` | ✅ 同上 |

工具调用那一项的第二跳同时是 **`reasoning_content` 回声契约的实测**：`deepseek` 档案把它保留着发回去、`strict-openai` 档案一律剥除，两条都被端点接受。

## 3. 编程任务用例（端到端跑 occ）

脚本：[`scripts/qianmo-provider-task.ts`](../../scripts/qianmo-provider-task.ts)

任务设计（关键在于**不能让模型自己出题**）：临时 git 仓库里放一份**已经写好的失败测试** `test/slugify.test.ts`（5 条断言）和一个会抛异常的桩 `src/slugify.ts`。提示词要求「实现 `slugify` 让 `bun test` 通过，不许改 `test/` 下任何文件」。跑完之后脚本做三件事：

1. 校验 `test/slugify.test.ts` 的 **sha256 前后一致**（模型没把测试改成通过）；

3. 落盘 `model-patch.diff` / `task-tests.log` / `occ-stdout.json` 供取证。

脚本还会先跑一次**基线**：桩实现下 `bun test` 必须是红的，否则这条用例什么都证明不了。

（`script` 一栏就是本仓库 `scripts/qianmo-provider-task.ts` 当前内容的 sha256，可用 `shasum -a 256` 复核。）

**第二层——命令行逐字相同，只改配置文件内容。**用两份**同 id、不同内容**的配置：[`ac5-config-a.json`](../../tests/integration/fixtures/ac5-config-a.json)（deepseek）与 [`ac5-config-b.json`](../../tests/integration/fixtures/ac5-config-b.json)（qwen），都叫 `qianmo-ac5`：

## 4. 能力差异记录

| # | 差异 | 谁处理 | 证据 |
|---|---|---|---|
| **D-1** | **thinking 开关三件套**：`deepseek-v4-pro` 的请求体带 `thinking:{type:'enabled'}` + `enable_thinking:true` + `chat_template_kwargs`，`qwen3.8-max` 一个都不带 | **基座已处理**：`isDeepSeekTuningActiveForModel()` 按模型名/主机名开关（`requestBody.ts:137`），命中条件是 `model.toLowerCase().includes('deepseek')`（`deepseekHost.ts`） | §2.1 的确定性用例逐字段断言过 |
| **D-2** | **`reasoning_effort` 阶梯**：DeepSeek 有自己的三档（`low`/`high`/`max`），未设时默认 `max`；qwen 路径不发这个字段 | **基座已处理**：`resolveDeepSeekReasoningEffort()`。⚠️ 注意**默认是 `max`**，一致性套件显式传了 `low`，否则每条用例都按最贵档跑 | `deepseekTuning.ts` + 确定性用例 |
| **D-3** | **`reasoning_content` 回声**：DeepSeek 契约要求把上一轮的 `reasoning_content` 原样带回（缺了会 400），`strict-openai` 档案则一律剥除 | **基座已处理**：`anthropicMessagesToOpenAI` 的 thinking→`reasoning_content` 映射 + 工具轮的空串兜底；`applyCompatRule` 的 `always-preserve` / `strip` 两档 | §2.2 工具调用第二跳两条都绿 |
| **D-4** | **空 `reasoning_content` 把消息切碎**：qwen3.8-max 经本网关会在**正文分片之间**回 `reasoning_content: ""`。基座流适配器的判断是 `if (reasoningContent != null)`（`openaiStreamAdapter.ts:150`）——空串不是 `null`，于是每次都**新开一个空 thinking 块并关掉正在写的 text 块**。实测同一条编程任务的最终助手消息被切成 **37 个内容块**（其中 18 个是空 thinking，与 text 交替），而 deepseek 只有 **2 块** | **要我方补**（或推回基座）。见 §5 G-3 | 会话 JSONL 实测（§3.1 那两次运行的 `config/projects/**/*.jsonl`） |
| **D-5** | **`--print` 的 `result` 字段为空**：`QueryEngine.ts:1154` 只取**最后一个内容块**且要求它是 `text`。D-4 让最后一块是空 thinking，于是 `result:""`。deepseek 同样任务下 `result` 有完整文本 | **要我方补**：任何用 `-p --output-format json` 驱动节点的脚本都不能只信 `result` | §3.1 两次运行的 `occ-stdout.json` 对比 |
| **D-6** | **`stream_options.include_usage` 被剥除后 usage 照样回来了**：`strict-openai` 档案会删掉这个字段（为 Cerebras/Qwen 官方端点写的），但本网关无此要求，仍回了 `usage=87/283` | 无需处理，但要知道**档案是按官方端点写的、对网关偏保守** | §2.2 的 `usage=87/283` |
| **D-7** | **上下文窗口**：deepseek 走 `DEEPSEEK_CONTEXT_WINDOW`=1,000,000，qwen 落到第三方默认 200,000 | **基座已处理**：`getDeepSeekContextWindow()`；其他端点用 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 修正 | occ 结果里的 `contextWindow` 字段：1000000 vs 200000 |

## 5. 缺口清单（AC-5 没满足的部分）

| # | 缺口 | 影响 | 建议处置 |
|---|---|---|---|
