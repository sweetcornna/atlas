## 1. 出发点：白名单不变

`policy.ts` 的论证照旧有效：工作区里的 `.omp/config.yml` 能加覆盖层没写的键，后来出现的工具也不受覆盖层管，所以常驻回合只跑表里列出的工具。高权限模式没有把白名单改成黑名单，只多加一张**放权期间才生效**的表；表外的工具在任何模式下都拒绝：`eval`（解释器在 qianmopi 宿主进程里，有文件、进程和网络，沙箱管不到）、`lsp`、`debug`、`ida`、`security_scan`、基座自带的 `browser` 与 `computer`（P21 专属浏览器和电脑另算）、记忆与技能写入、`goal`、`ask`、`task`。

## 2. 四种模式

| 模式 | 标识 | 直接执行 | 每次要确认（P14 单次批准） |
|---|---|---|---|
| 人工确认（缺省） | `off` | 原有工具面，一个字节不变 | 原有规则 |
| 自动接受编辑 | `accept-edits` | 工作区内的文件编辑 | 沙箱命令、联网读取、GitHub（读写都问） |
| 自动审批 | `auto` | 沙箱命令、工作区编辑、联网读取、GitHub 只读操作 | GitHub 写操作（`pr_create`） |
| 跳过权限确认 | `full-access` | 以上全部 | 无；红线规则、受保护路径、云端电脑设成「每一步都确认」的照旧 |

每种模式都有到期时间（到期回到人工确认），都能立即收回（单个或全部），急停时永久清零，审计不记原始输入，派发前后都复核租户与归属。

### 2.1 分类与审批矩阵

宿主按工具名和参数确定性地分类，不调用模型、不信扩展或模型自报，也不用基座的 auto 顾问：

| 类别 | 包括 | 人工确认 | 自动接受编辑 | 自动审批 | 跳过权限确认 |
|---|---|---|---|---|---|
| `local` | `bash`（只在沙箱里） | 不提供 | 问 | 直接 | 直接 |
| `read-out` | `web_search`；`read` 读 `http(s)://`；GitHub `repo_view`、`file_read`、`search_*`、`run_watch` | 不提供 | 问 | 直接 | 直接 |
| `act-out` | GitHub `pr_create` | 不提供 | 问 | 问 | 直接 |
| — | GitHub 其他操作（`pr_push`、`pr_checkout` 会在节点上改 git 状态） | 拒 | 拒 | 拒 | 拒 |

工作区编辑（`write` / `edit` / `ast_edit`）在任何放权模式下都直接执行，限制与 `--allow-workspace-edits` 相同：只限工作区，不准碰 `.git`、`.omp` 等策略目录和受保护根，不计次。工作区外的写入仍走 P14 原有审批。

「问」的那一次走 P14 一次性审批：工具名为 `qianmo_elevated_<工具>`，只认「仅批准本次」，授权窗口（allow-window）一律拒绝，批准绑定节点、智能体、会话、任务、调用号与参数摘要。

### 2.2 工具面

| 条件 | 进 `--tools` 的 |
|---|---|
| 放权生效 | 工作区编辑三件、`web_search` |
| 节点有可用沙箱（§3） | 另加 `bash` |
| 节点 `PATH` 上有 `gh` | 另加 `github`。基座对 `--tools` 里没注册的名字直接拒绝启动，`gh` 不在就不能写；没有时权限模式页写「GitHub 不提供」 |

覆盖层同时打开 `web_search.enabled`、`fetch.enabled`（`read` 读网址靠它）、按上表打开 `github.enabled`，并把 `bash` 的 `direnv` 关掉（它会在进沙箱前在宿主上执行工作区的 `.envrc`）、自动转后台关掉（长命令留在前台，结果才能回到闸门的完成阶段）。每个子进程的 `--approval-mode` 在放权期间取 `write`（读写工具免问），否则保持 `always-ask`；不用 `yolo`，问不问由宿主闸门决定，这样批准能绑定精确参数并进审计。

**子智能体不放**：节点上不派生 qianmopi 原生子智能体，`task` 在所有模式下都在拒绝表里，`before_subagent_spawn` 始终拦截。需要分工时用名册里的其他智能体（P29）。

### 2.3 云端电脑（P21）

专属浏览器和电脑本来就有自己的确认设置：「敏感操作确认」（缺省：截图、读页面等观察直接放行，导航、点击、输入、按键、滚动逐次确认）、「每一步都确认」、「自主」。放权模式只改一处：**跳过权限确认**期间，「敏感操作确认」的资源按「自主」走；「每一步都确认」照旧逐步问；其他模式不改资源自己的设置。每次动作现读当前模式，收回、到期、急停立即恢复。打开终端类应用仍然要确认，输入文本与剪贴板仍过红线检查。

## 3. 命令在哪里执行

- `bash` 只在沙箱里跑。扩展在 `tool_call` 里把命令改写成 `bwrap … --chdir <工作区> -- <shell> -c '<原命令>'`（基座的 `input` 修订：改写后的命令就是实际执行、持久化和审批看到的命令）。沙箱参数由宿主算好写进授权文件，模型选不了；`cwd` 必须在工作区内。
- 参数（Linux + bubblewrap）：`--unshare-user/pid/ipc/uts/net`、`--die-with-parent`、`--new-session`、`--hostname sandbox`；`--proc`、`--dev`、`/tmp` 用 tmpfs；系统目录 `/usr /bin /sbin /lib /lib64 /lib32 /etc /opt /nix` 存在的才只读挂；**这一个智能体的工作区**按真实路径读写挂载，其中 `.git`、`.omp`、`.claude`、`.codex`、`.gemini`、`.qianmo` 只读（防止植入下一次在宿主上运行的 git 钩子和配置）；不挂用户主目录和阡陌配置根（节点私钥、审计链、ESTOP、授权账本、别的智能体都看不见）；`--clearenv` 后只给 `PATH`、`HOME=/tmp`、`LANG=C.UTF-8`。**沙箱里的命令没有网络。**
- 每个智能体第一次放权时，宿主用它真正要用的那组参数跑一次 `… -- <shell> -c true` 探测；过了才把沙箱写进授权文件。沙箱按智能体分开建，不共用。
- 没有可用沙箱时（macOS、没装 bubblewrap、建不了用户命名空间）照样能开模式，但 `bash` 不进工具面，状态里写明原因；即使扩展被绕过，宿主闸门也拒绝没有沙箱的 `bash`。
- **Ubuntu 24.04 缺省开着 `kernel.apparmor_restrict_unprivileged_userns=1`**，非特权 bubblewrap 建不了用户命名空间，探测失败，`bash` 不提供（按设计关闭，不降级成裸跑）。要在这类节点上提供命令，需要运维给 bwrap 配 AppArmor 配置或放开该开关，这是节点运维决定，代码不改它。

## 4. 联网

- 只经类型化、过闸门的工具：`web_search`、`read` 读网址、`github`（用节点上 `gh` 已登录的身份）。命令本身没有网络。
- `read` 读网址：宿主闸门先查每个目标主机。字面地址直接判；域名解析出的**每个**地址都必须是公网地址。回环、内网、链路本地（含 `169.254.169.254` 云元数据）、CGNAT、组播、文档与保留段、IPv4 映射的 IPv6、ULA、解析不出，一律拒绝并记一行。判据复用 `outboundPolicy.ts` 的 `publicAddress`。
- 未覆盖：检查与基座实际连接之间的 DNS 重绑定窗口；基座抓取跟随跳转（`redirect: "follow"`），公网地址跳到内网不在检查范围内。这两处要改基座，本轮没做。

## 5. 要确认时：前台确认框

1. 节点照 P14 生成一次性审批请求，经控制链路送到中枢，按会话属主路由。后台审批队列（`/admin/approvals`）照常列出；权限模式页（`/admin/elevation`）只列已经放行或拒绝的调用记录。
2. 对话前台 `/` 不轮询审批区，另有一条独立的确认流：页面可见时每 5 秒请求一次 `GET /v0/approvals?mine=1`（只列自己会话里待批的），有新的一条就弹确认框（智能体、类别、参数摘要、到期，按钮「批准本次」「拒绝」「稍后」）；用户以前允许过浏览器通知时同时发一条通知。只有个人账号（非 viewer）且中枢开了审批时才挂这段脚本。
3. 已登录的个人成员或运维点批准就生效，不再要个人凭据，也不看登录了多久（负责人 2026-10-22 决定）；被拒时就地写明原因。开启或改模式仍要 30 分钟内验证过的个人 ops 凭据（§7）。
4. 节点等一次批准最多 60 秒（P14 上限，同时受任务剩余时间和看门狗约束）；扩展侧闸门 75 秒超时。过时未批即拒。

## 6. 闸门、到期、次数、收回、急停、审计

| 项 | 规则 |
|---|---|
| 闸门 | 每次高权限调用前，扩展经 `QIANMO_ELEVATION_V1` 问宿主；宿主核对急停、模式、代次、到期、次数、调用来自当前活动回合，需要时转 P14 审批，再计次；调用结束补一条完成记录。同一调用号重复授权不重复计次 |
| 到期 | 5 分钟到 24 小时，缺省 2 小时；到期即回到人工确认，不续签。每 2 秒巡检一次，不必等下一次调用 |
| 次数 | 每次放行记 1 次，缺省 200，最多 2000；用尽即回到人工确认 |
| 关闭（回到人工确认） | 代次 +1，作废待批的高权限审批，回收子进程，当前回合可以收尾但之后的调用全拒 |
| 收回（单个 / 全部） | 同上，并**立即关掉**该智能体全部子进程，正在跑的沙箱命令随父进程退出 |
| 急停 | 节点急停拉下时闸门全拒、所有模式清零；松开后不恢复，要重新开 |
| 重启 | 放权不跨重启：节点起来时所有智能体都是人工确认、代次重置，旧子进程的调用因代次不符被拒 |
| 外部底层 | 只对 qianmopi 底层生效；智能体跑在 dsh、ACP 等外部底层上时拒绝开启并写明原因，已开的会在切过去时被巡检收回 |
| 节点审计链 | `elevation.grant` / `elevation.disable` / `elevation.revoke` / `elevation.estop`（操作人、模式、到期、次数、代次）；每次调用 `elevation.action`（工具、类别、GitHub 操作名、目标主机、参数摘要、是否经批准、结果、任务号、调用号）。**不记命令正文、搜索词与网页内容** |
| 控制操作 | `elevation.status|actions|enable|disable|revoke`；急停下 `status|actions|disable|revoke` 仍放行，`enable` 拒绝；写操作按 operationId 去重 |

## 7. 谁能开

- **开启或改模式**：个人 `ops` 账号，且 30 分钟内验证过凭据；旧式管理令牌和应急身份不能开。
- **回到人工确认、收回、全部收回**：能写运维动作的主体都可以，收回不设门槛。
- **租户**：租户范围内的运维只看得到、改得了本租户的智能体，范围外的地址答 404；派发前和等待中都复核。
- **记账**：开启、改模式、关闭、收回都在控制台动作账本记一行（`elevation.enable` / `elevation.disable` / `elevation.revoke`，失败带码），节点审计链有对应行，靠 operationId 关联。

## 8. 怎么启用

节点常驻宿主总是装着 `elevation` 控制处理器，所有智能体启动时都是人工确认，什么都不用配。中枢要加 `--elevation`，并且必须同时开 `--approvals` 和 `--control`（命令见 [`console.md`](./console.md)「高权限模式（P39）」）。

## 10. 未覆盖与残余风险

- **舰队节点没实测**：真 bubblewrap 只在本机 colima 里跑过；舰队节点（Ubuntu 24.04）在缺省 AppArmor 设置下预计拿不到 `bash`。
- **浏览器里的界面脚本没在真浏览器里点过**：权限模式页与前台确认框的脚本只在测试里的假 DOM 上验证过。
- **`web_search` 和 GitHub 没有真调用**：测试里网络读取只读过本机网页；搜索后端、`gh` 的真实请求没跑。
- DNS 重绑定与跳转（§4）。
- 沙箱里的命令能读工作区里的一切，联网工具能把读到的东西带出去（URL 参数也算）；要防外泄就用「自动接受编辑」。
- 宿主上的 qianmopi 进程本身不在沙箱里：模型密钥和会话文件仍在它手里，命令看不到；`eval` 因此在所有模式下都不放。
- `github` 的权限以节点 `gh` 登录的令牌为准，建议细粒度令牌。
- 沙箱强度是 bubblewrap 的强度，不是虚拟机；章程里 gVisor 的冻结态是另一件事。
