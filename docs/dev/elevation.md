## 1. 为什么仍从白名单出发

`policy.ts` 的论证不变：工作区里的 `.omp/config.yml` 能加覆盖层没写的键，后来出现的工具也不受覆盖层管，所以「常驻回合只跑表里列出的工具」才是第一道线。高权限模式**不改成黑名单**，只是给白名单多加一张按档位生效的表；表外的工具在任何档位下照旧拒绝。以下工具在所有档位都不放：`eval`（它的执行环境在 omp 宿主进程里，有文件、进程与网络，沙箱管不到；复核 D13–D16 的结论原样有效，基座的 `browser`、`computer` 前导函数依赖它，也一并不放）、`lsp`、`debug`、`ida`、`security_scan`（都会在宿主上起工作区可控的程序）、记忆与技能写入、`goal`、`ask`。

## 2. 档位

| 档位 | 自动放行 | 要用户单次批准（P14） |
|---|---|---|
| 关（默认） | 现有工具面，一个字节不变 | 现有规则 |
| 逐次确认 `confirm-each` | 无 | 每一次高权限调用 |
| 对外动作确认 `confirm-external` | 沙箱内命令、子智能体、工作区写入、联网只读（搜索、抓取网页、GitHub 只读操作）、浏览器观察 | 对外改动：GitHub `pr_create` / `pr_push`；P21 浏览器与电脑的导航、点击、输入、按键、滚动 |
| 完全放权 `full` | 以上全部 | 无（P21 资源自己设成「每一步都确认」时仍按它） |

- 高权限工具：`bash`、`task`、`web_search`、`github`、`read` 读 `http(s)://`。节点只读启动时，放权期间同时打开工作区写入（`write` / `edit` / `ast_edit`，限制与 `--allow-workspace-edits` 相同：只限工作区、不准碰 `.git`、`.omp` 等策略目录；不计次、不逐次确认）。
- 分类由宿主按工具名与参数重新计算，不信扩展或模型自报。批准只认一次性授权（`qianmo_elevated_*`，拒绝窗口授权），绑定节点、智能体、会话、任务、调用号与参数摘要。
- **子智能体**：档位同样作用于子智能体（omp 的 `--tools` 不约束子会话，靠扩展在每个子会话里重新绑定的 `tool_call`）。子会话没有界面，**不等待审批**：要批准的调用在子智能体里直接拒绝；自动放行的调用照样过宿主闸门、计次、进审计。档位为关时 `before_subagent_spawn` 照旧全拒。

## 3. 命令在哪里执行

- `bash` 只在沙箱里跑，不在宿主上裸跑。扩展在 `tool_call` 里把命令改写成 `bwrap … -- /bin/bash -c '<原命令>'`（omp 的 `input` 修订，改写后的命令即实际执行、持久化与审批看到的命令），沙箱参数由宿主算好写进授权文件，模型选不了。
- 沙箱（Linux + bubblewrap）：只读挂载 `/usr`、`/bin`、`/lib*`、`/etc`、`/opt`、`/nix`；读写挂载**这一个智能体的工作区**，其中 `.git`、`.omp`、`.claude`、`.codex`、`.gemini`、`.qianmo` 只读（防止植入下一次在宿主上运行的 git 钩子与配置），工作区内的受保护根用空目录遮住；不挂用户主目录、阡陌配置根（节点私钥、审计链、ESTOP、授权账本、别的智能体都看不见）；独立 PID、IPC、UTS、网络命名空间，**命令没有网络**；`--clearenv` 后只给 `PATH`、`HOME=/tmp`、`LANG`；`--new-session`、`--die-with-parent`。
- 联网只经类型化、受闸门的工具：`web_search`、`read` 读网址（宿主先解析地址，回环、私网、链路本地、CGNAT、组播一律拒绝）、`github`（用节点运维为 `gh` 配好的身份）、P21 专属浏览器。完整的浏览器操作走该智能体在「云端电脑」开出的专属浏览器；完全放权档下这些操作不再逐次确认。
- 节点没有可用沙箱（macOS、未装 bubblewrap）时可以开档位，但 `bash` 不在工具面里，状态页写明原因。命令带网络（pasta/slirp 网络命名空间）留到下一轮，本机 root 容器里未能验证。

## 4. 预算、急停与审计

| 项 | 规则 |
|---|---|
| 到期 | 打开时选 5 分钟 ~ 24 小时，默认 2 小时；到期即失效，不续签 |
| 次数 | 每次放行的高权限调用记 1 次，默认 200、最多 2000；用尽即失效 |
| 急停（单个） | 控制台「急停」→ `elevation.revoke`：节点档位归零、代次 +1、撤销待批的高权限审批、立刻回收该智能体全部 omp 子进程（沙箱随父进程退出）；之后到达的调用因代次不符被拒 |
| 急停（全部） | 「全部收回」对每个已放权的智能体发同一条命令；节点本地 ESTOP 文件拉下时，闸门全拒、档位清零，松开后不恢复 |
| 闸门 | 每次调用前扩展经 `QIANMO_ELEVATION_V1` 问宿主：宿主核对 ESTOP、档位、代次、到期、次数、活动回合，需要时转 P14 审批，再计次；调用结束补一条结果 |
| 审计链 | 节点 `elevation.grant` / `elevation.disable` / `elevation.revoke`（操作人、档位、到期、次数、代次）与每次调用的 `elevation.action`（工具、类别、GitHub 操作名、目标主机、参数摘要、是否经批准、结果、任务号、调用号）；不记命令正文与网页内容 |

控制链路上的 `elevation.status|actions|disable|revoke` 在 ESTOP 下仍放行，`elevation.enable` 拒绝。

## 5. 谁能打开

- **打开或改档**：个人 `ops` 账号，且凭据在 30 分钟内验证过（Bearer 个人凭据，或 30 分钟内登录的会话，或在开关对话框里重新输入个人凭据）。旧式管理令牌与 break-glass 不能打开。
- **关闭与急停**：能写运维动作的任何主体（含 break-glass）——收回权限不设门槛。
- **租户**：租户范围内的运维只能操作本租户的智能体，别的租户的地址按「资源不存在」答 404；控制台在派发前、等待中都复核。
- **记账**：打开、改档、关闭、急停都在控制台动作账本记一行（`elevation.enable` / `elevation.disable` / `elevation.revoke`，目标是智能体地址，失败带码），节点审计链同时有对应行，靠 operationId 关联。

## 6. 残余风险（如实写）

- 沙箱里的命令能读工作区里的一切，联网工具能把读到的东西带出去（URL 参数也算）；要防外泄就用「逐次确认」。
- omp 进程本身不在沙箱里：模型密钥、会话文件仍由宿主上的 omp 持有，命令看不到，但 `eval` 一旦放开就看得到——所以 `eval` 不放。
- 地址检查与 omp 的实际连接之间有 DNS 重绑定与跳转的窗口；外部抓取不跟随到内网需要改基座，本轮未做。
- `github` 用节点上 `gh` 的身份，权限以运维给的令牌为准；建议细粒度令牌。
- 沙箱的强度是 bubblewrap 的强度，不是虚拟机；章程 A-1 的 gVisor 冻结态仍是另一件事。本节验证在 Linux root 容器里做，未在舰队节点上实测。
