## 1. 可运行性验证（实测）

### 1.1 依赖安装

首次执行依赖安装**失败**：锁文件把全部依赖包的下载地址硬编码到了某个特定的国内镜像站，而其中一个包在该镜像上返回 404。

**第二次执行同一命令成功**，补齐了剩余 8 个包（其中 4 个是被替换成空实现的内部原生包、3 个是本地垫片包）。安装完成后依赖目录约 274 个顶层条目。

> **结论**：依赖可装，但可复现性依赖第三方镜像站的可用性，且依赖来源不受我方控制。这本身就是一条不应把该树纳入任何构建流程的理由。

### 1.2 版本命令

版本命令**执行成功**，正常输出版本号。

但这个"成功"具有误导性。该树的开发入口自带一个"缺失模块自检"：扫描源码目录，统计无法解析的相对导入数量；若不为零，则在版本号后附加警告并拒绝转发到真实 CLI。实测输出是**干净的版本号**，即自检认为缺失数为零。

**自检不可信**：它的扫描只覆盖静态导入与同步 require 两种写法，不覆盖动态导入；且对带扩展名的路径做了过宽的存在性判定。

### 1.3 独立的静态解析（关键证据）

我用打包器对 CLI 入口做了一次**纯静态、不联网、不执行**的模块解析，结果是**失败，31 处模块无法解析**，可分为两类：

| 类别 | 数量 | 内容 |
|---|---|---|
| **树内真实缺失的模块** | 8 | 工具注册表引用的 3 个工具实现、对话框启动器引用的 3 个界面/命令模块、上下文压缩的缓存实现、终端渲染引擎的调试模块 |
| **依赖清单里根本没声明的可选第三方包** | 23 | 三家云厂商的模型后端 SDK、一个云身份库、一个对象存储客户端、10 个可观测性导出器、一个 HTML→Markdown 转换器、一个图像缩放库 |

此外还有一批**被特性开关包住的同步 require**，指向**整个不存在的目录**（跨会话对端发现工具、若干实验性工具）。这些在打包阶段被死代码消除掉了，不报错，但一旦对应开关打开就会在运行时直接崩溃。

### 1.4 可运行性结论

| 项目 | 结果 |
|---|---|
| 依赖安装 | ✅ 可成功（需容忍镜像抖动） |
| 版本命令 | ✅ 成功 |
| 真实 REPL 启动 | ❌ **未实测成功；静态解析表明会在模块解析阶段失败**（工具注册表是启动必经路径，其中 3 处缺失） |

我**没有**执行交互式启动命令——它会拉起 REPL 并可能触发登录与模型调用，违反本次调研的约束。因此"REPL 启动会失败"是**基于静态解析的推断，不是运行时实测**。

> **对阡陌的意义**：这棵树的定位只能是**只读的行为参考**。任何"先让它跑起来再改"的路线在第一步就要先补 8 个缺失模块和 23 个未声明依赖，且这还只是静态可见的部分。这与章程 §5.7 的判断一致。

## 2. 架构地图（模块 / 目录粒度）

以下按**功能职责**描述，不涉及具体文件与符号。

| 层 | 所在目录 | 职责 |
|---|---|---|
| **入口分发** | `src/entrypoints/` | 极薄的快路径路由器，按首个命令行参数分发到各运行形态，全部使用动态导入以压缩启动开销 |
| **CLI 枢纽** | `src/` 顶层的主模块（单文件约 800 KB） | 命令行选项注册、快路径路由、REPL 全量初始化 |
| **查询主循环** | `src/` 顶层的查询模块 + `src/query/` | 对话生命周期：构建消息 → 流式调用模型 → 解析响应 → 检测工具调用 → 执行并回灌结果；含 token 预算与终止钩子 |
| **工具系统** | `src/` 顶层的工具基类与注册表 + `src/tools/`（52 个子目录） | 统一的工具抽象（校验、权限检查、只读/破坏性/并发安全标记、特性开关、渲染） |
| **会话与历史** | `src/` 顶层的历史/上下文/初始化模块 + `src/utils/` 下的会话存储模块 | 提示词历史、上下文装配、会话初始化、逐行追加的会话记录 |
| **状态管理** | `src/state/` | 轻量可观察 store + React Provider + 派生选择器 |
| **后台任务** | `src/tasks/` | 多种任务类型：子智能体、同进程队友、本地 shell、工作流、远程智能体等 |
| **多智能体协作** | `src/utils/` 下的 swarm 相关模块 + `src/coordinator/` | 团队创建、队友派生、权限同步、协调者模式 |
| **记忆** | `src/memdir/` | 分层记忆的目录布局、扫描、相关性召回、时效标注、团队共享记忆 |
| **远程控制** | `src/bridge/`（33 个模块） | 把本机作为工作节点注册到云端并轮询领取任务 |
| **服务集成** | `src/services/`（40 个条目） | 模型 API 客户端、MCP、上下文压缩、记忆抽取、OAuth、策略限制、遥测 |
| **钩子系统** | `src/utils/` 下的钩子模块 + `src/schemas/` | ⚠️ 注意：`src/hooks/`（85 个文件）是 **React hooks**，与事件钩子系统无关 |
| **扩展面** | `src/skills/`、`src/plugins/`、`src/commands/`（约 100 个） | 技能、插件、斜杠命令 |
| **终端渲染** | `src/ink/`、`src/vim/` | 定制的终端渲染引擎与 Vim 模拟器（与阡陌无关） |

**配置根目录**：所有全局状态默认落在用户主目录下的一个隐藏配置目录中，且支持通过单个环境变量整体重定向。

> **对阡陌的意义**：这个"单一环境变量重定向整个状态根"的做法，是多租户/多智能体隔离最省事的一个杠杆，我方在运行时适配层应保留等价能力。

**编译期特性开关**：全树用编译期宏做死代码消除，据统计有 40 个以上的内部开关。与阡陌相关的四个（按功能命名，非其内部代号）：**常驻助手**、**跨会话收件箱**、**后台会话管理**、**定时触发**。

> **关键判断**：这四类能力在该产品的**公开发行版中被死代码消除掉了**——也就是说，公开渠道拿不到这部分的设计信息。这正是该树对我们唯一不可替代的价值：**理解设计问题，而不是获取代码**。

## 3. 扩展点分析

以下每个主题均按章程 §5.6 的固定三段式记录。

### 3.1 常驻 / 守护形态

#### ① 来源（行为与设计意图）

该产品文档列出五种运行形态：交互式 REPL、无头/SDK 模式、MCP 服务端、远程控制、后台守护。

从入口分发器的行为可以看出守护形态的**进程模型**：一个长驻的**监督进程**负责生命周期，按"工作类型"派生出多个**精简的工作子进程**；子进程走独立的命令行标志启动，且刻意跳过配置加载与遥测初始化以降低派生开销。**监督进程本身的实现目录在该树中整体缺失**，只剩调用点。

树中唯一可读的长驻工作进程是"远程控制"那一类，其设计意图明确表述为：配置由调用方以 JSON 形式下发；认证凭据由监督进程通过进程间通信推送，而非工作进程自行登录；日志走工作进程的标准输出管道；停止通过中止信号完成，不使用进程退出；错误按"永久失败"与"瞬时失败"分类，映射到不同退出码，供监督进程决定是否重启。

**保活机制**观察到三层：一是注册-轮询循环本身；二是向服务端定期续租，服务端租约有效期约为心跳间隔的数倍（观察到心跳为十秒级、租约为分钟级）；三是定期发送空的保活帧以防止中间代理掐断长连接，该帧在进入界面层之前被过滤掉。代码注释还记录了两个已知的时间边界：长时间空闲后指针会失效、不刷新凭据的会话会在数小时后静默死亡。

**子会话的拉起方式**是真正的操作系统子进程：监督方以同一个 CLI 可执行文件派生子进程，令其进入"标准输入输出流式 JSON"模式，通过管道双向驱动；子进程环境中被刻意删除了顶层凭据、注入了会话级短期凭据与环境类型标记；标准输出逐行按 NDJSON 解析，标准错误进入固定长度的环形缓冲。监督侧持有一个会话句柄，可写入标准输入、强制终止、刷新凭据、查询当前活动。

另外观察到两套**与常驻直接相关的轻量持久化**：

- **活跃会话注册表**：每个进程在用户配置目录下写一个以自身进程号命名的 JSON 文件，内含进程号、会话标识、工作目录、启动时间、会话类型（交互/后台/守护/守护工作进程）、可选的名称、可选的消息套接字路径、以及活跃状态与最近更新时间。目录权限收紧到仅属主可访问。进程退出时自行清理；枚举时对每个条目做存活探测，判定为死进程则清扫，但在跨系统边界的场景下（进程号无法可靠探测）刻意跳过清扫，宁可少数也不误删。文件名匹配采用严格的全量正则，注释中记录这是为了修复一个真实事故——宽松的数字前缀解析会把用户的普通文件误判为进程号并删除。
- **定时提示词**：每个项目目录下一个 JSON 文件，记录若干条"到点入队一段提示词"的任务，含 5 字段 cron 表达式、创建时间、最近触发时间、是否周期、是否持久、是否豁免自动过期。最近触发时间会被回写，使得**进程重启后仍能重建下一次触发时刻**；另有"错过的任务"检测，用于在宕机后补做。触发的提示词以低优先级进入命令队列，在两轮对话之间排空。

最后，该产品的"常驻助手"形态从注释与历史拉取逻辑看，其**智能体主循环运行在服务端**，本地 CLI 更接近一个事件流查看器与消息投递端；历史按页惰性拉取。（此判断置信度较低，见第 6 节。）

#### ② 结论（我们得到的设计判断）

1. **"监督进程 + 流式 stdio 子进程"是常驻智能体最务实的进程模型。** 它不需要把智能体运行时嵌进自己的进程，升级与崩溃隔离都天然成立。
2. **保活应当用租约心跳，而不是 pid 文件。** 租约天然适配云端多副本与网络分区；pid 文件只在单机成立。
3. **唤醒必须有两条腿**：消息触发与定时触发。只有其中一条的系统，要么无法响应外部事件，要么无法自主推进。
4. **常驻态本身的状态量很小**：身份、端点、活跃度、几个时间戳。它应当是一张随时可重建的表，而不是需要备份的重资产。
5. **"错过的任务"是必须显式建模的**——进程重启后不补做，用户就会认为智能体不可靠。
6. **进程号级别的资源清扫极其危险**：那条被记录在注释里的误删事故，本质是"宽松解析 + 破坏性操作"的组合。任何按名字模式清扫用户数据的逻辑都必须用全量严格匹配。

#### ③ 我方实现差异

已落地于 `@qianmo/registry` 与 `@qianmo/runtime-adapter`：

**注册与发现**（`@qianmo/registry`）
- 我们采用**内存注册表 + 租约 TTL**（默认 90 秒），而非参考实现的"进程号文件 + 目录扫描"。理由：进程号文件天然绑死单机，无法跨主机；阡陌从第一天就是双节点目标，注册表必须能通过 HTTP 暴露。
- 过期采用**读时惰性判定**，不启用定时器。理由：无后台任务意味着无需生命周期管理，测试可注入可控时钟做确定性验证；参考实现的目录扫描则必须承担"何时扫、扫多少"的额外决策。
- **同名不同端点视为冲突并拒绝**，而参考实现允许后写覆盖。理由：允许覆盖等于允许任意进程劫持一个已存在的智能体名字；我们宁可让重启的节点显式注销后再注册。
- 记录中包含**能力声明列表**（上限 64 项），参考实现没有等价物。理由：阡陌需要"按能力寻址"，而不只是"按名寻址"。
- 时钟通过构造参数注入，测试使用手动时钟。

**常驻生命周期**（`@qianmo/runtime-adapter`）
- 我们把智能体生命周期定义为 `running` / `sleeping` / `stopped` 三态，其中 **`sleeping` 是一等状态**：保留身份与记忆、不消耗算力。参考实现没有显式的休眠态，其"空闲"只是"两轮之间"的隐含条件。理由：阡陌的核心卖点之一是常驻成本可控，休眠必须是可观测、可审计、可被协议显式驱动的状态，而不是一个推断出来的瞬时属性。
- 唤醒被建模为**协议消息类型**（见 §3.2），而不是进程信号或退出码。因此"外部事件唤醒常驻智能体"与"另一个智能体发消息唤醒它"走**完全相同的路径**，只有一套语义需要维护。
- 我们定义 `AgentNode` 作为运行时接缝：当前由桩实现满足，将来可替换为真实运行时。参考实现没有这样的接缝——其守护逻辑与具体 CLI 强绑定。这条接缝正是章程 §5.7 中"基座退场"得以低成本执行的技术前提。

**尚未实现、已列入计划**
- 监督进程与子进程派生（对应路线图 A-1 / R-3）：将采用"官方 SDK 驱动 + 租约心跳 + 中止信号收尾"的组合，退出码区分永久/瞬时失败。
- 定时唤醒与"错过的任务"补做（对应 R-3）：数据结构上会保留"最近触发时间回写"这一使重启后可重建的关键属性。

### 3.2 跨会话消息机制

这是阡陌通信层最重要的一个调研主题，也是发现最丰富的一节。

#### ① 来源（行为与设计意图）

**对模型暴露的接口只有一个消息发送能力**，参数为：接收方、一句简短摘要（用于界面预览）、消息体。消息体既可以是纯文本，也可以是几种结构化控制消息之一（关停请求、关停应答、计划审批应答）。

**接收方地址是一个联合体**，共四种形态：队友名字、通配符广播、本机套接字路径、远程会话标识。地址解析被刻意拆成一个独立的小模块，使得工具枚举阶段不必把 HTTP 客户端与套接字实现一并加载——这是一个值得注意的懒加载分层。

**投递路径按优先级共四条**：

1. **远程会话**（跨机器，经服务商中转）——调用点存在，**实现模块在该树中是空壳**。
2. **本机套接字**（同机跨进程）——调用点存在，**服务端与客户端实现在该树中都是空壳**。但从调用契约仍可读出完整的接口形状：服务端在会话初始化阶段绑定套接字并把路径导出到环境变量（且刻意在任何钩子可能派生子进程之前完成，以保证子进程能继承到正确的环境快照）；无头模式下注册一个"收到消息即踢一次主循环"的回调；套接字路径还会被写进 SDK 的初始化事件中，但对公开类型隐藏。
3. **同进程子智能体**（按名字或标识寻址）——**完整可读**。目标正在运行则把消息挂入其待处理队列，在它下一个工具回合排空；目标已停止或已被状态表淘汰，则**从磁盘上的会话记录复活该智能体**，并把消息作为新一轮输入。
4. **队友名字 / 广播**（文件邮箱）——**完整可读，是实际的主力机制**。

**文件邮箱的存储形态**：用户配置目录下，按团队分目录，每个接收方一个 JSON 文件，内容是消息数组，每条含发送方、正文、时间戳、已读标记、可选的颜色与摘要。写入时先确保文件存在，再用建议性文件锁串行化，**锁内重新读取**后追加、整体写回；锁配置为带退避的有限次重试，注释说明这是为了让并发的多个进程排队等待而不是直接失败。

**结构化协议消息与普通消息共用同一条通道**：协议消息被序列化成 JSON 塞进正文字段，靠其中的类型字段做二次分发；一个统一的判别函数负责把它们从模型上下文里过滤掉。观察到的协议类型约 10 类，覆盖空闲通知、权限请求/应答、沙箱权限请求/应答、计划审批请求/应答、关停请求/批准/拒绝、任务指派、团队权限更新、模式设置请求。

**接收侧有三个彼此独立的消费者**：

- **交互式 REPL**：约 1 秒一次轮询未读消息，先按类型分拣到十来个桶，普通消息被包装成一个带发送方属性的 XML 标签，作为**新的一轮用户输入**提交。若当前空闲则立即提交；若正忙则暂存到应用状态的收件箱中，等本轮结束再排空。**已读标记只在投递或入队成功之后才写回**——崩溃时宁可重投也不丢失。
- **回合中途的附件通道**：在一轮对话进行中直接读同一批邮箱，过滤掉协议消息，按"发送方+时间戳+正文前缀"做去重，产出为元信息类型的 API 消息。这条路径是**无头模式下唯一生效的接收方式**（那里没有界面层的轮询钩子）。
- **同进程队友的阻塞等待**：约 0.5 秒一次的轮询循环，返回"新消息 / 关停请求 / 已中止"三种结果之一，作为下一轮的输入。这是"常驻智能体在两轮之间挂起等消息"的完整实现。

此外还有一条**人类快捷方式**：用户在输入框里以 `@名字` 开头即可直接投递到对应邮箱，发送方记为用户。

> ⚠️ **命名陷阱**：该树中另有一个名为"邮箱"的模块，实为单进程内的界面事件队列，从不落盘，与跨会话通信无关。

**空闲与唤醒语义**：该系统**没有休眠概念**。所谓空闲就是"两轮之间"；消息之所以能唤醒接收方，是因为接收方要么在轮询、要么会在下一个工具回合读邮箱。空闲信标由每个回合边界主动向领导者邮箱投递一条空闲通知实现，带空闲原因与最近一条对话的摘要，并有重复抑制。模型侧的行为契约被明确写进提示词：给空闲队友发消息会唤醒它并被正常处理。

**权限分级**观察到五层：

| 层 | 规则 |
|---|---|
| L1 | **跨机器发送必须人工确认，且免疫权限绕过模式** |
| L2 | 其余目标（本机套接字 / 队友名 / 广播）一律自动放行 |
| L3 | 校验层白名单：地址不得含特定分隔符（因为一个会话只有一个团队）；结构化消息不得广播、不得跨会话（跨会话只允许纯文本）；关停应答只能发给领导者；拒绝关停必须给理由；远程目标要求连接处于活跃状态，且在实际发送前**二次复查**（因为人工确认可能阻塞数分钟） |
| L4 | 处理器层角色校验：只有领导者能审批/驳回计划 |
| L5 | **接收侧发送方鉴权**：计划审批应答只接受来自领导者名字的消息，注释明确写着这是为了防止队友伪造审批 |

L1 的实现细节值得注意：它使用的是"安全检查"而非"权限模式"通道，注释解释说这样才能同时挡在权限绕过模式与自动放行分类器之前，因为跨机器的提示注入必须保持不可绕过。

**限流与防循环：完全不存在。** 我用多组关键词（速率、冷却、节流、跳数、深度上限、最大消息数、乒乓）扫过全部消息相关模块，**零命中**。真实存在的只是饿死防护、去重、容量上限与轮询节流：

| 机制 | 观察到的量级 |
|---|---|
| 界面层收件箱轮询 | 约 1 秒 |
| 同进程队友轮询 | 约 0.5 秒 |
| 文件锁重试 | 十次量级、毫秒级退避 |
| 单次工具结果上限 | 十万字符量级 |
| 队友消息界面留存上限 | 数十条，超出丢弃最旧 |
| **优先级阶梯（防饿死）** | 关停请求可跳序 → 来自领导者的未读优先 → 其余先进先出。注释明确说明是为了防止对等消息洪泛时领导者指令被饿死 |
| 空闲通知折叠 | 每个发送方每批只保留最新一条 |
| 跨来源去重 | 按"发送方 + 时间戳 + 正文前缀"三元组 |
| 用户输入优先 | 有用户输入排队时拒收智能体消息，退回队列 |

**防循环完全依赖提示词约束**：提示词中明确要求不要主动发起关停请求、不要发送结构化状态消息（改用任务更新接口）。

#### ② 结论（我们得到的设计判断）

1. **"文件邮箱 + 建议性锁 + 已读标记 + 轮询"是一个完全站得住的 v0 通信层。** 零依赖、崩溃可恢复、易于人工调试；代价是全量重写的写放大与秒级延迟。对双节点原型而言这个代价可以接受。
2. **投递语义应当是"至少一次"**：先投递成功、再标记已读，宁可重投不可丢失。这要求接收侧具备幂等能力。
3. **地址应当是带 scheme 的统一形态。** 参考实现的四形态联合体（名字/通配符/套接字/会话号）导致每一处校验都要穷举分支，且"裸路径按套接字处理"这类兼容逻辑会长期腐蚀协议清晰度。
4. **协议消息不应当复用正文字段。** 参考实现把控制消息序列化成 JSON 塞进文本里，导致每个消费者都要先做一次"这是不是协议消息"的判别，且判别函数成为所有接收路径的隐式依赖。
5. **空闲唤醒的本质就是"踢一次主循环"**，实现成本极低。真正的难点不在唤醒机制，而在于唤醒之后的优先级与去重。
6. **优先级阶梯是必需品**：一旦对等消息可以自由流动，控制指令就会被饿死。这个问题在双节点时不明显，节点一多必然爆发。
7. **两个必须补上的缺口**：
   - **发送方身份认证**：参考实现的 L5 只是一次字符串比较。谁能写那个文件，谁就能冒充领导者。
   - **限流与跳数上限**：完全缺失，仅靠提示词约束。两个自动对话的智能体极易形成无限往返，这在阡陌的双节点场景下是**必然会发生**而不是可能发生。

#### ③ 我方实现差异

已落地于 `@qianmo/protocol`。核心差异是：**参考实现把安全性与收敛性交给提示词，我们把它们放进协议本身。**

**统一寻址**
- 我们只有一种地址形态：`qianmo://<节点>/<智能体>`，两段均限制为小写字母数字加连字符下划线、长度上限 64、且首尾必须是字母数字。理由：窄字符集让地址天然大小写不敏感且 URL 安全，避免了参考实现中"名字里能不能带某个字符"这类需要在多处重复校验的问题。
- 解析函数在畸形输入上**返回空值而不抛异常**（热路径无异常），另提供在信任边界使用的断言版本。
- 我们**不提供通配符广播地址**。理由：广播的代价与团队规模成线性关系，且它与限流、跳数控制的交互复杂；v0 阶段由发送方显式列举收件人。

**不可变信封与结构化防循环**
- 消息是**版本化的不可变信封**，字段包括：信封版本、消息标识、贯穿全链路的追踪标识、发送方、接收方、消息类型、载荷、创建时间、生存期、**已途经节点列表**。
- **防循环是结构性的，不是靠提示词**：转发时向途经列表追加当前节点；若该节点已在列表中，立即以"检测到环路"错误码拒绝；列表长度超过上限（8 跳）则以"跳数超限"错误码拒绝。转发产生**新信封**而非原地修改，保证在途消息不可变。
- **生存期是协议字段**：默认 30 秒，超期消息以"生存期过期"错误码拒绝投递。参考实现没有等价物——一条消息可以永远躺在邮箱文件里。
- **单条信封体积上限 256 KiB**，超限有独立错误码。
- **每发送方入站预算 600 条/分钟**，作为协议级限制由接收节点执行，有独立错误码。参考实现完全没有这一层。

**类型是一等字段**
- 消息类型是信封上的独立枚举字段（任务请求、任务结果、存活探测、探测应答、**唤醒**、错误），而不是塞在正文里的判别符。理由见结论第 4 条：每个消费者不必再实现一次"这是不是协议消息"的判别。
- **唤醒是一个显式的消息类型**，因此 §3.1 所说的"休眠一等状态"与本节的消息通道天然接通：唤醒一个休眠智能体与给它发任务走同一条链路、同一套校验、同一套限流。

**稳定的线上错误码**
- 我们定义了 10 个稳定的、对端可见的错误码（信封格式错、版本不支持、地址非法、类型非法、体积超限、生存期过期、跳数超限、环路、限流、未知智能体），每个错误携带出错字段路径。参考实现的失败以自然语言字符串返回给模型，无法被程序可靠分类。
- 校验分**两阶段**：先结构、后边界（体积/生存期/跳数/环路），且**同一阶段的所有问题一次性全部报出**，而不是遇到第一个就返回。理由：调试跨节点问题时，一次拿到全部原因比逐个试错节省大量时间。

**邮箱作为可替换接口**
- `@qianmo/runtime-adapter` 把邮箱定义为接口（投递 / 取出 / 队列长度），当前提供进程内的先进先出实现，并预留了持久化实现的位置。参考实现直接把"JSON 文件 + 锁 + 整体重写"焊死在唯一实现里。理由：我们需要在原型阶段用零依赖实现快速验证协议，同时保证将来换成持久化队列时协议层零改动。

**仍待补齐（已知缺口，列入计划）**
- **发送方身份认证**：当前协议层只做地址格式校验，尚无签名。这是 §3.2 结论第 7 条指出的缺口，对应路线图 C-5 / S-3，必须在双节点联通前完成。
- **审计追踪**：追踪标识已在信封中就位，但落库与查询尚未实现（对应 C-6）。

### 3.3 会话持久化与恢复

#### ① 来源（行为与设计意图）

会话记录采用**按项目分目录、每会话一个逐行追加文件**的布局，位于用户配置目录之下；子智能体的记录写入子目录，并可按运行批次分组。

恢复语义提供四种：按标识恢复指定会话、继续当前目录下最近一次会话、恢复时派生出新标识（保留原会话不变）、只恢复到指定的某条消息为止。另有"回滚文件到某条消息时的状态"的能力。

有三处设计意图值得记录：

1. **会话标识与存储根必须原子切换。** 注释记录了一个真实缺陷：恢复会话后存储根变了但标识计算仍沿用旧的工作目录，导致钩子拿到的记录路径指向不存在的文件。修复方式是把两者绑定为一个原子单元。
2. **尾部窗口扫描的元数据丢失。** 会话列表功能只读取记录文件的尾部若干字节来提取标题等元数据；如果用户改名之后又追加了足够多的消息，改名记录会被挤出尾部窗口，列表就退回显示自动生成的首句提示词。修复方式是在进程退出前重新追加一次元数据。
3. **单文件体积失控。** 注释明确记录会话记录可以增长到 GB 量级，因此所有读取原始记录的调用方都必须在一个体积阈值（数十 MB 量级）处主动放弃，以避免内存耗尽。

**上下文压缩**提供多档策略（自动压缩、微压缩、反应式压缩、上下文折叠、会话记忆压缩）。⚠️ 其中反应式压缩在该树中被替换为恒等函数，缓存版微压缩模块缺失，上下文折叠的持久化是空实现——**这条链在参考树里是断的**，但主循环中的调用点与状态转移语义仍可读。

#### ② 结论

1. **"逐行追加 + 尾部扫描列表"这个组合有已知的失效模式**：元数据被挤出窗口。任何采用该模式的系统都会遇到，必须提前设计。
2. **会话标识与存储位置必须视为一个不可分割的单元**，否则所有下游（钩子、附件、恢复）都会出现路径漂移。
3. **单会话记录的无界增长是常驻场景的必然问题**，必须从第一天就规划分片与归档，而不是事后加一个读取上限来兜底。
4. **不应自行复刻记录文件格式**：格式是实现细节、会随版本变化，而恢复语义（按标识/继续/派生/截断恢复）是稳定的抽象。

#### ③ 我方实现差异

**当前状态：尚未实现**，属于路线图 R-1（会话持久化）范围，由常驻运行时方向 owner 负责。本节记录的是**已确定的设计约束**：

- **不复刻记录文件格式。** 持久化将定义为 `@qianmo/runtime-adapter` 中 `AgentNode` 接缝之下的一个接口，首个后端直接使用官方 SDK 提供的会话列举 / 查询 / 派生 / 恢复能力（章程 §5.7 路径 A）。理由：格式是易变的实现细节，恢复语义才是稳定契约；这也让基座退场时该模块无需重写。
- **列表元数据独立成索引，不做尾部窗口扫描。** 理由：直接规避结论第 1 条的失效模式。代价是多维护一份索引与一致性，我们认为这个代价低于"列表偶发显示错误标题"的用户可见故障。
- **会话标识与存储根在类型层面绑定为单一值对象**，不允许分别传递。理由：把结论第 2 条的不变式变成编译期约束，而不是靠注释与评审保证。
- **从第一天就按体积分片**，单片有硬上限，超限自动滚动并归档。理由：结论第 3 条。参考实现的"读取上限"是一个止血措施，而非解法。
- **恢复语义只暴露四种**（按标识、继续最近、派生新标识、截断到某条），与参考实现观察到的语义集合一致——这是能力对齐，不是表达复制。

### 3.4 记忆机制

#### ① 来源（行为与设计意图）

记忆存放在一个专用目录中（可通过环境变量整体重定向到远端挂载点），包含：

- **一个入口索引文件**，作为常驻内容进入系统提示词，有**行数与字节数双重硬上限**（数百行 / 数万字节量级），超限自动截断；
- **若干主题文件**，每个带 YAML 前置元数据，其中包含一句描述与一个类型字段；类型共四类：关于用户的、用户给出的纠正反馈、项目事实、参考资料；
- **按日期命名的日志文件**：智能体先向当日日志追加，事后再整理成主题文件并更新索引。

**相关性召回不使用向量检索。** 观察到的流程是：递归扫描目录下的 Markdown 文件（排除索引文件本身），**只读每个文件的前若干行**取出前置元数据，按修改时间新→旧排序，总量上限百量级；把"文件名 + 描述"拼成一份清单；然后**调用一个小模型**，以受 JSON 模式约束的输出格式让它挑选最多 5 个相关文件；返回结果再用合法文件名集合过滤掉幻觉；此前几轮已经浮现过的文件在调用之前就被排除，以免浪费选择器有限的名额。为掩盖这次额外调用的延迟，主循环中有对应的预取。

选择器的系统提示词表达了两条明确意图：**宁缺毋滥**（不确定就不选）；以及**当某个工具正在被使用时，不要再选它的用法参考文档**（对话里已经有可用范例了），**但仍要选关于该工具的警告、坑与已知问题**，因为正在使用恰恰是这些内容最有价值的时刻。

**时效性的处理方式很克制**：不删除、不降权，而是把修改时间换算成人类可读的天数，并对超过一天的记忆自动附加一段"这是时间点观察而非实时状态、其中的代码行为断言可能已过期、请先核实再当作事实"的提示。注释解释了动机：模型不擅长日期算术，原始时间戳不会触发"这可能过时了"的推理，而"47 天前"会；且有用户反馈过时的代码位置引用被当作事实断言，**带引用反而让过时的说法显得更权威**。

**记忆根目录的路径校验被当作安全边界处理**（因为它同时是读取白名单的根）：拒绝相对路径、拒绝根目录与近根目录、拒绝盘符根、拒绝网络共享路径、拒绝含空字节的路径、拒绝会展开为用户主目录或其祖先的简写形式。

**团队共享记忆**位于记忆目录下的一个子目录，有独立的同步服务。

此外还有两条独立通路：项目指令文件（按 托管 > 用户 > 项目 的优先级从工作目录逐级向上收集）；以及一个回合结束后运行的后台记忆抽取智能体。

#### ② 结论

1. **"元数据清单 + 小模型选择器"是比向量检索简单一个数量级的召回方案，且天然可解释。** 对阡陌 M0 阶段而言，这是正确的起点：无需嵌入模型、无需向量库、无需索引重建，且选择理由可追溯。代价是每轮多一次小模型调用，可用预取掩盖。
2. **只读前置元数据、不读正文**，使得扫描成本与文件体积解耦。这是让该方案在文件数增长时仍然可用的关键。
3. **时效性用"贴标签 + 免责声明"而非删除或降权，是一个成本几乎为零而收益明显的设计。** 判断权交给模型，系统不必维护衰减函数。
4. **常驻索引必须有硬上限**，否则它会无声地吃掉上下文预算。
5. **记忆目录同时是读取白名单的根，因此它的路径校验是安全边界，不是输入清洗。** 那六条拒绝规则每一条都对应一种真实的越权读取路径。
6. **分层的依据应当是生命周期与作用域**，而不是文件角色。

#### ③ 我方实现差异

已落地于 `@qianmo/runtime-adapter` 的记忆模块：

- **三层按生命周期划分**：`working`（当前任务）→ `project`（本项目累积）→ `baseline`（跨项目长期知识），由热到冷。参考实现的分层依据是文件角色（索引 / 主题 / 日志 / 团队），冷热关系是隐含的。理由：阡陌需要"整层降温"这一显式操作（见下条），而按文件角色分层无法定义这个操作。
- **提供显式的归档（降温）操作**：把某一层的全部记录整体下移到相邻的更冷一层，返回移动条数；最冷层归档是空操作。这正是"一个任务做完，其工作集变成项目上下文；项目上下文最终沉淀为长期知识"的机制化表达。参考实现依赖一个**后台抽取智能体**做整理，属于概率性行为；我方的降温是**确定性的、可测试的**状态转换。理由：确定性操作可以在测试中断言，也可以被审计；概率性整理无法保证收敛。
- **记录携带 键 / 值 / 所属层 / 更新时间**四元组。时效性在**读取时**由更新时间派生，而不是写入时固化。理由：与结论第 3 条一致，但把标签生成推迟到读取时，可以让同一条记忆在不同场景下呈现不同的时效表述。
- **召回策略不进存储接口。** 存储接口只负责读写与分层，检索策略作为可插拔组件独立演进。首个策略将采用结论第 1 条的"清单 + 选择器"方案。理由：向量检索是我们明确的**后续**选项而非首选，接口必须允许两者共存而不是二选一。
- **注入时钟**：更新时间通过构造参数注入，测试使用可控时钟。参考实现直接读系统时间。

**尚待补齐**
- 持久化后端（当前为进程内实现）、记忆根目录的安全校验（结论第 5 条，必须在接入真实文件系统之前完成）、团队共享层（对应路线图 R-2 的后半程）。

### 3.5 钩子与可扩展性

#### ① 来源

**事件钩子系统**（注意：与该树中数量庞大的界面层 hooks 完全无关，二者仅名字相同）覆盖约 28 个生命周期事件，其中与阡陌控制面直接相关的有：工具使用前/后、工具失败、用户提示提交、会话开始/结束、停止、子智能体开始/结束、压缩前后、权限请求/拒绝、**队友空闲**、**任务创建**、**任务完成**、工作目录变更、文件变更。

钩子有四种形态：执行 shell 命令、以提示词形式调用小模型、派生一个子智能体、发起 HTTP 请求。共有配置包括一个**在派生之前求值的过滤表达式**（用权限规则语法匹配工具名与参数，避免为不相关的调用白白派生进程）、超时、状态提示、是否只触发一次。命令型钩子有一个**异步变体**：钩子以特定退出码结束时会主动唤醒模型——这构成了一条独立于消息通道的唤醒路径。HTTP 型钩子的请求头变量插值采用**显式白名单**，未列入的环境变量不会被插值。

配置来源分五层（托管策略 / 用户 / 项目 / 项目本地 / 命令行），其中托管策略层可以全局禁用所有钩子或只允许托管钩子，且**非托管层无法禁用托管钩子**。执行器有一道独立的守卫：所有钩子在交互模式下都要求工作区已被信任，注释明确说明这是一个集中式的远程代码执行防护点。

钩子的输入是一个带会话标识、记录路径、工作目录、权限模式、智能体标识的基础对象，各事件再叠加自己的字段；输出要么声明转为异步，要么返回一个同步响应，其中可以携带"是否继续"、"是否抑制输出"、"放行/阻断决定"、"追加上下文"等；特定退出码表示阻断性错误。

**MCP 集成是双向的**：

- 作为**客户端**：支持标准输入输出、SSE、HTTP、WebSocket 等多种传输；配置从工作目录逐级向上收集并按"近覆盖远"合并，另有用户级、项目本地级与企业托管级。外部工具被包装成内部工具对象，名字带服务端命名空间前缀，只读性与并发安全性取自服务端声明的注解。**服务端提供的元数据被明确当作不可信输入处理**——注释指出其中的换行会注入到工具清单的渲染中，因此做了空白折叠。外部提供的提示词被转成斜杠命令时，使用其名称而非标题，因为标题中的空格会破坏命令解析。
- 作为**服务端**：通过标准输入输出暴露**完整的内建工具注册表**（而非精选子集），工具描述与参数模式由内部工具对象动态生成。仅暴露一个斜杠命令。有注释标明"嵌套的外部工具不会被再导出"。

**智能体定义**从约定目录下的 Markdown 文件加载，支持声明可用工具、禁用工具、技能、外部服务、**会话级钩子**、模型、权限模式、最大轮数、记忆、隔离方式（工作树/远程）等。加载时按 托管 > 用户 > 项目 优先级从工作目录逐级向上收集，**按 inode 去重**以处理配置目录被符号链接进项目树的情况，并对版本控制工作树做了专门的回退处理（注释引用了三个真实缺陷编号）。

#### ② 结论

1. **空闲事件与任务生命周期事件是控制面最合适的信号源**，用它们替代轮询可以显著降低常驻成本。
2. **"异步钩子以特定退出码唤醒模型"是一条被验证过的第二唤醒通道**，说明唤醒机制本身应当是可插拔的多入口，而非单一通道。
3. **托管层不可被下层禁用**这一优先级规则是多租户安全的必要条件；反过来说，任何允许下层覆盖安全策略的配置系统都不适合托管场景。
4. **"工作区信任"这道守卫在云端常驻场景下没有等价物。** 参考实现依赖一次人类确认；阡陌的常驻智能体没有人在旁边，必须设计替代品，否则钩子系统就是一个远程代码执行入口。
5. **第三方提供的元数据必须当作攻击面处理**：名字、描述、注解都会进入渲染与提示词。
6. **对外暴露能力应当走协议注入，而不是修改运行时。** 该产品自己就把"作为 MCP 服务端暴露全部内建工具"作为一等能力提供。

#### ③ 我方实现差异

**当前状态：MCP 子集与钩子体系属于路线图 P-3 范围，尚未实现。** 已确定的设计决策：

- **能力注入而非运行时改造。** 阡陌的通信能力（发送消息、列举对端）与记忆能力将以**进程内 MCP 服务端**的形式注入给官方运行时，而不是修改运行时代码。理由：这使得我方能力对运行时是纯加法，运行时升级零成本，同时天然满足章程 §5.7 的"基座可退场"要求。
- **唤醒不使用退出码通道。** 结论第 2 条指出唤醒应当多入口，但我方选择让**所有入口都收敛到同一个协议消息类型**（见 §3.2）：外部事件由适配层翻译成一条唤醒信封，而不是一个特殊退出码。理由：退出码通道无法携带发送方身份、追踪标识与生存期，因而无法纳入我们的限流、防循环与审计体系。这是一处我们**有意不采纳**参考实现做法的地方。
- **信任门改为按注册能力授权。** 参考实现的"工作区信任"是一次性的人类确认，作用域是整个工作区。我方改为：能力在智能体**注册时**声明（`@qianmo/registry` 的记录中已预留能力列表字段），由注册中心按声明授权，作用域是单个智能体而非整台机器。理由：结论第 4 条——云端常驻没有"旁边的人"，且工作区粒度对多租户过粗。
- **第三方元数据统一过白名单与规范化**，不直接进入提示词渲染。理由：结论第 5 条。
- **不暴露完整工具注册表。** 参考实现作为 MCP 服务端时暴露全部内建工具；阡陌只暴露显式声明的子集。理由：托管场景下"默认全开"不可接受。

## 5. 集成路线建议

### 5.1 两条路线对比

#### 路线 (a) fork-and-patch：直接在该源码树上改造

| 维度 | 评估 |
|---|---|
| **改造成本** | 🔴 **极高**。要跑起来先得补：守护进程整个目录、后台会话管理模块、6 个缺失工具目录、跨会话消息的服务端与客户端与跨机器投递共三处空壳、对端发现与注册表、常驻助手的五个符号、上下文压缩缓存、终端调试模块，以及 23 个未声明的可选依赖。而这**只是静态可见的部分**——被特性开关包住的运行时缺失要等开关打开才暴露。此外编译期特性宏本身依赖上游的构建配置，每个开关的默认语义都需要逆推。 |
| **升级跟随成本** | 🔴 **不可行**。上游闭源，本地检出只有一个压缩提交，没有可对齐的历史。上游发新版时只能等待再次还原，然后对一个 800 KB 的单文件做三方合并。**实质上是一次性快照，不存在升级路径。** |
| **法律风险** | 🔴 **高且明确**。依赖清单声明了一个许可文件，而该文件在树中**并不存在**；提交历史是单个匿名提交；**未识别到任何有效的许可授权**。这是对专有软件的逆向还原产物。把它编译进阡陌产物、纳入镜像、或让它出现在任何公开仓库中，都直接触碰版权与合同风险，并直接违反章程 §5.4 与根 `NOTICE`。 |

#### 路线 (b) wrap-as-lib：把它当只读参考，自研运行时驱动官方发行版

| 维度 | 评估 |
|---|---|
| **改造成本** | 🟢 **低到中**。官方 SDK 自带打包好的可执行体，且其公开接口与阡陌需求高度重合（见 5.2）。阡陌只需实现监督进程、通信层、记忆层，智能体主循环完全外包。 |
| **升级跟随成本** | 🟢 **低**。走包管理器升级即可。官方 SDK 有半正式的类型契约与试验特性标识机制，破坏性变更有迹可循。 |
| **法律风险** | 🟢 **可控**。走官方分发渠道与官方许可。**注意**：官方 SDK 的许可同样是"保留所有权利、使用受其公开法律协议约束"，并非开源许可；商用前仍需确认"作为托管平台组件对第三方提供服务"这一使用方式是否被允许。但这是**可以合规完成的确认**，而路线 (a) 连确认的基础都不存在。 |

### 5.2 明确推荐：路线 (b)

推荐路线 **(b) wrap-as-lib**，并把参考树严格降级为"只读的行为分析材料"。这与章程 §5.7 把"迁移到官方 SDK"列为首选路径的判断一致。

理由按权重排序：

1. **法律风险是硬约束，不是权衡项。** 未识别到有效许可 + 不可再分发 + 逆向还原产物，三条叠加之下，(a) 不存在"接受风险后推进"的空间。章程 §6.2 已把"基座代码被误提交或被复制进自研包"列为极高影响、高概率风险（L-1），并注明**已实际发生过一次**（roadmap P0.3）。
2. **(a) 的升级路径为零。** 阡陌是平台定位，基座每落后一个版本就损失一分意义；而 (a) 的每次升级都是对一个巨型单文件的人工合并。
3. **官方 SDK 已经提供了阡陌需要的全部原语。** 我实际查阅了随依赖安装到本地的官方 SDK 的公开类型声明，确认它提供：向一个**活着的会话持续注入消息**的流式输入能力（这正是我方通信层的投递终点）；会话的列举、查询、派生、改名与多种恢复方式（可直接支撑"按名寻址 + 会话发现"）；约 28 个生命周期事件钩子，其中包含**空闲**与**任务创建/完成**（正是我方控制面需要的信号）；工具放行回调、权限模式控制、外部服务配置、**进程内 MCP 服务端构造**（正是 §3.5 所述的能力注入方式）；以及中断、模型切换、上下文用量查询等运行时控制。
4. **参考树的不可替代价值恰恰在"读"而不在"跑"。** §2 末尾指出，与阡陌相关的四类能力在公开发行版中被死代码消除了，只有在这棵树里能观察到它们的设计问题：投递语义、优先级阶梯、幂等去重、不可绕过的安全检查、进程清扫的误删事故、定时任务的重启重建。**理解这些问题是合法的；复制其表达不是。** 本文档的存在本身就是这条边界的执行记录。

### 5.3 落地形态

```
阡陌运行时（自研，Apache-2.0）
├── 监督进程            ← 参考"监督 + 流式 stdio 子进程"的问题拆解
│     └── 驱动官方 SDK / 官方 CLI 的流式会话
├── @qianmo/registry     ← 已落地：租约注册表（TTL / 心跳 / 惰性过期 / 冲突拒绝）
├── @qianmo/protocol     ← 已落地：不可变信封 / 统一寻址 / 结构性防循环 / 限流 / 稳定错误码
├── @qianmo/runtime-adapter ← 已落地：AgentNode 接缝 / 邮箱接口 / 三层记忆
└── 能力注入：以进程内 MCP 服务端形式向官方运行时暴露通信与记忆能力
```

关键决策：**通信与记忆通过协议注入，而不是改造运行时。** 这样阡陌的能力对官方运行时是纯加法，升级零成本，且 M0 结项时的 `no-vendor` CI 作业（章程 §5.7）可以直接通过。

**必须在双节点联通前补齐、且参考实现无从借鉴的三项**：

1. **发送方身份认证** —— 参考实现的发送方校验是一次字符串比较，任何能写入存储的主体都可冒充。对应 C-5。
2. **限流与跳数上限** —— 参考实现完全没有，仅靠提示词约束。我方已在协议层落地（跳数上限、生存期、体积上限、每发送方速率预算），但**接收节点的执行逻辑尚未实现**。对应 C-4。
3. **消息加密** —— 参考实现在此**零参考价值**（见 §4.4）。对应 C-3 / S-3，须完全独立设计。

## 6. 调研局限（置信度声明）

1. **未实测运行交互式启动。** 该命令会拉起 REPL 并可能触发登录与模型调用，违反本次调研约束。§1.4 的"启动会失败"结论来自静态解析，**不是运行时验证**。
2. **CLI 枢纽模块（约 800 KB 单文件）只做了检索与窄范围阅读，未通读。** 涉及该模块的结论（命令行选项、常驻助手流程、会话服务器命令）基于命中位置及其上下文，可能不完整。
3. **编译期特性开关的默认取值未知。** 全部结论均按"该开关开启时的代码路径"陈述。哪些开关在公开发行版中为真，本树无法判定。
4. **本报告中我把握最低的一条结论**：§3.1 末尾关于"该产品的常驻助手把智能体主循环放在服务端、本地只是事件流查看器"的定性。它来自若干注释表述与历史拉取接口的形状，**而不是来自完整的实现代码**（监督进程目录与安装器均缺失）。存在另一种同样成立的解读：守护进程在**本机**常驻，客户端只是连接本机守护进程，其中的"远程"指的是"另一个进程"而非"另一台机器"。**这两种解读会导向完全不同的部署架构**（前者指向"薄客户端 + 云端主循环"，后者指向"本机守护 + 多进程协作"）。建议在 A-1 动工前，用官方文档或官方 SDK 的实际行为做二次验证，不要基于本条结论直接定架构。
5. **本报告不构成法律意见。** §5 中的法律风险判断是工程视角的风险识别，正式申报与开源前应按章程 §6.2 咨询学校科技处或知识产权办公室。
